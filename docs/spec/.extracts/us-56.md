# Extract: us-56

## Summary

Added the `EARNINGS_PROXIMITY` rule to the pure alert registry — firing medium-urgency when a position's next earnings event is within 10 calendar days **and** on/before the active leg's expiration — and built the earnings-date feed it depends on: a new Finnhub integration (free tier, per-ticker calendar query, 12 h in-module cache) consumed by `evaluateAlerts` as a third concurrent degradeable boundary fetch. All four AC scenarios pass as named e2e tests, missing earnings data skips cleanly with a DEBUG log, and no schema, IPC, or renderer change was needed (the US-51 queue displays the new rule code transparently).

## Architecture Decisions

### ADR: Finnhub free tier as the earnings-date source

- **Decision:** Fetch next-earnings dates from Finnhub's earnings-calendar endpoint (`/api/v1/calendar/earnings?symbol={ticker}&from={date}&to={date}&token={key}`), one request per ticker.
- **Why:** Official, keyed, free at this app's scale (single user, handful of active tickers, 60 calls/min limit), JSON over HTTPS with query-param auth matching the existing Massive adapter conventions. Massive's own earnings data is a $99/mo Benzinga add-on — disproportionate; Alpaca has no earnings endpoint.
- **Alternatives considered:** Massive Benzinga add-on (rejected: cost), Nasdaq unofficial API (rejected: unofficial/brittle; fallback if Finnhub's free window proves too narrow), Yahoo scraping (rejected: most brittle, active anti-bot). User decision 2026-07-04: Finnhub free tier.
- **Source:** `plans/us-56/research.md`

### ADR: Standalone earnings integration module, not a `MarketDataProvider` method

- **Decision:** New `src/main/integrations/finnhub-earnings.ts` exposing a batch `fetchNextEarningsDates(tickers) → Promise<Record<ticker, isoDate>>`; it is **not** added to the `MarketDataProvider` type or the market-data factory.
- **Why:** `MarketDataProvider` is the Massive vendor seam — Massive cannot serve earnings on the current plan, so putting the method there would force every provider (including the fake) to implement a capability the primary vendor lacks. The Barchart IVR scraper (US-43) is the established precedent for a vendor-specific auxiliary feed living in its own integration module.
- **Alternatives considered:** extend `MarketDataProvider` (rejected: wrong seam), extend `BrokerProvider` (rejected: Alpaca has no earnings data), new generic multi-vendor provider abstraction (rejected: speculative — one vendor, one consumer).
- **Source:** `plans/us-56/research.md`

### ADR: Transient per-run boundary fetch with an in-module TTL cache — no SQLite table, no scheduled collector job

- **Decision:** `evaluateAlerts` pre-fetches earnings dates as a third concurrent `fetchOrDegrade` alongside stock quotes and option snapshots. The integration module holds a module-level per-ticker cache (12 h TTL, negative results cached too) so the 60 s evaluation cadence produces roughly one Finnhub burst per half-day, not one per run.
- **Why:** Matches the market-data domain invariant ("market data is transient — no SQLite rows") and the exact enrichment shape US-53/54/55 established; missing data naturally degrades to a skip. The IVR-style persisted snapshot table exists because IVR needs *history*; earnings proximity needs only the *next* date.
- **Alternatives considered:** IVR-style `earnings_snapshot` table + after-close collector job (rejected: 4 extra artifacts for data that needs no history); uncached per-run fetch (rejected: ~4k Finnhub calls per market day for near-static data).
- **Source:** `plans/us-56/research.md`

### ADR: Query window spans 7 days back to 30 days forward; prefer the next upcoming event

- **Decision:** The integration queries `from = now − 7d`, `to = now + 30d` and selects, per ticker, the earliest event with `date >= today`, falling back to the most recent past event when no upcoming event exists in the window.
- **Why:** The 30-day lookahead comfortably covers the 10-day rule (and stays inside Finnhub's free-tier window). The 7-day lookback exists purely for **alert resolution**: a recent-past event yields negative `daysToEarnings`, the predicate returns false, and the open alert resolves on the next run instead of freezing open on a skip.
- **Alternatives considered:** `from = today` only (rejected: post-earnings resolution freeze); tri-state engine input distinguishing "no event" from "feed failed" (rejected: AC 4 treats both uniformly as a skip; flat `null → skip` matches every existing rule input).
- **Source:** `plans/us-56/research.md`

### ADR: Engine input carries precomputed `daysToEarnings` plus raw `expiration`

- **Decision:** Extend `AlertEvaluationInput` with `daysToEarnings: number | null` (computed in the service via the shared `computeDte(nextEarningsDate, now)`) and `expiration: string | null` (raw leg expiration, needed by the summary template). Predicate: `daysToEarnings >= 0 && daysToEarnings <= 10 && daysToEarnings <= dte`.
- **Why:** The engine is pure and has no `now`, so day-count math happens at the boundary — exactly how `dte` already works. Comparing two `computeDte` results is equivalent to `earningsDate <= expirationDate` and reuses one date-math code path (no string comparisons, per the date-handling standard). A narrow `EarningsProximityInput` Pick-slice types the summary helper, per the established helper-input convention (final slice: `'daysToEarnings' | 'expiration'`).
- **Alternatives considered:** passing raw `nextEarningsDate` into the engine (rejected: engine lacks `now`); lexicographic ISO string comparison (rejected: date-handling standard requires date-fns).
- **Source:** `plans/us-56/research.md`, `plans/us-56/refactor-phase-results.md`

### ADR: Finnhub API key via env-var loader, mirroring Massive credentials

- **Decision:** `loadFinnhubApiKey()` reads `import.meta.env.MAIN_VITE_FINNHUB_API_KEY` with a `process.env.FINNHUB_API_KEY` runtime fallback (the `massive-credentials.ts` pattern). A missing key makes the batch fetch log one WARN and return empty — the rule skips everywhere and every other rule is unaffected.
- **Why:** Simplest precedent that already exists for a static per-install key; no settings UI, no encrypted storage, no migration. The app must remain fully functional without the key (failure-isolation ADR).
- **Alternatives considered:** encrypted `credential_settings` + Settings UI like Alpaca (rejected: outside scope; can be promoted later).
- **Source:** `plans/us-56/research.md`

### ADR: Rule shape — medium urgency, phase-agnostic over open short legs, co-fires with existing rules

- **Decision:** `EARNINGS_PROXIMITY` is `urgency: 'medium'`, quick action `Review position`, applies to any evaluable position (`CSP_OPEN` or `CC_OPEN`), and co-fires independently of the DTE/profit/proximity rules. Skip reasons: `missing_dte` when `dte === null`; `missing_expiration` when `expiration === null` (added post-review — the summary interpolates it); `missing_earnings_date` when `daysToEarnings === null`. Constant `EARNINGS_PROXIMITY_MAX_DAYS = 10`.
- **Why:** Medium urgency and the summary template come verbatim from the ACs. Gap-risk applies to CSPs and CCs alike. Co-firing follows the US-53/54/55 decision — orthogonal conditions, no AC asks for suppression.
- **Alternatives considered:** suppressing EARNINGS_PROXIMITY inside the EXPIRATION_IMMINENT window (rejected: no cross-rule precedence exists or is asked for).
- **Source:** `plans/us-56/research.md`

## Contracts

### finnhub-earnings-calendar (external HTTP contract)

- **Type:** other (external vendor HTTP contract; no new IPC handler — the renderer reads new alerts through the existing `alerts:list` channel unchanged)
- **Shape:**

```typescript
// GET https://finnhub.io/api/v1/calendar/earnings
// One request per ticker; auth via `token` query param (Finnhub free tier).
interface FinnhubEarningsRequest {
  symbol: string // uppercased ticker, e.g. 'NVDA'
  from: string   // 'YYYY-MM-DD' — now − EARNINGS_LOOKBACK_DAYS (7)
  to: string     // 'YYYY-MM-DD' — now + EARNINGS_LOOKAHEAD_DAYS (30)
  token: string  // loadFinnhubApiKey()
}

// HTTP 200
interface FinnhubEarningsResponse {
  earningsCalendar: Array<{
    date: string // 'YYYY-MM-DD' — the only field the story consumes
    symbol: string
    hour?: 'bmo' | 'amc' | 'dmh' | ''
    quarter?: number
    year?: number
    epsEstimate?: number | null
    epsActual?: number | null
  }>
}
// Empty earningsCalendar array = no events in the window (valid; cached as null → rule skips).

// Internal batch wrapper:
export async function fetchNextEarningsDates(
  tickers: string[],
  opts?: { now?: Date; logger?: LoggerLike }
): Promise<Record<string, string>> // ticker → selected event date; failed/eventless tickers absent
```

  Error behavior (isolated per ticker, never thrown to the batch caller): missing key → `{}` + WARN `earnings_fetch_no_api_key` (once per process); 401/403 → WARN `earnings_fetch_failed` code `auth_failed`; 429 → `rate_limited`; network/other → `network_error` / `unknown`; empty calendar → DEBUG `earnings_no_event_in_window`, null cached. Failures are negatively cached for 5 minutes (`EARNINGS_FAILURE_TTL_MS`, added post-review) so a rate-limited ticker backs off instead of refiring on every 60 s run; calendar rows without a valid `YYYY-MM-DD` date string are dropped before event selection. A whole-feed outage degrades to an empty record; `evaluateAlerts` additionally wraps the batch call in `fetchOrDegrade` (WARN `alert_evaluation_earnings_unavailable`).

- **Source:** `plans/us-56/contracts/finnhub-earnings-calendar.md`
- **Implementation:** `src/main/integrations/finnhub-earnings.ts`; key loader `src/main/integrations/finnhub-credentials.ts`; consumed by `src/main/services/evaluate-alerts.ts` (third concurrent boundary fetch, injectable `FetchEarnings` seam)

## Schema Changes

None recorded. The story reuses the US-50 `alerts` table — `rule_code` is plain TEXT, so `'EARNINGS_PROXIMITY'` is just a new value under the existing partial unique open index. No migration, no `schemas.ts` change.

## Acceptance Criteria

- Alert fires when earnings are within 10 calendar days and before expiration (NVDA CC_OPEN, expiration 2026-08-21, earnings 2026-08-14, today 2026-08-08 → medium-urgency EARNINGS_PROXIMITY, summary exactly `Earnings in 6 days before your 2026-08-21 expiration`)
- Alert does not fire when earnings are more than 10 days away (expiration 2026-08-27, earnings 2026-08-21, today 2026-08-08)
- Alert does not fire when earnings occur after the option expires (expiration 2026-08-15, earnings 2026-08-18, today 2026-08-10)
- Missing earnings data skips the rule without failing the run, and the engine records a debug log that the rule was skipped

Each AC has exactly one named e2e test in `src/main/services/evaluate-alerts.e2e.test.ts` (`describe('US-56 acceptance — EARNINGS_PROXIMITY')`).

## Decisions & Tradeoffs

- **Post-earnings skip-freeze tail (accepted limitation):** if earnings pass and the next event is beyond the 30-day window **and** the 7-day lookback has rolled off, the input goes null → skip → an open alert would freeze; in practice the lookback covers the resolution window. (`plans/us-56/research.md`)
- **No confirmed-vs-projected distinction:** Finnhub's free calendar has no `date_status`; every returned date is treated as actionable. (`plans/us-56/research.md`)
- **Summary wording (revised post-review):** the original decision was always-plural `days` (`plans/us-56/research.md`), but the code-review pass flagged "Earnings in 1 days" as user-facing broken copy at the highest-urgency moment; the summary now renders `today` / `in 1 day` / `in {N} days`. The AC-pinned 6-day string is unchanged.
- **No Playwright e2e / no env-var fake seam:** AC coverage lives in the vitest `evaluate-alerts.e2e.test.ts` suite with an injected earnings stub, as US-53/54/55 did; a `WHEELBASE_FAKE_EARNINGS` seam can be added later if manual QA needs it. (`plans/us-56/research.md`)
- **Test determinism:** `makeInput` core-test default is `daysToEarnings: 45` (inert), not null; service test files `vi.mock` the Finnhub module so un-injected tests never reach the network; `stubEarnings(map)` / `inertEarnings()` fixtures added to `evaluate-alerts-test-utils.ts`. (`plans/us-56/red-phase-results.md`, `plans/us-56/green-phase-results.md`)
- **Refactor consolidations:** shared `LoggerLike` hoisted to `src/main/logger.ts`; `FetchEarnings` seam type owned/exported by the service; `EarningsProximityInput` tightened to the two fields the summary helper reads. (`plans/us-56/refactor-phase-results.md`)
