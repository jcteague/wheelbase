# Extract: us-14

## Summary

US-14 adds the CC (Covered Call) roll operation — the mirror image of the CSP roll (US-12). When a trader is in `CC_OPEN` phase, they can close the current call (ROLL_FROM BUY CALL) and open a new one at a different strike or expiration (ROLL_TO SELL CALL) as a linked pair, with the net credit or debit updating the cost basis. The done state is a working "Roll CC →" button on the detail page that opens a right-side sheet, validates inputs, previews the net credit/debit, warns when the new strike is below cost basis, and creates the linked leg pair on confirm. The CC roll reuses `calculateRollBasis()` unchanged and follows the exact CSP roll architecture (lifecycle → service → IPC → preload → API adapter → hook → sheet/form/success).

## Architecture Decisions

### ADR: Replicate CSP Roll Architecture, Don't Generalize

- **Decision:** The CC roll follows the exact CSP roll architecture. All patterns (lifecycle → service → IPC → preload → API adapter → hook → sheet/form/success) are replicated with CALL instead of PUT, adjusted validations, and CC-specific UI.
- **Why:** The codebase has a clear, consistent implementation of CSP roll (US-12). Deviating from it would create inconsistency.
- **Alternatives considered:** Generalizing a single `rollPosition()` function with an `instrumentType` flag — rejected because the lifecycle validations are meaningfully different (expiration `>=` vs `>`, no-change guard) and CC adds the below-cost-basis warning which is CC-specific.
- **Source:** `plans/us-14/research.md`

### ADR: Lifecycle Validation Differences for CC

- **Decision:** `rollCc()` validates `newExpiration >= currentExpiration` (on or after), whereas `rollCsp()` validates `newExpiration > currentExpiration` (strictly after). Additionally, `rollCc()` must reject the case where both strike and expiration are unchanged.
- **Why:** CC rolls can be "same expiration, higher strike" (Roll Up) which is a valid and common scenario. The no-change guard prevents a no-op transaction from being recorded.
- **Alternatives considered:** Putting no-change validation only on the renderer — rejected because defense-in-depth is preferred; the lifecycle engine should be the source of truth for business rules.
- **Source:** `plans/us-14/research.md`

### ADR: New `getCcRollTypeLabel()` (originally `getCcRollType()`) Function

- **Decision:** Extend `src/renderer/src/lib/rolls.ts` with a new `getCcRollType()` function (renamed during refactor to `getCcRollTypeLabel`) that returns one of: `'Roll Up & Out'`, `'Roll Down & Out'`, `'Roll Up'`, `'Roll Down'`, `'Roll Out'`, `'No Change'`. Add `getCcRollTypeColor()` returning CSS variable strings.
- **Why:** The existing `getRollTypeLabel()` only handles strike comparison, not expiration comparison. CC rolls can keep the same expiration (Roll Up / Roll Down) — a scenario that doesn't arise in CSP rolls (which always require a later expiration).
- **Alternatives considered:** Overloading the existing function — rejected because it changes the signature for existing callers.
- **Source:** `plans/us-14/research.md`, `plans/us-14/refactor-phase-results-cc-roll-type.md`

### ADR: Below-Cost-Basis Warning is Renderer-Only

- **Decision:** Computed purely on the renderer inside `RollCcForm`. Compare `newStrike < basisPerShare` (numerically). Show amber `AlertBox variant="warning"` with exact loss-per-share amount. Non-blocking — the confirm button stays enabled.
- **Why:** Technical notes explicitly call this a renderer-side calculation. Experienced traders may intentionally sell a CC below basis in defensive scenarios (e.g., stock has dropped significantly).
- **Alternatives considered:** Backend validation error — explicitly excluded by Technical Notes.
- **Source:** `plans/us-14/research.md`

### ADR: Reuse `calculateRollBasis()` Unchanged for CC

- **Decision:** Reuse `calculateRollBasis()` from `src/main/core/costbasis.ts` unchanged. Net credit (newPremium − costToClose) reduces basis per share; net debit increases it.
- **Why:** The math is identical to CSP roll — the instrument type (CALL vs PUT) doesn't affect the cost basis formula. The function is already generic.
- **Alternatives considered:** A separate `calculateCcRollBasis()` — unnecessary duplication.
- **Source:** `plans/us-14/research.md`

### ADR: `newStrike` Optional in Schema, Defaults to Current Strike

- **Decision:** `newStrike` is `z.number().positive().optional()` in `RollCcPayloadSchema`. If omitted, the service defaults to `activeLeg.strike`. The lifecycle engine receives the resolved `newStrike` alongside `currentStrike` to check for no-change.
- **Why:** Consistent with `RollCspPayloadSchema` where `newStrike` is optional. The roll form pre-fills the current strike so the user always has a value; the optional pattern enables programmatic callers to omit it when keeping the same strike.
- **Source:** `plans/us-14/research.md`

### ADR: No New Database Migrations

- **Decision:** No new tables or columns. The CC roll writes to existing `legs` and `cost_basis_snapshots` tables with `instrument_type = 'CALL'`, `leg_role = 'ROLL_FROM'` / `'ROLL_TO'`.
- **Why:** The schema already supports CALL instrument type (used by CC_OPEN legs). Roll legs follow the exact same structure as CSP roll legs.
- **Source:** `plans/us-14/research.md`, `plans/us-14/data-model.md`

### ADR: Extract Shared `RollPayloadBaseSchema` and `RollResultBase` (Refactor)

- **Decision:** During refactor, `RollCspPayloadSchema` and `RollCcPayloadSchema` were consolidated to be assigned from a single `RollPayloadBaseSchema`. Similarly, `RollCspResult` and `RollCcResult` extend a shared `RollResultBase` interface adding only their differing `position.phase` literal. Date validation extracted to constants `IsoDateRegex` and `IsoDateMessage`.
- **Why:** The two schemas were field-for-field identical Zod objects (6 identical fields including the date regex). The only semantic difference between the result types is the phase literal (`'CSP_OPEN'` vs `'CC_OPEN'`); all other fields are identical.
- **Source:** `plans/us-14/refactor-phase-results.md`

## Contracts

### positions:roll-cc

- **Type:** IPC handler
- **Shape:**

  Request payload (validated by `RollCcPayloadSchema`):

  ```ts
  {
    positionId: string           // UUID — position in CC_OPEN phase
    costToClosePerContract: number   // positive — buy-to-close price
    newPremiumPerContract: number    // positive — sell-to-open price
    newExpiration: string        // YYYY-MM-DD — must be >= current CC expiration
    newStrike?: number           // positive — defaults to current CC strike if omitted
    fillDate?: string            // YYYY-MM-DD — defaults to today
  }
  ```

  Success response (`{ ok: true, ...RollCcResult }`):

  ```ts
  {
    ok: true
    position: {
      id: string
      ticker: string
      phase: 'CC_OPEN'
      status: 'ACTIVE'
    }
    rollFromLeg: LegRecord // BUY CALL — closes old CC
    rollToLeg: LegRecord // SELL CALL — opens new CC
    rollChainId: string // UUID linking the two legs
    costBasisSnapshot: CostBasisSnapshotRecord
  }
  ```

  Error response:

  ```ts
  {
    ok: false
    errors: Array<{ field: string; code: string; message: string }>
  }
  ```

  Error codes:
  | Field | Code | Message | Trigger |
  | --- | --- | --- | --- |
  | `__phase__` | `invalid_phase` | `'No open covered call on this position'` | Not CC_OPEN |
  | `newExpiration` | `must_be_on_or_after_current` | `'New expiration must be on or after the current expiration (MMM DD, YYYY)'` | newExpiration < currentExpiration |
  | `__roll__` | `no_change` | `'Roll must change the expiration, strike, or both'` | newStrike == currentStrike AND newExpiration == currentExpiration |
  | `costToClosePerContract` | `must_be_positive` | `'Cost to close must be greater than zero'` | <= 0 |
  | `newPremiumPerContract` | `must_be_positive` | `'New premium must be greater than zero'` | <= 0 |
  | `__root__` | `not_found` | `'Position not found'` | Bad positionId |
  | `__root__` | `no_active_leg` | `'Position has no active leg'` | Data integrity issue |

- **Source:** `plans/us-14/contracts/roll-cc.md`
- **Implementation:** `src/main/ipc/positions.ts`

## Schema Changes

No new database tables, columns, or migrations. The CC roll persists into existing tables:

### legs

- **Change:** new rows written (no schema change)
- **Columns / fields:** Each roll writes two rows:
  - ROLL_FROM (BUY CALL — close current CC): `leg_role='ROLL_FROM'`, `action='BUY'`, `instrument_type='CALL'`, `strike`=current CC strike, `expiration`=current CC expiration, `contracts` inherited from `activeLeg.contracts`, `premium_per_contract=costToClosePerContract`, `fill_price=costToClosePerContract`, `fill_date`=payload `fillDate` or today, `roll_chain_id`=new UUID
  - ROLL_TO (SELL CALL — open new CC): `leg_role='ROLL_TO'`, `action='SELL'`, `instrument_type='CALL'`, `strike=newStrike` (or current if omitted), `expiration=newExpiration`, `contracts` inherited, `premium_per_contract=newPremiumPerContract`, `fill_price=newPremiumPerContract`, `fill_date`=payload `fillDate` or today, `roll_chain_id`=same UUID as ROLL_FROM
- **Source:** `plans/us-14/data-model.md`
- **Migration file:** None (no migration)

### cost_basis_snapshots

- **Change:** new row written per roll (no schema change)
- **Columns / fields:** One snapshot per roll computed via `calculateRollBasis()`:
  ```
  net = newPremiumPerContract − costToClosePerContract
  basisPerShare = prevBasisPerShare − net
  totalPremiumCollected = prevTotalPremiumCollected + (net × contracts × 100)
  ```
- **Source:** `plans/us-14/data-model.md`
- **Migration file:** None

### positions

- **Change:** no rows updated (phase remains `CC_OPEN`)
- **Source:** `plans/us-14/data-model.md`

## Acceptance Criteria

- Roll form shows current CC details (strike, expiration, DTE, premium collected) and cost basis context when opened.
- Net credit preview shows for CC roll up and out (e.g., "Roll Up & Out: $185 → $190 strike, Apr → May expiration"); displays "+$0.70/contract" and "$70.00 total".
- Amber warning shown when new CC strike is below cost basis (e.g., new strike $175 vs basis $176.50 → "$1.50/share" loss); warning is non-blocking, confirm button stays enabled.
- Successful CC roll creates linked ROLL_FROM (BUY CALL) and ROLL_TO (SELL CALL) leg pair sharing the same `roll_chain_id`; success screen shows "CC Rolled Successfully", "Roll Complete", phase remains `CC_OPEN`, cost basis transition shown (e.g., $176.50 → $175.80/share).
- CC roll out accepted with same strike and later expiration; label shows "Roll Out".
- CC roll down and out accepted with lower strike and later expiration; label shows "Roll Down & Out".
- CC roll up accepted with same expiration and higher strike; label shows "Roll Up".
- Net debit preview shown when cost to close exceeds new premium (e.g., cost $5.00, premium $3.50 → "-$1.50/contract", "$150.00 total"); roll can still be confirmed.
- Validation error shown when new expiration is before current expiration: "New expiration must be on or after the current expiration (...)"; success screen NOT shown.
- Validation error shown when neither strike nor expiration changed: "No change detected" / "Roll must change the expiration, strike, or both"; Confirm Roll button is disabled.
- Validation error shown when cost to close is zero: "Cost to close must be greater than zero".

## Decisions & Tradeoffs

- **CSP architectural mirror over generalization:** Per CLAUDE.md style ("avoid premature abstraction — three similar lines of code is better than a premature abstraction"), the plan explicitly chose not to generalize a single `rollPosition()` function. The refactor phase later extracted a `RollPayloadBaseSchema` and `RollResultBase` interface once the duplication was concrete and identical.
- **`getCcRollType` renamed to `getCcRollTypeLabel` during refactor** for naming consistency with the existing CSP `getRollTypeLabel`.
- **No-change validation lives in lifecycle engine, not just renderer:** Even though the button is disabled in the UI, the lifecycle engine throws `no_change` as defense-in-depth.
- **Below-cost-basis is a warning, not an error:** Experienced traders may intentionally sell a CC below basis for defensive reasons; the warning is non-blocking.
- **`newStrike` is optional in payload, defaults server-side:** The form pre-fills it so users always have a value, but programmatic callers can omit it when keeping the same strike.
- **`NetCreditDebitPreview` duplication noted as potential refactor:** The plan flags that this component may be duplicated between `RollCspForm` and `RollCcForm` and could be extracted to `src/renderer/src/components/ui/NetCreditDebitPreview.tsx` if identical.
- **Hook is a one-liner wrapper:** `useRollCc` has no dedicated test file because it's a thin wrapper over `usePositionMutation`; coverage comes from the sheet integration tests.
- **`overlayOpen` derivation:** `rollCcOpen` must be OR'd into the `overlayOpen` expression in `usePositionDetailSheets` so the page content blurs when the sheet opens.
