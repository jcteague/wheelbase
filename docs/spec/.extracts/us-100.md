# Extract: us-100

## Summary

IV rank is collected the moment a ticker enters the app — a watchlist add or a manually
entered position — and an explicit "Refresh IVR now" is no longer refused on a weekend or
a market holiday, while the nightly scheduled run keeps its calendar guard. Every reading
is stamped at the close of the exchange session it belongs to, so a weekend fetch
refreshes Friday's row instead of inventing a Saturday one, and `ivr_snapshot` holds at
most one row per underlying per session. No migration: `ivr_snapshot`, `watchlist` and
`trading_session` are unchanged in shape; only the meaning of `ivr_snapshot.observed_at`
changed.

## Architecture Decisions

### ADR: The non-trading-day guard is scoped by trigger, not deleted

- **Decision:** `collectIVRSnapshots` takes `trigger?: 'scheduled' | 'explicit'`,
  defaulting to `'scheduled'`. A `closed` calendar verdict returns
  `skippedReason: 'market_closed'` only for a scheduled run; an explicit run logs
  `IVR collection proceeding on a closed day at explicit request` and proceeds. An
  explicit run can never return `market_closed`.
- **Why:** The guard exists to avoid pointless *scheduled* fetches. A trader clicking
  refresh, or adding a ticker, has stated their intent, and Barchart needs no broker
  credentials and serves the last close whenever it is asked — so there is no
  market-hours dependency in the data source itself, only in a guard written for the
  other caller. Scheduled runs become strictly stricter (weekends **and** holidays),
  which is the ask in `followup-ivr-trading-day-calendar.md`; explicit runs stop
  consulting the calendar for permission at all.
- **Alternatives considered:** A boolean named `force` — rejected as it does not say who
  is asking. Having `ivr:collect-now` call `collectIVRSnapshots` directly instead of
  routing through the scheduler — simpler, but loses the scheduler's run tracking and
  the join-in-flight concurrency guard.
- **Source:** `plans/us-100/research.md`, `plans/us-100/plan.md`

### ADR: A reading is stamped at the session close it reflects, not the fetch instant

- **Decision:** `persistSnapshot` resolves
  `session = getMostRecentCompletedSession(calendar, parseISO(observedAt))` and writes
  `observed_at = session.closeAt`. The dedupe delete runs over that session's
  half-open observation window `[session.closeAt, nextSession.closeAt)` rather than the
  UTC calendar day. When the calendar cannot place the instant, the raw fetch instant is
  written and `ivr_observation_unstamped` is warned.
- **Why:** Barchart derives IV rank from the **last close**, so a Saturday fetch and a
  Sunday fetch are the same observation. Keying on the UTC day of the fetch stored both,
  producing two rows carrying Friday's values under two different dates. `ivr_snapshot`
  is a time series US-98 ages in completed exchange sessions, so a weekend row makes a
  Friday reading look fresher than it is, and any percentile work computed over stored
  rows would be skewed by duplicated non-observations. Stamping the observation
  preserves the invariant every reader already assumed: a row means "a trading day's
  close".
- **Alternatives considered:** Allow weekend rows and teach readers to tolerate them —
  simpler to build, but pushes the problem onto US-98 and everything downstream.
- **Source:** `plans/us-100/research.md`, `plans/us-100/data-model.md`

### ADR: The invariant is enforced by the delete window, not a constraint

- **Decision:** At most one row per `underlying` per session, enforced by
  `persistSnapshot`'s delete window. The primary key stays `(underlying, observed_at)`
  and a same-session overwrite remains delete-then-insert.
- **Why:** Keeps the existing overwrite mechanism and requires no migration.
- **Source:** `plans/us-100/data-model.md`

### ADR: On-demand collection is a single-ticker path, not the batch

- **Decision:** A new `IvrOnDemand` port (`createIvrOnDemand`) collects exactly one
  ticker. The per-ticker body is extracted from the batch loop as
  `collectTicker({ db, logger, fetchIvr, calendar, ticker })` returning
  `'persisted' | 'not_available' | 'failed'`, and is shared by both callers. The
  on-demand path never runs `COLLECTION_TARGETS_QUERY`.
- **Why:** Reusing `collectIVRSnapshots` per add would refetch the entire
  positions ∪ watchlist bench on every add. Sharing only the per-ticker body stops the
  two paths drifting apart.
- **Source:** `plans/us-100/plan.md`, `plans/us-100/data-model.md`

### ADR: The add never waits on the network, and collection never fails it

- **Decision:** `addWatchlistEntry` and `createPosition` take an optional
  `ivrOnDemand` and fire `void ivrOnDemand?.collect(ticker)` **after** the write has
  committed and after their existing INFO log. `IvrOnDemand.collect` is documented and
  tested as never rejecting — its whole body sits in a `try/catch` that logs and
  swallows.
- **Why:** `watchlist:add` is a user-facing IPC call and a ~1s Barchart fetch inside it
  makes the add feel broken. Because the call is detached, a rejection would surface as
  an unhandled rejection and make a good add look like a failure. This is CLAUDE.md's
  boundary-I/O degradation rule and the `alert-evaluation-failure-isolation` precedent.
  The duplicate-ticker `ValidationError` is thrown before the insert, so a rejected add
  never triggers collection.
- **Source:** `plans/us-100/plan.md`, `plans/us-100/data-model.md`

### ADR: The renderer learns about a late reading from a push event

- **Decision:** `onCollected(ticker)` sends `ivr:snapshot-updated` on the main window's
  `webContents`; `useIvrSnapshotUpdates` subscribes and invalidates
  `watchlistQueryKeys.snapshot` and `screenerQueryKeys.results`.
- **Why:** The add response has already returned by the time the reading lands, and
  `useWatchlistSnapshot` has no `refetchInterval` by design, so without the push the new
  card would read `n/a` until a manual reload. Follows the `market-data:stock-quote`
  precedent from US-32.
- **Source:** `plans/us-100/contracts/ivr-snapshot-updated.md`

### ADR: The scheduler tells a handler which trigger started the run

- **Decision:** `JobHandler = (ctx: JobRunContext) => Promise<unknown>` with
  `JobRunContext = { trigger: 'scheduled' | 'explicit' }`. A timer tick passes
  `'scheduled'`; `runNow(name, opts?)` defaults to `'explicit'`. A `runNow` that joins an
  in-flight run keeps the trigger that run started with — the joiner's context is never
  handed to a handler already executing.
- **Why:** `ivr:collect-now` routes through `scheduler.runNow` into the registered
  handler, so the trigger has to travel through the scheduler for the guard split to
  reach the collector at all.
- **Source:** `plans/us-100/data-model.md`, `plans/us-100/plan.md`

### \_test:scheduler-run-scheduled (new, dev-only)

- **Type:** IPC handler, registered only when `NODE_ENV === 'test'`
- **Shape:** `jobName: string` → the handler's result. Calls
  `scheduler.runNow(jobName, { trigger: 'scheduled' })`; unlike
  `_test:scheduler-run-now`, it returns the result.
- **Why it exists:** the only way a spec can assert that a *scheduled* run still refuses

  reason.
- **Source:** `plans/us-100/contracts/dev-only-test-channels.md`
- **Implementation:** `src/main/ipc/test-scheduler.ts`

## Schema Changes

### ivr_snapshot (no migration — semantic change only)

- **Change:** the value carried by an existing column
- **Columns / fields:** `observed_at` was the ISO instant of the **fetch**; it is now the
  ISO instant of the **close of the session the reading belongs to**
  (`TradingSession.closeAt`), falling back to the fetch instant only when the calendar
  cannot speak for that instant. `underlying`, `ivr`, `ivp`, `iv30` and `source` are
  unchanged.
- **Invariant introduced:** at most one row per `underlying` per exchange session,
  enforced by `persistSnapshot`'s delete window rather than by a constraint. The primary
  key stays `(underlying, observed_at)`.
- **Source:** `plans/us-100/data-model.md`
- **Migration file:** none — `ivr_snapshot` (007), `watchlist` (012) and
  `trading_session` (015) are unchanged in shape.

## Acceptance Criteria

Background: the trader holds an open CSP on MSFT, and the watchlist contains KO.

- Adding a ticker to the watchlist collects its IVR immediately
- Adding a ticker collects only that ticker
- Adding a ticker that already has a reading for the day does not refetch
- The add succeeds even when the IVR fetch fails
- A ticker Barchart does not cover is added without an IV rank
- Opening a position collects its IVR immediately
- Opening a position for an already-collected ticker does not refetch
- The position is created even when the IVR fetch fails
- Manual refresh works on a weekend
- Manual refresh works on a weekday market holiday
- A weekend reading is stored against the trading day it belongs to
- The scheduled run still skips a weekend
- The scheduled run still fires after hours on a weekday

## Decisions & Tradeoffs

- **`trigger`, not `force`.** A named trigger says *who is asking*; a boolean only says
  that the guard is being overridden.
- **Same-day dedupe reads the database, not an in-memory cache.** "Already has a reading
  for the day" is answered from `ivr_snapshot` via `getLatestIvrByUnderlying`, so a
  restart cannot lose it. Attribution is by session: the reading's session equals the
  current session. With no calendar at all, it degrades to Eastern-calendar-day equality.
- **`ensureTradingCalendar` is awaited before the stamp is resolved.** On a fresh install
  the calendar is empty, so an unawaited refresh would write the reading at the raw fetch
  instant and US-98 would assess it as unreadable — the reading would exist and still
  render `n/a`.
- **`not_available` stays a skip, not an error.** Bench names are likelier to be
  uncovered than held names.
- **The two services deliberately share no abstraction.** `addWatchlistEntry` and
  `createPosition` end with the same two lines (INFO log, `void ivrOnDemand?.collect`).
  That is two call sites of a port, not a concept.
- **`utcDayBounds` survives only as the unstamped fallback**, named and commented as
  such.
- **Sequential batch pacing is unchanged.** `fetchIVR` awaits its own 1 req/s limiter, so
  the batch loop adds no sleep; the single-ticker path has no pacing concern.
