# Extract: us-52

## Summary

US-52 formalizes the **expiration-imminent alert** as a dedicated, high-urgency rule that fires for active short option legs at 5 DTE or less (`0 <= dte <= 5`). Almost all of the behavior already existed inside the shared alert engine delivered by US-50 (rule registry, `computeDte`, `evaluateAlerts` compute/persist lifecycle) and the management-queue read path from US-51. The story's work was therefore primarily **regression hardening**: adding US-52-named direct test coverage at the core, service, and e2e layers, plus a small e2e helper consolidation. No production code changes were required in `src/main/core/alerts.ts`, `src/main/core/dte.ts`, `src/main/services/evaluate-alerts.ts`, or `src/main/services/alerts.ts`. No migration, IPC contract, or renderer view-model was added.

## Architecture Decisions

### ADR: Build US-52 on the existing US-50/US-51 alert backbone

- **Decision:** Implement US-52 on top of the existing alert-engine stack (US-50) and management-queue read path (US-51), with no new migration, IPC channel, or renderer contract.
- **Why:** The codebase already has the `alerts` table, `evaluateAlerts(...)` orchestration, the `alerts:list` surface, and dashboard rendering for persisted alerts. The story only needs to define and preserve one built-in rule's behavior in that pipeline.
- **Alternatives considered:** A story-specific table, IPC channel, or dashboard component — rejected as duplication of existing persistence/queue layers.
- **Source:** `plans/us-52/research.md`

### ADR: EXPIRATION_IMMINENT stays a fixed built-in threshold (0 <= dte <= 5)

- **Decision:** Keep `EXPIRATION_IMMINENT` as a fixed built-in rule matching only when `0 <= dte <= 5`, with no dependency on the configurable management-window threshold (`managementWindowDte`).
- **Why:** The story's technical notes state `DTE <= 5` is fixed for this epic and must remain distinct from the later configurable management-window behavior.
- **Alternatives considered:** Reuse `managementWindowDte` or make the threshold configurable now — rejected to preserve the separation between US-52 and later settings stories.
- **Source:** `plans/us-52/research.md`
- **Verified in source:** `src/main/core/alerts.ts` — `EXPIRATION_IMMINENT_MAX_DTE = 5`; predicate `input.dte !== null && input.dte >= 0 && input.dte <= EXPIRATION_IMMINENT_MAX_DTE`.

### ADR: Encode rule precedence via mutually exclusive DTE ranges

- **Decision:** Keep `EXPIRATION_IMMINENT` and `MANAGEMENT_WINDOW` mutually exclusive in the rule registry (`dte <= 5` vs `dte > 5`) rather than emitting both and deduping downstream.
- **Why:** The expiration-imminent alert is "louder" than a normal management reminder; exclusive ranges are simpler and easier to regression-test than downstream dedup.
- **Alternatives considered:** Emit both inside 5 DTE and suppress the lower-urgency row during persistence/rendering — rejected as it complicates persistence and weakens the rule contract.
- **Source:** `plans/us-52/research.md`
- **Verified in source:** `src/main/core/alerts.ts` — `MANAGEMENT_WINDOW.test` requires `input.dte > EXPIRATION_IMMINENT_MAX_DTE && input.dte <= managementWindowDte`.

### ADR: Use the shared calendar-day DTE helper

- **Decision:** Continue using `computeDte(expiration, now)` from `src/main/core/dte.ts` as the only DTE calculation feeding the rule, based on `differenceInCalendarDays(parseISO(expiration), now)`.
- **Why:** Keeps summaries/queue messaging consistent with market-data surfaces; repo standard requires `date-fns` calendar comparisons, not timestamp slicing.
- **Alternatives considered:** Recompute DTE inline in `evaluate-alerts.ts` or renderer helpers — rejected for drift risk.
- **Source:** `plans/us-52/research.md`
- **Verified in source:** `src/main/core/dte.ts` uses `differenceInCalendarDays(parseISO(expiration), now)`; returns `null` when expiration is absent; counts whole calendar days so time-of-day does not cause off-by-one.

### ADR: Phase gating lives in the evaluation target query

- **Decision:** Enforce "open short option legs only" in `src/main/services/evaluate-alerts.ts` by restricting the evaluable-position query to active `CSP_OPEN` and `CC_OPEN` positions with an active option leg (`activeLegSubquery()`); the core engine stays focused on DTE and summary generation.
- **Why:** The rule should never consider `HOLDING_SHARES`; the service already filters to the named phases before the pure engine runs.
- **Alternatives considered:** Add phase checks inside `evaluatePosition(...)` — rejected; the service guarantees the eligible set.
- **Source:** `plans/us-52/research.md`
- **Verified in source:** `src/main/services/evaluate-alerts.ts` — `EVALUABLE_QUERY` uses `WHERE p.status = 'ACTIVE' AND p.phase IN ('CSP_OPEN', 'CC_OPEN')` joined to `activeLegSubquery()`.

### ADR: Resolution reuses global open-alert resolution

- **Decision:** Let expiration-imminent alerts resolve through the existing `resolveAlertsNotIn(...)` flow when the active leg is closed, expires out of scope, or otherwise stops matching on a later evaluation.
- **Why:** The final scenario is lifecycle cleanup, not a custom resolution pathway; the compute-then-persist pipeline already resolves unmatched open alerts globally.
- **Alternatives considered:** A story-specific "resolve expiration imminent" branch — rejected as duplication.
- **Source:** `plans/us-52/research.md`
- **Verified in source:** `src/main/services/alerts.ts` — `resolveAlertsNotIn` marks every open alert whose `(positionId, ruleCode)` key is absent from the matched set as `resolved`.

## Contracts

### EXPIRATION_IMMINENT rule (core engine)

- **Type:** pure rule definition in the `RULES` registry (no IPC/broker)
- **Shape (rule output `AlertMatch`):**

```ts
{
  ruleCode: 'EXPIRATION_IMMINENT',
  urgency: 'high',
  summary: `Expires in ${dte} days at $${strike.toFixed(2)} strike`, // e.g. "Expires in 5 days at $180.00 strike"
  quickAction: 'Review position'
}
```

- **Predicate:** `input.dte !== null && input.dte >= 0 && input.dte <= 5`. Matches `0..5`; does not match `dte >= 6` or `dte < 0`; skips with reason `missing_dte` when `dte === null`.
- **Source:** `plans/us-52/data-model.md`, `plans/us-52/plan.md`
- **Implementation:** `src/main/core/alerts.ts` (`RULES[0]`, `expirationImminentSummary`, `formatStrike`, `QUICK_ACTION_REVIEW`)

### AlertEvaluationInput (derived engine input)

- **Type:** Zod-free plain-value interface passed from service to core engine
- **Shape:** `{ positionId: string; phase: WheelPhase; instrumentType: 'PUT'|'CALL'|null; strike: string|null (4dp TEXT); dte: number|null; managementWindowDte?: number }`. `managementWindowDte` is present on the shared input but **not used** by EXPIRATION_IMMINENT matching.
- **Source:** `plans/us-52/data-model.md`
- **Implementation:** `src/main/core/alerts.ts` (`AlertEvaluationInput`), built by `toEvaluationInput(...)` in `src/main/services/evaluate-alerts.ts`

### evaluateAlerts orchestration (unchanged, reused)

- **Type:** service function
- **Shape:** `evaluateAlerts({ db, now?, managementWindowDte?, logger? }) => EvaluateAlertsResult` where result is `{ createdCount, updatedCount, resolvedCount, skippedRuleCount }`. Job name constant `ALERT_EVAL_JOB_NAME = 'alert-evaluation'`.
- **Source:** `plans/us-52/plan.md`, `plans/us-52/data-model.md`
- **Implementation:** `src/main/services/evaluate-alerts.ts`

### upsertOpenAlert / resolveAlertsNotIn (persistence primitives, unchanged, reused)

- **Type:** service persistence functions
- **Shape:** `upsertOpenAlert(db, match, positionId, now) => 'inserted' | 'updated'` — on an existing open `(positionId, ruleCode)` row it updates `summary`, `urgency`, `quick_action`, `last_evaluated_at`, `updated_at` in place while **preserving `triggered_at`**. `resolveAlertsNotIn(db, matchedKeys, now) => number` marks open rows absent from `matchedKeys` as `resolved` and sets `resolved_at`.
- **Source:** `plans/us-52/data-model.md`, `plans/us-52/plan.md`
- **Implementation:** `src/main/services/alerts.ts`

### ManagementQueueItem (US-51 read model, verification surface only)

- **Type:** dashboard read projection (no new contract in US-52)
- **Shape:** `{ alertId, positionId, ticker, phase, urgency, summary, quickAction, triggeredAt }`. Queue sorts by urgency tier (high → medium → low) then `triggered_at` ascending.
- **Source:** `plans/us-52/data-model.md`
- **Implementation:** `src/main/services/alerts.ts` (`listManagementQueue`, `mapQueueRow`); type in `src/main/schemas.ts`. US-52 depends on it only as an observation surface for e2e verification.

## Schema Changes

None recorded. US-52 introduces no new migration, table, or column. The `alerts` table it reads/writes was created by migration `migrations/009_create_alerts.sql` (US-50). Relevant existing columns exercised by the story: `id`, `position_id`, `rule_code` (= `EXPIRATION_IMMINENT`), `urgency` (= `high` while open), `summary` (updated in place as DTE ticks down), `quick_action` (= `Review position`), `status` (`open` → `resolved`), `triggered_at` (preserved on re-eval), `last_evaluated_at` (advanced each match), `resolved_at`.

## Acceptance Criteria

- **Alert fires at 5 DTE remaining** — a qualifying active CSP/CC at exactly 5 DTE produces a high-urgency open alert with summary `Expires in 5 days at $180.00 strike` and `Review position` quick action.
- **Alert remains open inside the final 5-day window** — re-evaluating the same position later (e.g. at 3 DTE) keeps the same open alert row (same `alertId`, preserved `triggered_at`) and refreshes the summary to the live DTE (`Expires in 3 days at $180.00 strike`).
- **Alert does not fire before the threshold** — a position at 6 DTE produces no `EXPIRATION_IMMINENT` alert. (Note: at 6 DTE the `MANAGEMENT_WINDOW` rule fires instead at medium urgency, since it covers `dte > 5 && dte <= managementWindowDte` with default window 21; the e2e asserts the EXPIRATION_IMMINENT summary is absent while the medium `6 DTE remaining — review for roll or close` row is present.)
- **Alert resolves after the leg is closed or expires** — closing/removing the active short option leg (or it leaving the evaluable set) causes the next evaluation to transition the open row to `status = 'resolved'` with a `resolved_at` timestamp.

## Decisions & Tradeoffs

- **Story is regression hardening, not net-new feature code.** The Red phase confirmed the tests passed immediately because the behavior already existed in production; no production edits were made to the four core/service files. The only new implementation code was e2e helper support.
- **Test-naming alignment for traceability.** Existing core/service tests were renamed to explicit US-52 story language (5-DTE boundary, in-window summary refresh, 6-DTE non-match, precedence inside 5 DTE, calendar-day DTE stability) without behavior changes.
- **E2E helper consolidation (DRY).** `runAlertEvaluation`, `cspAtDte`, queue/DB read helpers, and `setActiveLegExpiration` were extracted into `e2e/alert-helpers.ts`; `e2e/management-queue.spec.ts` was refactored to reuse them, and the new US-52 spec consumes the same surface. No production API was broadened.
- **Summary formatting kept local.** `formatStrike` / `expirationImminentSummary` stay small and local to `src/main/core/alerts.ts`; not extracted to a generic formatting module.
- **Refactor phase note:** the `code-simplifier` agent was explicitly not used for Areas A/B; refactorings were manual (test naming, lifecycle coverage, e2e helper consolidation).
