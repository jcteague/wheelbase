# Extract: us-70

## Summary

Wires the Finnhub earnings calendar into the candidate screener so a candidate whose
earnings print lands on or before expiry is hard-excluded (default) or flagged and
demoted, and so a missing or unreadable earnings date surfaces as a visible caution
rather than a silent pass. Selling a CSP into earnings is selling a binary event, and
pre-earnings IV inflation is exactly what lifts such candidates up US-65's
yield-per-delta rank — so earnings has to be judged before score. The story is not a
pure add-on: it widens the shared `finnhub-earnings.ts` module that US-56 depends on
(caller-supplied lookahead, four-state result), replaces that module's process-local
success cache with a new persisted `earnings_date` table, and updates US-56's consumer
to read through the new store.

## Architecture Decisions

### ADR: Reuse the Finnhub feed rather than introduce a screener-specific source

- **Decision:** US-70 consumes `src/main/integrations/finnhub-earnings.ts`, the
  auxiliary module shipped with US-56, widening it in place. No second provider, and
  earnings stays off `MarketDataProvider`.
- **Why:** The vendor decision was already made — Massive gates earnings behind a paid
  Benzinga add-on and Alpaca does not serve it. Two consumers of one calendar with two
  different fetchers would drift on cache, quota, and date semantics. The adapter rules
  forbid adding a capability to `MarketDataProvider` that the primary vendor lacks; the
  Barchart IVR scraper set the same precedent.
- **Alternatives considered:** A paid Benzinga/Massive add-on (rejected: cost, and it
  does not remove the need for the outage path); a new `EarningsProvider` interface
  (rejected: one vendor, two call sites — a speculative abstraction).
- **Source:** `plans/us-70/research.md`

### ADR: Persist earnings dates in SQLite; keep only failure backoff in memory

- **Decision:** Add an `earnings_date` table (one row per ticker) and a
  `src/main/services/earnings-dates.ts` read-through service. The DB becomes the cache:
  the integration module loses its 12-hour success `Map` and keeps only a short
  in-memory **failure** backoff (5 min).
- **Why:** (1) Future work needs earnings outside the running process — the watchlist
  already ships an unimplemented `post_earnings_only` entry condition whose premise is
  "has this ticker already reported?", unanswerable from a cache that dies on restart.
  (2) For a desktop app, restart is the common case, so the process-local `Map`'s
  effective hit rate is far below what its TTL suggests and every cold start re-issues
  one Finnhub call per watchlist ticker against a 60/min ceiling. (3) An earnings date is
  a durable fact about a scheduled event, not a decaying quote — the refresh trigger is a
  calendar event rather than a clock TTL.
- **Alternatives considered:** Keeping the in-memory cache alone (rejected: cannot serve
  `post_earnings_only`); a full per-event history table keyed `(ticker, event_date)` like
  `ivr_snapshot` (rejected: it cannot express "we checked and there is nothing scheduled"
  — an absent row and a genuinely empty calendar become indistinguishable, and this story
  turns on exactly that difference); caching in both places (rejected: two TTLs over one
  fact).
- **Contrast with `ivr_snapshot`:** that table is a time series with a composite
  `(underlying, observed_at)` key because IVR's history *is* the product. Earnings is a
  point-in-time lookup where a stale value is simply wrong, so it stores one current row
  per ticker and overwrites. Both feeds persist; they persist differently because the
  data has different semantics.
- **Failures are never persisted.** A 429 or auth error writes no row — it is not
  knowledge about the ticker.
- **Source:** `plans/us-70/research.md`, `plans/us-70/data-model.md` §2

### ADR: Make the calendar lookahead a caller-supplied parameter

- **Decision:** Replace the module-level `EARNINGS_LOOKAHEAD_DAYS = 30` constant with a
  `lookaheadDays` option. US-56 keeps its 30-day horizon; the screener passes
  `criteria.dteMax + LOOKAHEAD_BUFFER_DAYS`.
- **Why:** The constant was sized for US-56's ~7-day alert proximity rule. The
  screener's DTE window runs to 45, so a print at day 31–45 returned no event and
  rendered as "unknown" — precisely the silent pass this story exists to prevent. The
  story's own Background (today 2026-07-15, expiry 2026-08-21 at 37 DTE) falls in that
  dead zone.
- **Alternatives considered:** Raising the constant globally to 60 (rejected: silently
  widens US-56's request for no benefit and hides the coupling); a second fetch function
  with its own window (rejected: duplicate cache, duplicate quota).
- **Source:** `plans/us-70/research.md`

### ADR: Model the earnings lookup as a four-state union, not a nullable date

- **Decision:** The feed returns a per-ticker `EarningsLookup`
  (`found` / `none` / `unavailable`), and the engine emits a per-candidate
  `CandidateEarnings` (`clear` / `flagged` / `unknown` / `unavailable`).
  `ScoredCandidate.earningsFlagged: boolean` is replaced by
  `ScoredCandidate.earnings: CandidateEarnings`.
- **Why:** `fetchNextEarningsDates` returned `Record<string, string>` and omitted the
  ticker for *both* a null date and a caught error, collapsing the two states the story
  must render differently. A boolean flag cannot carry the third and fourth states at
  all. The four states map one-to-one onto the ACs.
- **Invariant:** `fetchNextEarnings` returns an entry for **every** requested ticker. A
  missing key is never a valid outcome — that ambiguity is the defect this story fixes.
- **Alternatives considered:** A parallel `unavailableTickers: Set<string>` beside the
  record (rejected: two sources of truth for one fact); keeping the boolean and passing
  status separately through the service (rejected: the badge and the sort both need the
  status on the row).
- **Source:** `plans/us-70/research.md`, `plans/us-70/data-model.md` §1, §3

### ADR: Three-tier ranking — clear, then unknown/unavailable, then in-window

- **Decision:** Rank by earnings tier first (0 clear, 1 unknown/unavailable, 2
  flagged-in-window), then by `yieldPerDelta` within a tier. Demoted rows render `—`
  instead of a rank number.
- **Why:** This is what the approved US-66 mockup shows in its `earnings` state: NVDA at
  score 0.69 with an unknown date sits *below* MSFT at 0.50, and both demoted rows carry
  `rank: null`. The reasoning holds independently — pre-earnings IV inflation is exactly
  what pushes these to the top of a yield-per-delta sort, so score must not rescue a
  tier. Demoting `unavailable` is harmless during a full outage because every row lands
  in the same tier and relative order is unchanged.
- **Alternatives considered:** Demoting only flagged candidates and ranking unknown
  normally (rejected: contradicts the mockup, and an unknown date is precisely the case
  where an elevated premium might be unexplained earnings IV); a score penalty
  multiplier (rejected: unexplainable to the trader, and a large enough score still jumps
  the tier).
- **Source:** `plans/us-70/research.md`, `plans/us-70/data-model.md` §5

### ADR: Unknown and unavailable never exclude, in either handling mode

- **Decision:** The `earnings_in_window` hard filter fires only on a `found` date that
  lands in the holding window. `unknown` and `unavailable` produce a caution and a
  tier-1 demotion, never an exclusion — including in `exclude` mode.
- **Why:** Excluding on unknown means one free-tier coverage gap, an exhausted quota, or
  an expired API key silently empties the results table with no indication that the
  screener is broken rather than the market. The existing `iv_rank_floor` filter already
  encodes the same principle in its `applies` guard ("an unknown IV rank is a gap in the
  data, not a low reading, so it passes").
- **Alternatives considered:** Excluding on unknown in `exclude` mode as the "safe"
  reading (rejected: it fails closed on the vendor, not on the risk, and the failure is
  invisible).
- **Source:** `plans/us-70/research.md`

### ADR: Cap earnings fetch concurrency at the service boundary

- **Decision:** Route the per-ticker fan-out through `mapWithConcurrency`
  (`src/main/concurrency.ts`) at the same limit the screener uses for quotes. **The
  per-ticker `try/catch` stays inside the mapped callback.**
- **Why:** The feed fanned out with a bare `Promise.all` over every ticker against a
  60 calls/minute free tier, with no cache to absorb a cold run. The screener's chain and
  quote reads already cap for exactly this 429 hazard.
- **Capping is not failure isolation.** `mapWithConcurrency` joins its workers with
  `Promise.all`, so a throw from `fn` rejects the whole batch — it is *less* forgiving
  than the bare `Promise.all` it replaces, whose callbacks each swallowed their own error.
  The helper's implicit contract is "`fn` must not throw". The `catch` is the only thing
  isolating a single 429, and it also owns the negative-cache write and the classified
  `failureCode` log (`auth_failed` / `rate_limited` / `network_error`).
- **Alternatives considered:** `Promise.allSettled` in place of the `try/catch`
  (rejected: it loses the per-ticker recovery behaviour — backoff write and classified
  log — and inside `mapWithConcurrency` there is no caller-visible join to swap);
  hardening `mapWithConcurrency` itself to `allSettled` (rejected: shared infrastructure,
  and making it swallow errors would hide genuine bugs in callers with no `catch`).
- **Source:** `plans/us-70/research.md`

### ADR (as-built): The engine owns `EarningsLookup`; the feed re-exports it

- **Decision:** `EarningsLookup` and `CandidateEarnings` are declared in
  `src/main/core/screener.ts`. `src/main/integrations/finnhub-earnings.ts` imports the
  type and re-exports it so callers of the feed can still name its return shape.
- **Why:** `data-model.md` §1 placed `EarningsLookup` in the integration module, but
  `plan.md` and `quickstart.md` both require that `src/main/core/screener.ts` import
  nothing from `integrations/`, `db/`, or `logger`. Those two constraints are mutually
  exclusive with a single definition, and the architecture rule wins. Precedent already
  existed: `IvRank` is declared in `core/screener.ts` and `services/ivr-snapshots.ts`
  conforms to it — the engine declares what it needs and outer layers conform.
- **Source:** as-built; supersedes `plans/us-70/data-model.md` §1

### ADR (as-built): A verdict that cannot answer "when is the next print" is never served

- **Decision:** A `found` date that has already passed, and a stored `NULL` whose
  `checked_through` is shallower than the caller's horizon, are both rejected as
  non-answers and fall through to `unavailable`. The past-date test is one shared
  predicate applied to the fetched value and the stored row alike.
- **Why:** The engine deliberately reads a past date as "history, not gap risk" and
  scores it `clear`, which would hand the ticker a rank number, no badge, and — in
  exclude mode — no exclusion, while its real next print (a quarter later) may land
  inside the expiry. The feed emits past dates as an ordinary outcome: its window opens
  at `now − EARNINGS_LOOKBACK_DAYS` and event selection falls back to the latest past
  date, so for the week after every print this is the normal reply. A shallow `NULL`
  served as `none` would assert "calendar read, no event" over a window it never
  examined, collapsing the outage-vs-empty distinction AC-10 requires.
- **Note:** Being merely time-stale does *not* disqualify a row — a future date read a
  week ago is the best knowledge available and is what carries the trader through an
  outage. The rejection is structural, not freshness-based, so this predicate is
  deliberately not the negation of the refresh rule.
- **Source:** as-built; not anticipated in the plan

### ADR (as-built): Refresh cadence is proximity-aware, not a flat backstop

- **Decision:** A ticker is re-fetched when no row exists, when a `NULL` row is
  shallower than the caller's horizon, or when the row's answer has stood longer than
  its refresh interval. That interval is 12 hours when the stored date has already
  passed or falls within 14 days, and 7 days otherwise.
- **Why:** Two failure modes the plan's flat rule missed. (1) The plan's "re-fetch when
  the stored date is earlier than today" trigger had no time floor, and with the feed's
  success cache removed a just-passed print would re-fetch on *every* 60-second alert
  tick — thousands of requests per ticker against a 60/min tier. (2) A flat 7-day
  backstop regressed US-56, whose rule fires on a 10-day threshold: a vendor revision
  inside ~2 weeks can move the answer across it, and the 12-hour interval restores the
  cadence US-56 had before the store replaced its in-memory TTL.
- **Source:** as-built; supersedes the flat four-trigger rule in
  `plans/us-70/data-model.md` §2

## Contracts

### `screener:results` (amended)

- **Type:** IPC handler (existing channel, changed payload)
- **Shape:**

```typescript
type IpcCandidateEarnings =
  | { status: 'clear' }
  | { status: 'flagged'; date: string; daysBeforeExpiry: number }
  | { status: 'unknown' }
  | { status: 'unavailable' }

type IpcScoredCandidate = {
  // …all US-65 fields unchanged…
  earnings: IpcCandidateEarnings // REPLACES `earningsFlagged: boolean`
}
```

- **Breaking change.** `earningsFlagged` is removed, not deprecated alongside the new
  field — it had exactly one reader, which never rendered it.
- **Ordering guarantee.** `ranked` order is authoritative and the renderer must not
  re-sort: earnings tier ascending, then `yieldPerDelta` descending within a tier, then
  `ticker` ascending. Rank numbers stay positional but only `clear` candidates display
  one; demoted rows render `—`.
- **Error codes.** No story-specific validation errors. Every expected failure is
  modelled inside the success payload — an earnings-feed outage surfaces as
  `earnings: { status: 'unavailable' }` per candidate, never as an envelope error and
  never as `status: 'provider_unavailable'` (which stays reserved for a Massive chain
  outage).
- **Source:** `plans/us-70/contracts/screener-results.md`
- **Implementation:** `src/main/ipc/screener.ts` (unchanged — the handler stays a thin
  `handleIpcCall` over one service call and never names a candidate field);
  `src/main/services/screener.ts`; `src/preload/index.d.ts`;
  `src/renderer/src/api/screener.ts`

## Schema Changes

### `earnings_date`

- **Change:** new table
- **Columns / fields:**
  - `ticker TEXT PRIMARY KEY`
  - `next_earnings TEXT` — `YYYY-MM-DD`; **NULL means "checked, nothing scheduled
    through `checked_through`"**, which is positive knowledge, not absence
  - `checked_through TEXT NOT NULL` — `YYYY-MM-DD`, the `to` bound of the request that
    produced this row
  - `checked_at TEXT NOT NULL` — ISO timestamp of that request
  - `source TEXT NOT NULL DEFAULT 'finnhub'`
- **One row per ticker**, overwritten on each successful fetch via
  `INSERT … ON CONFLICT (ticker) DO UPDATE`. No history.
- **`unavailable` is never a persisted state** — it is produced at read time when a
  fetch was needed and failed.
- **`checked_through` is what lets one row serve two horizons.** US-56 asks about 30
  days and the screener about ~90; a stored `NULL` from a 30-day request does not answer
  the 90-day question. Recording the `to` bound lets a shallow row be reused when it
  carries a date and re-fetched only when its `NULL` is too shallow for the caller. This
  replaced a composite `${ticker}:${lookaheadDays}` cache key, which would have split
  the two consumers into separate slots and doubled request volume.
- **Source:** `plans/us-70/data-model.md` §2
- **Migration file:** `migrations/013_create_earnings_date.sql`

## Acceptance Criteria

Background: the DTE window is 30–45, and today is 2026-07-15.

- **Exclude a candidate with earnings before expiration (default).** AAPL earnings
  2026-07-31, put expires 2026-08-21 (37 DTE), handling "Exclude" → excluded with reason
  `earnings 2026-07-31 falls on or before expiry`.
- **Flag a candidate with earnings before expiration when flag mode is on.** Same data,
  handling "Flag only" → shown with a warning naming the date and the days before expiry.
- **Ranking demotes by earnings certainty, then score.** KO (clear, 0.71), MSFT (clear,
  0.50), NVDA (unknown, 0.69), AAPL (earnings before expiry, 0.53) → order is KO, MSFT,
  NVDA, AAPL; only KO and MSFT carry a rank number, NVDA and AAPL show `—`.
- **Earnings on the expiration date is in the window.** Earnings 2026-08-21, expiry
  2026-08-21, handling "Exclude" → excluded (inclusive boundary).
- **No warning when earnings fall after expiration.** Earnings 2026-09-05, expiry
  2026-08-21 → no earnings warning.
- **Earnings beyond the alert horizon are still found.** With the window's furthest
  expiry 45 days out, the calendar is queried through at least that far, and a date 37
  days out is returned rather than reported unknown.
- **Unknown earnings date surfaces a caution, not a silent pass.** No date for XYZ → the
  candidate shows "Earnings date unknown" and is not silently treated as having no
  earnings.
- **Unknown earnings never hard-excludes, even in exclude mode.** XYZ is still scored and
  ranked with the caution, is not excluded, and sorts below every candidate with a known
  clear date.
- **Earnings-calendar outage does not suppress other results.** Candidates are still
  scored and ranked, each showing an "Earnings date unavailable" caution, and none is
  excluded for earnings.
- **Outage is distinguishable from a genuinely empty calendar.** XYZ empty and ABC failed
  in one run → XYZ reads "Earnings date unknown", ABC reads "Earnings date unavailable".

## Decisions & Tradeoffs

- **`LOOKAHEAD_BUFFER_DAYS = 45`, not a small buffer.** The plan specified
  `criteria.dteMax + LOOKAHEAD_BUFFER_DAYS` without fixing the constant, describing it as
  "a small buffer". Deciding *whether* earnings land in the window only needs coverage
  through expiry; the buffer exists for the other half of the judgement — telling `clear`
  ("we found the next print and it is after expiry") from `unknown` ("we did not look far
  enough to say"). Earnings are quarterly, so a buffer that merely clears `dteMax` would
  report `unknown` for most genuinely-clear candidates and bury the real cautions in
  noise. Sized to a full earnings cycle instead: with the default 45-day `dteMax` the
  calendar is read ~90 days out. Widening costs nothing per run — still one request per
  ticker — and a deeper `checked_through` row also satisfies US-56's shallower question.
- **Earnings status varies *within* a ticker.** `data-model.md` §5 asserted that
  `screenTicker`'s intra-ticker best-strike pick needed no change because "every strike
  for one ticker shares that ticker's earnings status". That is false: a chain is pulled
  across the whole DTE window, so it spans multiple expirations, and `CandidateEarnings`
  is derived per strike against `strike.expiration`. A print falling between two
  expiries leaves the earlier strike `clear` and the later one `flagged` — and the
  flagged one carries the richer premium precisely because pre-earnings IV inflates it.
  The survivor sort therefore leads with the earnings tier as well, so a ticker surfaces
  its clean expiry rather than being judged on its riskiest one.
- **Gold, not red, for the flagged badge.** An earnings-window candidate is a judgement
  call the trader may take on purpose, not an error.
- **`unknown` and `unavailable` share ranking tier 1** — the trader's next move is the
  same for both (go look it up). Only the badge copy differs.
- **`daysBeforeExpiry` travels on the payload** so the renderer never redoes date math
  and cannot form a second opinion on gap risk.
- **`clearEarningsCache` renamed `resetEarningsFeedState`** — it now clears only the
  failure backoff and the warn-once latch, not a success cache.
- **A write failure never costs the read.** Persisting is a side benefit, not the point of
  the call, so an upsert failure is logged and swallowed rather than degrading a fully
  successful fetch to "no earnings for anyone" at the caller.
- **Offline e2e seam.** `src/main/integrations/fake-earnings.ts` replaces the Finnhub HTTP
  call when `WHEELBASE_MOCK_EARNINGS` is set, following the `fake-ivr` /
  `fake-market-data` precedent. It honours `lookaheadDays` the way the live calendar does
  — a fixture past the requested `to` bound reads as `none` — which is what makes the
  lookahead-widening e2e test a real regression test rather than a tautology.
- **`src/**/*test-utils.ts` added to `coverage.exclude`** in `vitest.config.ts`: those
  modules import `vi` and are test infrastructure, generalising the existing
  `test-setup.ts` exclusion.

## Open Questions

- **Free-tier forward coverage is unverified.** Finnhub documents no maximum `from`/`to`
  range but does not contractually guarantee free-tier coverage at the ~90 days the
  screener now requests. `quickstart.md`'s live smoke check was never run — it needs a
  real API key. A wrong answer degrades to the `unknown` caution the story specifies,
  which is the correct failure mode, but it determines whether the feature is useful in
  practice.
- **BMO/AMC timing and confirmed-vs-estimated flags** are out of scope. Finnhub's rows
  carry an `hour` field (`bmo`/`amc`/`dmh`) that the module strips, and the free tier
  exposes no confirmation flag. Judging an AMC print on expiration Friday as harmless is
  a real refinement but needs a verified live payload behind it.
- **A shallow-horizon caller can starve a deep one.** The 30-day alert path re-fetches a
  just-passed date every 12 hours and rewrites `checked_at`, re-arming the floor before
  the ~90-day screener path can ask with its wider window. A ticker can therefore read
  "Earnings date unavailable" for up to a week after each print. Direction is
  over-caution only — never a false `clear` — so it was left as a follow-up.
- **A shallow fetch can clobber a still-future stored date.** A found-past reply
  overwrites a future `next_earnings` while the same call answers from the pre-fetch row
  snapshot, so two consecutive calls over identical data can disagree. Same direction of
  safety; also a follow-up.
