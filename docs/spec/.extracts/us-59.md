# Extract: us-59

## Summary

US-59 adds a `Dismiss` action to open management-queue alerts. Dismissing an
alert transitions it to `status = 'dismissed'` with a `dismissed_at`
timestamp, removes it from the open queue, and makes the evaluation job's
upsert logic dismissal-aware so a still-true condition doesn't silently
re-open it on the next tick. When the underlying condition genuinely clears,
the dismissed row is retired to `resolved`; if the condition later returns, a
brand-new open row is created with a fresh `triggered_at`, exactly like the
existing resolve→refire lifecycle. Delivered across 6 layers: schema, service
layer, evaluation-job wiring + IPC, preload/renderer API adapter, renderer
UI, and e2e tests — all complete.

## Architecture Decisions

### ADR: Model "condition cleared" as a dismissed→resolved transition, not a new status or column

- **Decision:** Reuse the existing `open → resolved` semantics for dismissed
  rows. On every evaluation run, after computing `keepOpenKeys` (matched ∪
  skipped, the same set `resolveAlertsNotIn` already uses), a new
  `clearStaleDismissals` step finds every row with `status = 'dismissed'`
  whose `(position_id, rule_code)` key is absent from `keepOpenKeys` and
  transitions it to `status = 'resolved'`, `resolved_at = now`. The
  `dismissed_at` timestamp is never cleared, so the row keeps both
  `dismissed_at` and `resolved_at` — a permanent audit record. Once no `open`
  or `dismissed` row exists for a key, `upsertOpenAlert`'s existing lookup
  falls through to its normal insert path and creates a brand-new row with a
  fresh `triggered_at` the next time the rule matches.
- **Why:** Keeps one state machine (`open ⇄ resolved`, plus the one-way
  branch into `dismissed`) instead of inventing a second parallel "cleared"
  concept. Reuses `resolveAlertsNotIn`'s exact `keepOpenKeys` set, so
  "condition cleared" means precisely the same thing for a dismissed alert as
  it already means for an open one — a rule skipped for missing data is never
  treated as cleared (preserves the `alert-evaluation-failure-isolation`
  guarantee).
- **Alternatives considered:**
  - New `dismissed_condition_cleared_at` column, row stays `dismissed`
    forever — rejected; two parallel timestamp mechanisms for the same
    question.
  - In-place mutation of the dismissed row (never insert a new one on
    re-fire) — rejected; the AC explicitly wants a fresh `triggered_at` on
    re-trigger.
- **Source:** `plans/us-59/research.md`

### ADR: `upsertOpenAlert` gains a dismissal-aware guard; `UpsertOutcome` gets a third value

- **Decision:** `upsertOpenAlert` first checks for a row with
  `status = 'dismissed'` at the same `(position_id, rule_code)` key. If
  found, it does not insert or update — it returns a new `'suppressed'`
  outcome and logs `alert_dismissal_suppressed_reopen` at DEBUG. Otherwise
  behavior is unchanged. A partial unique index `idx_alerts_dismissed_unique`
  on `(position_id, rule_code) WHERE status = 'dismissed'` (mirroring
  `idx_alerts_open_unique`) guarantees at most one "blocking" dismissed row
  per key, so the lookup is a simple existence check.
- **Why:** This is the one lookup that must change to stop the "condition
  still true → silently re-opens" carryover bug from US-50; every other
  read/write primitive already ignores non-open rows correctly.
- **Alternatives considered:** Query "most recent row regardless of status"
  and branch on its status — rejected; more expensive and duplicates
  information the partial unique index already guarantees.
- **Source:** `plans/us-59/research.md`

### ADR: New `AlertError` class mirrors `PendingAssignmentError`, not `ValidationError`

- **Decision:** `dismissAlert(db, alertId, now)` throws a dedicated
  `AlertError` (`code: 'NOT_FOUND' | 'NOT_OPEN'`) defined in
  `src/main/services/alerts.ts`, following the exact shape of
  `PendingAssignmentError` in `pending-assignments.ts`. `handleIpcCall`
  (`src/main/ipc/utils.ts`) gets one new `instanceof AlertError` branch,
  mapped identically to the `PendingAssignmentError` branch.
- **Why:** The story's technical note explicitly calls for reusing the
  existing "dismissed but retained in SQLite" pattern established by pending
  assignments. `core/lifecycle.ts`'s `ValidationError` is a different pattern
  (field-level input validation) — not the right fit for a service-level
  "this row isn't in the state you think it's in" check.
- **Alternatives considered:** Reuse
  `ValidationError('__status__', 'invalid_status', ...)` — rejected; would
  import a `core/` class into a service for a non-validation case and loses
  the `NOT_FOUND` vs `NOT_OPEN` code distinction.
- **Source:** `plans/us-59/research.md`

### ADR: No dedicated "Alert History" read path or component in this story

- **Decision:** Ship the persistence half of the audit trail (the
  `dismissed_at` column and the retained row) but do not build the mockup's
  separate "Alert History" panel/read path. Frontend work is scoped to what
  the Gherkin ACs test: the dismiss action, its inline confirm step, and the
  alert's removal from the open queue.
- **Why:** None of the four Gherkin scenarios assert anything about a
  history *view* — they assert DB state and open-queue membership. Building
  a new read path + IPC channel + component for a non-tested display surface
  would exceed this story's estimate and the "no features beyond what was
  asked" standard.
- **Alternatives considered:** Build the full 3-panel mockup including
  history — rejected for this pass; flagged as a natural follow-up story.
- **Source:** `plans/us-59/research.md`

## Contracts

### `alerts:dismiss`

- **Type:** IPC handler
- **Shape:**

```typescript
// Request
z.object({
  alertId: z.string().min(1)
})

// Response (success)
{
  ok: true
  alert: {
    id: string
    positionId: string
    ruleCode: string
    urgency: 'high' | 'medium' | 'low'
    summary: string
    quickAction: string
    status: 'dismissed'
    triggeredAt: string
    lastEvaluatedAt: string
    resolvedAt: string | null
    dismissedAt: string
    createdAt: string
    updatedAt: string
  }
}
```

| field      | code             | message                             |
| ---------- | ---------------- | ------------------------------------ |
| `__root__` | `NOT_FOUND`      | `Alert {alertId} not found`         |
| `__root__` | `NOT_OPEN`       | `Only open alerts can be dismissed` |
| `__root__` | `internal_error` | `An unexpected error occurred`      |

`NOT_OPEN` covers dismissing an alert that is currently `resolved` or already
`dismissed` — the AC does not distinguish between those two prior states.

- **Source:** `plans/us-59/contracts/alerts-dismiss.md`
- **Implementation:** `src/main/ipc/alerts.ts` (`registerAlertsHandlers`), `src/main/services/alerts.ts` (`dismissAlert`, `AlertError`)

## Schema Changes

### Migration `011_add_alerts_dismissal.sql`

- **Change:** new column + new partial unique index on the existing `alerts` table
- **Columns / fields:**
  - `alerts.dismissed_at TEXT` (nullable) — set once, when `status`
    transitions `open → dismissed`; never cleared, even if the row later
    moves to `resolved`.
  - `CREATE UNIQUE INDEX idx_alerts_dismissed_unique ON alerts (position_id, rule_code) WHERE status = 'dismissed'` —
    mirrors `idx_alerts_open_unique`; at most one "blocking" dismissed row
    per `(position_id, rule_code)` at a time.
- **Source:** `plans/us-59/data-model.md`
- **Migration file:** `migrations/011_add_alerts_dismissal.sql`

### State transitions (extends `docs/spec/domain/alerts.md`)

```
(none) ──match──▶ open ──match again──▶ open (updated in place)
  open ──dismiss (user action)──▶ dismissed
  dismissed ──condition clears (rule evaluated, no longer matches)──▶ resolved
  open ──condition clears──▶ resolved                        (unchanged, US-50)
  resolved ──match again──▶ (none, new row) open              (unchanged, US-50)
```

- `open → dismissed`: only triggered by the trader (via `alerts:dismiss`).
  Sets `status = 'dismissed'`, `dismissed_at = now`, `updated_at = now`.
  `triggered_at` untouched.
- `dismissed → resolved`: triggered automatically by the evaluation job
  (`clearStaleDismissals`) when the rule was genuinely evaluated and did not
  match. Sets `status = 'resolved'`, `resolved_at = now`, `updated_at = now`.
  `dismissed_at` preserved.
- `dismissed → dismissed` (blocked re-open): while a dismissed row exists for
  a key, `upsertOpenAlert` returns `'suppressed'` and leaves the row
  untouched.
- Illegal: dismissing a non-`open` row is rejected with `AlertError`
  (`NOT_OPEN` or `NOT_FOUND`).

## Acceptance Criteria

```gherkin
Background:
  Given AAPL has an open MANAGEMENT_WINDOW alert in the dashboard queue

Scenario: Trader dismisses an alert from the queue
  When the trader clicks "Dismiss" on the AAPL alert
  Then the alert status changes to dismissed
  And the alert stores a dismissed_at timestamp
  And the alert no longer appears in the open management queue

Scenario: Dismissed alert does not immediately reappear while the condition is unchanged
  Given the AAPL MANAGEMENT_WINDOW alert was dismissed today
  And AAPL still has 12 DTE remaining
  When the alert engine evaluates active positions again
  Then the dismissed alert remains hidden from the open queue
  And no new MANAGEMENT_WINDOW alert is created for AAPL

Scenario: Dismissed alert can reappear after the condition clears and later returns
  Given the AAPL MANAGEMENT_WINDOW alert was dismissed
  And AAPL is later rolled to 30 DTE
  And on a future cycle AAPL returns to 14 DTE
  When the alert engine evaluates active positions
  Then a new MANAGEMENT_WINDOW alert is created for AAPL
  And the new alert has a new triggered_at timestamp

Scenario: Dismissing an already resolved alert is rejected
  Given the AAPL alert has already been resolved
  When the trader attempts to dismiss it again
  Then the request is rejected with message "Only open alerts can be dismissed"
```

## Decisions & Tradeoffs

- **Renderer interaction is a two-panel confirm, not a modal.** Per the
  mockup (`mockups/us-59-dismiss-alert.mdx`), clicking `Dismiss` puts the
  row's `alertId` into `ManagementQueue`'s local `confirmingAlertId` state,
  which renders a second stacked panel (`DismissConfirmPanel`) below the
  queue list — not an inline row expansion or an overlay dialog.
- **Confirm-panel copy is genericized**, not AAPL/21-DTE-specific like the
  mockup, so it reads correctly for any rule code:
  `{ticker} will disappear from the open queue, but the dismissal will be
recorded with a timestamp. If the condition clears and later returns, a
fresh alert can appear.`
- **No new "dismissed" UI state is built.** Once the mutation succeeds,
  `listManagementQueue` (US-51's existing `status = 'open'` filter)
  naturally excludes the row, so the existing empty state takes over
  unchanged.
- **`throwMappedIpcErrors` promoted** from `api/positions.ts` into a shared
  `api/error.ts` during the Layer 4 refactor, since both `api/positions.ts`
  and the new `api/alerts.ts` needed to throw a mapped `ApiError` from an IPC
  error envelope.
- **Grid layout widened during Layer 5 refactor**: `ManagementQueueRow`'s
  action column changed from a fixed `grid-cols-[...]_160px` to `..._auto` so
  the new `Dismiss` button fits alongside the existing `quickAction` button
  without clipping.
- **Shared e2e arrange-helper extracted during Layer 6 refactor**:
  `seedAndResolveAlert(page, dbPath, fixture)` added to `e2e/alert-helpers.ts`,
  replacing duplicated seed→evaluate→close-leg→evaluate setup that existed
  in both the new `dismiss-alert.spec.ts` and the pre-existing
  `expiration-imminent-alert.spec.ts`.
