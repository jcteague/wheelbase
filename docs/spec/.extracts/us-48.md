# Extract: us-48

## Summary

Three small, independent correctness fixes surfaced by the post-merge code review on US-35: (1) `createPollingScheduler` now accepts a broker **getter** (`() => BrokerProvider`) instead of a broker instance, so credential changes propagate without app restart; (2) `stop()`'s 5-second drain-fallback timeout is now properly cancelled in `.finally` when the drain wins, preventing a timer leak; (3) `handleMassiveTestConnection`, `handleTestConnection`, and `handleStoredConnectionTest` in `SettingsPage.tsx` now wrap `mutateAsync` in try/catch and surface `getApiErrorMessage(error)` on rejection rather than silently swallowing it. No DB migrations, no IPC surface changes beyond these fixes, no schema changes.

## Architecture Decisions

None recorded. These are correctness fixes, not architectural changes. The broker getter pattern was already used by `index.ts` (`registerBrokerHandlers(() => brokerFactory.create())`); this fix aligns the scheduler with that established pattern.

## Contracts

- **Type:** TypeScript function signature
- **Shape:**
  ```typescript
  // Before:
  export function createPollingScheduler(brokerProvider: BrokerProvider, clock?: Clock): PollingScheduler
  // After:
  export function createPollingScheduler(getBroker: () => BrokerProvider, clock?: Clock): PollingScheduler
  ```

  The getter is called fresh on every tick inside `reschedule()` and `startAfterClose()`. The broker reference is never cached beyond the single tick.

## Acceptance Criteria

- **Scheduler getter injection:** Assignment polling resumes after credentials are saved at runtime — `reschedule()` and `startAfterClose()` resolve the broker fresh via the getter on every tick.
- **Scheduler getter injection:** Switching the active broker environment refreshes the scheduler's broker source without app restart.
- **stop() timeout cleanup:** `stop()` does not leak the drain-fallback timeout when the in-flight drain completes before the 5-second fallback fires.
- **stop() timeout cleanup:** `stop()` still falls back to the 5-second timeout when the in-flight drain stalls.
- **Settings rejection handling:** Clicking **Test connection** under Market Data → Massive when the call fails shows an error-tone message; it was previously swallowed silently.
- **Settings rejection handling:** Clicking **Test connection** (Alpaca, unsaved credentials) when the call fails shows an error-tone message inside the card.
- **Settings rejection handling:** Clicking **Test connection** (Alpaca, stored credentials) when the call fails shows an error-tone message inside the card.

## Decisions & Tradeoffs

- **Getter not instance** — the one API-breaking change is the `createPollingScheduler` signature. The only production consumer is `scheduler-instance.ts`; all test fixtures needed a one-line wrap (`() => broker`). Acceptable trade-off for correctness.
- **No `fallbackBroker` change** — `getSafeBroker` still returns `fallbackBroker` before `brokerFactory.configure()` runs. This is intentional bootstrap-window safety; the getter pattern does not break it.
- **No helper extracted for Settings handlers** — three try/catch blocks with nearly identical shape were left inline. The story is a bug fix; a `applyTestResult` extraction was deferred as not measurably simplifying at this scope.
- **`getApiErrorMessage` handles unknown shapes** — the catch block does not assume `ApiError`; `getApiErrorMessage(error)` already falls through to `'Unable to complete the request'` for non-`ApiError` rejects.
