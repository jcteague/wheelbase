# Extract: us-51

## Summary

US-51 surfaces US-50's persisted open alerts as a prioritized "management queue" at the top of the dashboard. It adds a new enriched, sorted read path (`listManagementQueue`) that joins `alerts` to `positions`, exposes it through a new `alerts:list` IPC channel, a preload bridge, a renderer adapter, and a TanStack Query hook (`useManagementQueue`), and renders the result as a `SectionCard`-wrapped queue above the positions grid. Each row shows ticker, phase badge, trigger summary, an urgency pill, and a "Review position" action that navigates to the position detail page; an empty state shows when no alerts are open. No new migration or engine work is required — the entire alert backend (table, engine, scheduled evaluation) shipped in US-50. (`plans/us-51/plan.md`, `plans/us-51/research.md`)

## Architecture Decisions

### ADR: New enriched + sorted read path `listManagementQueue(db)` rather than reusing `listOpenAlerts`

- **Decision:** Add a new service function `listManagementQueue(db)` in `src/main/services/alerts.ts` that JOINs open `alerts` to `positions` to attach `ticker` and `phase`, returning rows already sorted by urgency tier then time. Leave `listOpenAlerts` untouched (still used by US-50 evaluation tests).
- **Why:** The queue UI needs `ticker` and the current `phase` badge, neither of which is on the `alerts` row. `listOpenAlerts` also sorts by `rowid`, which does not satisfy the "ordered by urgency then time" acceptance criterion. A dedicated function keeps the existing primitive's contract stable.
- **Alternatives considered:** (a) Sort/enrich in the renderer after calling a raw list — rejected: pushes business logic (urgency ranking, JOIN) into the UI and duplicates it per consumer. (b) Extend `listOpenAlerts` to JOIN and sort — rejected: changes a primitive relied on by US-50 tests and conflates the "raw open alerts" concept with the "display queue" concept.
- **Source:** `plans/us-51/research.md`

### ADR: Sort by urgency rank (high→medium→low) then `triggered_at` ascending, in SQL

- **Decision:** Order with `ORDER BY CASE urgency WHEN 'high' THEN 0 WHEN 'medium' THEN 1 WHEN 'low' THEN 2 ELSE 3 END, triggered_at ASC`.
- **Why:** The story requires "urgency then time". High urgency surfaces first. Within a tier, the alert that has needed attention longest (oldest `triggered_at`) surfaces first — the most actionable ordering for a start-of-day triage list. Doing it in SQL keeps the service a thin mapper and leverages the existing `idx_alerts_status_urgency` index for the status filter.
- **Alternatives considered:** Sorting in JS with a rank map (matches `list-positions.ts` style) — viable, but SQL keeps ordering co-located with the query and avoids a second pass. `triggered_at DESC` (newest first) — rejected: a brand-new low-urgency alert would jump ahead of a long-standing one in the same tier, which is the opposite of triage intent.
- **Source:** `plans/us-51/research.md`

### ADR: Dedicated `ManagementQueueItem` view-model type (not raw `AlertRecord`)

- **Decision:** Define a new `ManagementQueueItem` interface in `src/main/schemas.ts` with exactly the fields the UI needs: `alertId`, `positionId`, `ticker`, `phase`, `urgency`, `summary`, `quickAction`, `triggeredAt`. Mirror it in `src/preload/index.d.ts` and re-export the type from the renderer adapter `src/renderer/src/api/alerts.ts`.
- **Why:** `AlertRecord` carries audit fields (`lastEvaluatedAt`, `resolvedAt`, `createdAt`, `updatedAt`, `status`) that the queue does not use and lacks `ticker`/`phase` that it does. A purpose-built view-model keeps the contract honest and small. `alertId` is included to serve as a stable React `key` (one row per open alert per US-51 scope).
- **Alternatives considered:** Returning `AlertRecord & { ticker, phase }` — rejected: leaks unused audit fields across the IPC boundary and the type becomes ambiguous about what the queue depends on.
- **Source:** `plans/us-51/research.md`

### ADR: `alerts:list` IPC handler in a new `src/main/ipc/alerts.ts`, registered as `registerAlertsHandlers`

- **Decision:** Add `ipcMain.handle('alerts:list', …)` in a new `src/main/ipc/alerts.ts` exposing `registerAlertsHandlers({ db })`, wired into `src/main/index.ts` alongside the other `register*Handlers` calls. Handler body is `handleIpcCall('alerts_list_error', () => ({ items: listManagementQueue(db) }))`.
- **Why:** Matches the thin-handler architecture rule (Zod-or-nothing + single service call inside `handleIpcCall`). Read-only with no request payload, so no Zod schema is needed. Mirrors `assignments:list-pending` exactly.
- **Alternatives considered:** Folding the channel into `positions.ts` — rejected: alerts are their own domain; a dedicated handler file matches the one-domain-per-file convention.
- **Source:** `plans/us-51/research.md`

### ADR: Renderer fetches via `useManagementQueue` with a polling `refetchInterval`

- **Decision:** Add `src/renderer/src/api/alerts.ts` (`listManagementQueue()` adapter, returns `[]` on `!ok`) and `src/renderer/src/hooks/useManagementQueue.ts` (`useQuery` with `queryKey: ['alerts','queue']`, `refetchInterval: 30_000`).
- **Why:** The backend re-evaluates alerts on a 30–60s cadence; a matching renderer poll keeps the queue fresh without manual refresh, consistent with `usePendingAssignments` (`refetchInterval: 30_000`). Returning `[]` on error lets the queue degrade to its empty state rather than crash the dashboard.
- **Alternatives considered:** Push via an IPC event channel — rejected as out-of-scope for this slice; polling matches the existing read patterns and the evaluation cadence. Throwing `ApiError` like `usePositions` — the queue is a secondary surface, so silent empty-degrade is preferable to an error banner.
- **Source:** `plans/us-51/research.md`

### ADR: Reuse `PhaseBadge` (short variant) and `SectionCard`; new `UrgencyPill` for tiers

- **Decision:** Build the queue inside a `SectionCard` (header "Management Queue"), render each alert as a `ManagementQueueRow`, reuse `PhaseBadge variant="short"` for the phase, and add a small `UrgencyPill` component mapping `high|medium|low` → red/gold/blue `wb-*` tokens (labels HIGH/MED/LOW).
- **Why:** The story's Technical Notes mandate reusing `SectionCard` and `PhaseBadge` and the gold/red urgency accents. `PhaseBadge` short labels ("CSP Open"/"CC Open") match the mockup. A dedicated `UrgencyPill` isolates the tier→token mapping for reuse in future alert surfaces (US-59/60).
- **Alternatives considered:** Hand-rolling phase markup from the mockup's inline styles — rejected: violates the Tailwind-tokens-not-inline-styles rule and duplicates `PhaseBadge`.
- **Source:** `plans/us-51/research.md`

### ADR: Render the queue unconditionally above the positions grid (component owns loading/empty)

- **Decision:** Mount `<ManagementQueue />` in `PositionsListPage` immediately after `AssignmentNotificationBanner` and above the `Active` section. The component calls `useManagementQueue` itself and renders the empty state when there are zero open alerts.
- **Why:** AC requires the queue "above the positions grid" and an empty-state message when there are no alerts — both are satisfied by always mounting it. Self-fetching keeps `PositionsListPage` from growing another data dependency.
- **Alternatives considered:** Gating the queue behind `data.length > 0` (the positions-present block) — rejected: the empty-alerts state must show even when positions exist, and the queue is conceptually independent of the positions query.
- **Source:** `plans/us-51/research.md`

## Contracts

### alerts:list

- **Type:** IPC handler
- **Shape:**

```typescript
// Request: no payload. Channel invoked with no arguments.
// window.api.alerts.list()  ->  ipcRenderer.invoke('alerts:list')

// Response (success):
{
  ok: true
  items: ManagementQueueItem[] // sorted: high→medium→low, then triggered_at ASC; [] when no open alerts
}

interface ManagementQueueItem {
  alertId: string
  positionId: string
  ticker: string
  phase: WheelPhase // 'CSP_OPEN' | 'HOLDING_SHARES' | 'CC_OPEN' | ... (existing union)
  urgency: 'high' | 'medium' | 'low'
  summary: string
  quickAction: string
  triggeredAt: string // ISO timestamp
}

// Error envelope (only standard error applies):
// { ok: false, errors: [{ field: '__root__', code: 'internal_error', message: 'An unexpected error occurred' }] }
```

- **Source:** `plans/us-51/contracts/alerts-list.md`
- **Implementation:** `src/main/ipc/alerts.ts` (`registerAlertsHandlers`, channel `alerts:list`); service `src/main/services/alerts.ts` (`listManagementQueue`)

### window.api.alerts.list (preload bridge)

```typescript
alerts: {
  list: () => Promise<

```

- **Source:** `plans/us-51/contracts/alerts-list.md`, `plans/us-51/plan.md`

### listManagementQueue (renderer adapter)

- **Type:** other (renderer adapter function)
- **Shape:** `listManagementQueue(): Promise<ManagementQueueItem[]>` — reads `window.api.alerts.list()` and returns `result.ok ? result.items : []`.
- **Source:** `plans/us-51/contracts/alerts-list.md`, `plans/us-51/plan.md`
- **Implementation:** `src/renderer/src/api/alerts.ts`

## Schema Changes

None recorded. US-51 adds no schema migrations; it reads the existing `alerts` table (US-50, `migrations/009_create_alerts.sql`) joined to `positions` and projects the result into the `ManagementQueueItem` view-model. (`plans/us-51/data-model.md`)

## Acceptance Criteria

- Queue appears above the position cards ordered by urgency then time.
- Queue item shows the key fields traders need to act (ticker, phase badge, trigger summary, "Review position" button).
- Queue item opens the related position from the quick action.
- Empty state renders when there are no open alerts (message + no action buttons).

(`plans/us-51/plan.md`, "AC Audit" section)

## Decisions & Tradeoffs

- **View-model field selection:** `ManagementQueueItem` exposes only `alertId`, `positionId`, `ticker`, `phase`, `urgency`, `summary`, `quickAction`, `triggeredAt` — deliberately excluding `AlertRecord` audit fields (`lastEvaluatedAt`, `resolvedAt`, `createdAt`, `updatedAt`, `status`). `alertId` is included specifically to serve as a stable React key. (`plans/us-51/research.md`, `plans/us-51/data-model.md`)
- **Summary text displayed verbatim:** The alert `summary` (e.g. "Expires in 3 days at $180.00 strike") is generated and stored by the US-50 engine; US-51 displays it verbatim with no new summary generation. (`plans/us-51/research.md`)
- **One row per open alert:** No grouping by position in US-51 scope; an empty result set is valid and drives the empty state rather than an error. (`plans/us-51/data-model.md`)
- **Silent error degradation:** The renderer adapter returns `[]` on a non-ok envelope so the queue degrades to its empty state rather than showing an error banner — chosen because the queue is a secondary surface. (`plans/us-51/research.md`)
- **Inner JOIN behavior:** The JOIN drops any alert whose position is missing (should not happen given the FK, but keeps the result well-formed). (`plans/us-51/data-model.md`)
- **UrgencyPill token mapping:** `high → HIGH` (`text-wb-red`/`bg-wb-red-dim`), `medium → MED` (`text-wb-gold`/`bg-wb-gold-dim`), `low → LOW` (`text-wb-blue`/`bg-wb-blue-dim`); Tailwind `wb-*` tokens only, no inline color styles. (`plans/us-51/plan.md`)
- **Polling cadence:** `refetchInterval: 30_000` chosen to match the backend's 30–60s re-evaluation cadence and the existing `usePendingAssignments` pattern. (`plans/us-51/research.md`)
