# Extract: us-103

## Summary

"Add the running PMCC cost-basis ledger: a pure `calculatePmccLedger` over signed per-share
contributions, a service-layer writer (`appendPmccSnapshot`) that every PMCC leg event calls inside
its own transaction, a shared roll-chain helper extracted from the assignment service, and the
`Cost basis` drawer (six `StatGrid` cells) on the PMCC detail page plus the running total on the
PMCC list row. Done when every Linear scenario passes end to end against the two opening legs US-101
creates and against seeded expiration / subsequent-short / short-roll / LEAPS-roll events, the
five-row snapshot chain is auditable, and a classic wheel's detail page, list row and services are
unchanged." Linear story: OPT-9 / US-103 (the archived `docs/epics/09-stories/US-103-pmcc-cost-basis.md`
is a copy; Linear wins); estimated 5 points. Layout of record: `mockups/epic-09-pmcc-position-detail.mdx`
(`Cost basis` drawer, `healthy` / `rs-recorded` / `rl-recorded` presets). **No migration.** The
story adds the four reserved PMCC leg roles and the PMCC trigger-event vocabulary to the shared
enums, but writes none of the post-entry leg events in production — those belong to
US-104/105/111/115/119; e2e lands them through a new dev-only `_test:pmcc-record-leg-event` seam.
All 13 OPT-9 scenarios pass at e2e (`area-11-red-results.md`). (Source: `plans/us-103/plan.md`
Summary; `plans/us-103/research.md`; `plans/us-103/area-11-red-results.md`.)

## Architecture Decisions

### ADR: One pure `calculatePmccLedger` over signed contributions; the engine never sees legs

- **Decision:** Add to `src/main/core/costbasis.ts`:
  ```ts
  type PmccLedgerSide = 'LONG' | 'SHORT'
  interface PmccContribution { side: PmccLedgerSide; cashPerShare: string; contracts: number; fees: string }
  interface PmccLedgerInput { leapsContracts: number; longStrike: string | null; contributions: PmccContribution[] }
  interface PmccLedgerResult {
    basisPerShare: string; basisTotal: string
    leapsCostPerShare: string; leapsCostTotal: string
    shortCreditsPerShare: string; shortCreditsTotal: string
    effectiveShareCost: string | null; premiumRecoveredPercent: string | null
  }
  ```
  "`cashPerShare` is signed per share of contract: **positive = cash paid out, negative = cash
  received**. `fees` is dollars for the whole contribution. The fold is in dollars:
  `contributionTotal = cashPerShare × contracts × 100 + fees`; `leapsCostTotal = Σ LONG`;
  `shortCreditsTotal = −Σ SHORT` (so a net credit is positive); `basisTotal = leapsCostTotal −
  shortCreditsTotal`; `basisPerShare = basisTotal / (leapsContracts × 100)`; the two per-share side
  figures divide the same way. `effectiveShareCost = longStrike + basisPerShare` (null when no
  strike). `premiumRecoveredPercent = shortCreditsTotal / leapsCostTotal × 100`, **null when
  `leapsCostTotal ≤ 0`**. All strings 4 dp via the file's existing `money4`." `leapsContracts < 1`
  (or non-integer) throws `'leapsContracts must be a positive integer'` — callers validate. Only
  `decimal.js` imported; reuses the file's private `sharesFromContracts` / `money4`.
- **Why:** "The story's formula `basis = long_debits + fees − short_credits ± roll_nets` is exactly
  'sum the signed cash'. Signing by action at the boundary means one rule covers an opening debit,
  an opening credit, a buyback, a short roll (BUY to close + SELL to open → net debit $0.60) and a
  LEAPS roll (SELL to close + BUY to open → net credit $2.50) without a `kind` switch inside the
  engine, and US-105's 'no strike-delta term' is true by construction — strike never enters the
  fold." Folding in dollars and dividing once gives `2302.0000` / `23.0200` for the fee example and
  prorates US-115's partial coverage (1 short against 3 LEAPS) "the way `calculateCcOpenBasis`
  already prorates CC income across held shares". Side-splitting at the boundary keeps the engine
  free of leg roles (US-16 precedent: "the engine has no roll_chain_id grouping concept").
- **Alternatives considered:** (a) pass `LegRecord[]` into the engine — leaks `roll_chain_id` and
  role names into `core/`; (b) per-share-only arithmetic — breaks on unequal contracts and per-leg
  dollar fees; (c) a `kind` discriminator per contribution — "more surface for no extra rule";
  (d) extending `calculateRollBasis` with `legType: 'PMCC_SHORT' | 'PMCC_LEAPS'` — the wheel
  function is a prev-snapshot delta, the PMCC ledger is a replay over all fills.
- **Source:** `plans/us-103/research.md`, `plans/us-103/data-model.md` §1

### ADR: Display figures are recomputed from legs; snapshots are the audit chain

- **Decision:** `getPosition` and `listPositions` build the ledger from the position's **legs** on
  every read (`pmccLedger` on the detail result, `basisPerShare` / `basisTotal` on
  `PmccListSummary`). Snapshots are written for the audit chain (US-109's "cost basis after cycle
  N") and remain the source of the base-row `effectiveCostBasis`, "but the drawer and the row do not
  multiply `basis_per_share` back up."
- **Why:** The US-101 cold review replaced `basis_per_share × 100 × contracts` because "a rounded
  per-share basis drifts when multiplied back"; the same drift applies to "Total" (3 contracts with
  $0.01 fees per leg → `6900.0200`). "Recomputing from fills is also what makes the drawer honest
  after a direct SQL import or a consumer story that forgets a snapshot." Tests assert agreement:
  after every event the newest snapshot's `basis_per_share` equals the ledger's `basisPerShare`.
- **Alternatives considered:** Read the latest snapshot only — needs a new column for LEAPS cost to
  date and cannot show a correct `Total`. Store `basis_total` in a new column — a migration the
  story says to avoid, and still stale on import.
- **Source:** `plans/us-103/research.md`

### ADR: `appendPmccSnapshot` is the one writer, called inside the caller's transaction

- **Decision:** `src/main/services/pmcc-ledger.ts` exports
  `appendPmccSnapshot(db, positionId, { triggerEvent, eventDate, now }) → { ledger, snapshot }`. It
  reads the position's legs (shared `readLegs`), builds contributions, runs `calculatePmccLedger`,
  inserts one `cost_basis_snapshots` row (`basis_per_share = ledger.basisPerShare`,
  `total_premium_collected = ledger.shortCreditsTotal`, `final_pnl = NULL`,
  `snapshot_at = makeSnapshotAt(eventDate)`, `created_at = now`) and returns both. "It performs no
  transaction of its own: consumers insert their leg(s) and call it inside `db.transaction(...)`,
  so a throw anywhere rolls back leg and snapshot together." `createPmccPosition` is refactored to
  call it (`triggerEvent: 'PMCC_OPEN'`, `eventDate: long.fillDate`) after inserting its two legs —
  same row as before; its local basis / premium / `snapshot_at` arithmetic and inline INSERT are
  removed, `openingDebit` is still computed for the response and INFO log. Per Green results it is
  **generic over the trigger event** (`snapshot` narrows to `CostBasisSnapshotRecord & { triggerEvent: T; finalPnl: null }`),
  so `createPmccPosition` returns a typed `PMCC_OPEN` snapshot without a spread or cast, and it
  throws `PMCC position <id> has no LEAPS leg` when the ledger is `null` ("needed to type `ledger` as
  non-null; not test-driven").
- **Why:** The story: "Recalculate inside the same service-layer SQLite transaction as the leg event
  that triggered it, so a failed event leaves neither a leg nor a snapshot." "One writer means
  US-104/105/115/119 cannot restate the formula or the column mapping." Re-reading legs inside the
  transaction (better-sqlite3 is synchronous, single connection) sees the just-inserted leg.
- **Alternatives considered:** Passing the new leg(s) in memory and merging with the prior ledger —
  "two code paths for the same number". Having the writer own the transaction — "nests a savepoint
  the consumer did not ask for and hides the atomicity contract."
- **Source:** `plans/us-103/research.md`, `plans/us-103/area-5-green-results.md`

### ADR: Contributions are classified by leg role → side and signed by action; roll chains net by action

- **Decision:** `buildPmccContributions(legs: LegRecord[]): PmccContribution[]` in `pmcc-ledger.ts`:
  - Legs with `rollChainId === null`: `side = PMCC_LEG_SIDE[legRole]` where `PMCC_LEG_SIDE` is an
    exhaustive `Record<PmccLegRole, PmccLedgerSide>` (`LEAPS_*` → `LONG`, `SHORT_CALL_*` → `SHORT`);
    `cashPerShare = +premiumPerContract` for `BUY`, `−premiumPerContract` for `SELL`, `0` for
    `EXPIRE` / `ASSIGN` / `EXERCISE`; `fees` and `contracts` from the leg.
  - Roll chains (via `groupRollChains`): one contribution per chain, `cashPerShare = Σ BUY − Σ SELL`
    (= `−netCreditPerShare`), `fees = Σ leg fees`, `contracts = rollTo.contracts`, `side = LONG`
    when `rollFrom.action === 'SELL'` (closing a long), else `SHORT`.
  - Ordered by `fillDate`, then `createdAt` (chains by their earliest leg). "Order does not change
    the result; it is kept so the DEBUG log reads chronologically."
  - A leg whose role is not a PMCC role is excluded with WARN `pmcc_ledger_unknown_leg_role`.
- **Why:** "Side must come from the role, not from action or strike (US-109: 'a side discriminator …
  without inferring from strike'): a short-call buyback and a LEAPS purchase are both `BUY CALL`.
  Sign must come from action because every PMCC event is a cash flow with a direction." "The
  exhaustive record makes 'a PMCC role with no side' a compile error the day US-111 adds one."
- **Alternatives considered:** Classify by action + instrument — wrong for buybacks. Prefix-match
  the role string — untyped. Two role sets as arrays — not exhaustive.
- **Source:** `plans/us-103/research.md`, `plans/us-103/area-5-green-results.md`

### ADR: `groupRollsByChain` moves to `src/main/services/roll-chains.ts` and nets by action

- **Decision:** New shared `groupRollChains(legs: LegRecord[]): RollChain[]` with
  `RollChain = { rollChainId, rollFrom, rollTo, netCreditPerShare, contracts, fees, fillDate }`;
  `netCreditPerShare = Σ SELL premiums − Σ BUY premiums` (4 dp, signed; positive = credit); sorted by
  earliest `fillDate` then `createdAt`; chains missing either half are dropped.
  `assignCspPosition` deletes its private `groupRollsByChain` and maps `{ netCreditPerShare, contracts }`
  onto its existing `ROLL_NET` legs — tests and waterfall labels unchanged.
- **Why:** "The story names this as the second consumer US-16 was waiting for, and US-109 is the
  third. For wheel rolls `ROLL_TO.premium − ROLL_FROM.premium` and `SELL − BUY` are the same number,
  so the move is behaviour-preserving for the wheel while becoming correct for the inverted LEAPS
  roll" (`ROLL_FROM` = SELL, `ROLL_TO` = BUY per OPT-13).
- **Alternatives considered:** A third private copy in `pmcc-ledger.ts` — "exactly what US-16's note
  told us not to do". Netting by role with a `legType` flag — the caller would need to know which
  half is which.
- **Source:** `plans/us-103/research.md`

### ADR: The reserved PMCC leg roles and the PMCC trigger events enter the enums now

- **Decision:** Add `SHORT_CALL_CLOSE`, `SHORT_CALL_EXPIRED`, `LEAPS_CLOSE`, `SHORT_CALL_ASSIGNED`
  to `LegRole` (`src/main/core/types.ts`) and define
  `PmccTriggerEvent = z.enum(['PMCC_OPEN','PMCC_SHORT_OPEN','PMCC_SHORT_EXPIRED','PMCC_SHORT_CLOSED','PMCC_SHORT_ROLL','PMCC_LEAPS_ROLL'])`
  in `src/main/schemas.ts`, with `TriggerEvent = WheelTriggerEvent | z.infer<typeof PmccTriggerEvent>`
  (`WheelTriggerEvent` not exported — the 8 wheel values; `PMCC_OPEN` moved from the old union into
  `PmccTriggerEvent`, so `TriggerEvent` "is a strict superset of what it was before"). No
  `LEG_ROLE_LABEL` text for the new roles; `PHASE_*` maps untouched.
- **Why:** US-101's ADR reserved the role names; US-103 does not produce them but "is the first story
  that must **consume** every one of them". "Owning the trigger vocabulary here is what the story's
  'none of them restates the formula or its messages' ownership clause means in practice — US-104
  passes `'PMCC_SHORT_ROLL'`, it does not coin it." `LegRole` has no SQL CHECK, so no migration.
  `PMCC_CLOSED` / an assignment trigger are left to US-111 / US-120.
- **Alternatives considered:** Keep roles out of the enum and classify by string prefix — loses the
  exhaustive side map. Let each consumer add its trigger name — "guarantees drift in a column with
  no CHECK."
- **Source:** `plans/us-103/research.md`, `plans/us-103/area-1-results.md`

### ADR: Type design — derived types where they buy an invariant, plain types elsewhere

- **Decision:** (data-model §4, reviewed with `/typescript-advanced-types`) `PmccLegRole` is a slice
  of `LegRole`; per the implementation note it is "derived from a single
  `PMCC_LEG_ROLE_VALUES as const satisfies readonly LegRole[]` list, so the type and the runtime
  `Set` behind `isPmccLegRole` cannot drift while a misspelt role remains a compile error; the union
  is identical to the planned `Extract`." `isPmccLegRole(role): role is PmccLegRole` narrows a
  `LegRecord`. `PMCC_LEG_SIDE: Record<PmccLegRole, PmccLedgerSide>` makes "adding a PMCC role to the
  enum without a side" fail typecheck. `PmccTriggerEvent` is a `z.enum` + `z.infer` so "one list
  serves the writer's parameter type, the `_test:` payload schema and `TriggerEvent`".
  `PmccListSummary = { long; short } & Pick<PmccLedgerResult, 'basisPerShare' | 'basisTotal'>` so "a
  renamed engine field breaks the list at compile time". `appendPmccSnapshot` is generic over the
  trigger event (`AppendPmccSnapshotResult<T>`). `PmccCostBasisProps` uses the main-process
  `PmccLedgerResult` re-exported from `api/positions`, removing a cast. Engine types,
  `PmccLedgerSide`, `RollChain` and `GetPositionResult.pmccLedger` stay plain.
- **Why:** "Plain types wherever a plain type encodes the rule; an advanced construct only where it
  buys an invariant or a derivation."
- **Alternatives considered:** Not documented beyond the planned `Extract<LegRole, …>` form, which
  the shipped const-list derivation replaced with an identical union.
- **Source:** `plans/us-103/data-model.md` §4, `plans/us-103/area-5-green-results.md`

### ADR: One shared legs reader replaces `readPmccOpeningLegs`

- **Decision:** `src/main/services/leg-rows.ts` exports `readLegs(db, positionId): LegRecord[]` (the
  `GET_LEGS_QUERY` + `mapLegRow` formerly private to `get-position.ts`) and
  `readLegsByPosition(db, positionIds): Map<string, LegRecord[]>` (one `IN (...)` query, same
  `fill_date ASC, created_at ASC` ordering; `[]` → empty map with no query). `pmcc-opening-legs.ts`
  becomes pure over `LegRecord[]` (`pmccOpeningLegs(legs)`, `pmccInitialNetDebit(legs)`);
  `readPmccOpeningLegs` and the `PmccOpeningLegRow` DB shape are deleted. `get-position.ts` /
  `list-positions.ts` read legs once and derive the opening summary, `initialNetDebit` and the
  ledger from the same rows.
- **Why:** "The ledger needs every leg; reading the two opening roles separately would be a second
  query per position for a subset of the same rows."
- **Alternatives considered:** Keep `readPmccOpeningLegs` and add `readPmccLegs` — "two readers
  over one table."
- **Source:** `plans/us-103/research.md`, `plans/us-103/plan.md` §4

### ADR: The current LEAPS strike for `Effective share cost` is the newest long-side BUY leg

- **Decision:** `currentLongStrike(legs)` returns the `strike` of the most recent (by `fillDate`,
  `createdAt`) leg whose side is `LONG` and action is `BUY` — `LEAPS_OPEN` at entry, the `ROLL_TO`
  of the latest LEAPS roll afterwards — or `null`. Per Green: the newest long BUY is "latest of
  `LEAPS_OPEN` legs and `ROLL_TO` of chains with a SELL `ROLL_FROM`"; it also supplies
  `leapsContracts`, and `pmccLedgerFromLegs` returns `null` without one (not only for `[]`). A short
  roll's BUY half does not count.
- **Why:** The story: "The strike change surfaces through the effective-share-cost line, which reads
  the open long leg's strike, not through the basis." After US-105's roll the line re-anchors to
  $104.30 with no other rule.
- **Alternatives considered:** Reuse `readPmccOpeningLegs`' "later rows win" over `LEAPS_OPEN` only —
  misses the roll. Derive from `activeLegSubquery` — "phase-aware and wheel-shaped."
- **Source:** `plans/us-103/research.md`, `plans/us-103/area-5-green-results.md`,
  `plans/us-103/area-5-red-results.md`

### ADR: Detail and list carry the ledger as server-derived fields; the renderer formats only

- **Decision:** `GetPositionResult` gains `pmccLedger: PmccLedgerResult | null` (null for a wheel or
  a PMCC with no legs). `PmccListSummary` replaces `initialNetDebit` with
  `Pick<PmccLedgerResult, 'basisPerShare' | 'basisTotal'>`. `initialNetDebit` stays on the detail
  result because `PmccLegReference` still shows it. The optimistic row
  `position-list-items.ts#toPmccListItem` fills the two fields from the create response
  (`costBasisSnapshot.basisPerShare`, `openingDebit.initialNetDebit` — equal to the ledger at entry).
- **Why:** server-side-dte-and-derived-fields ADR: "derived money lives in the main process; the
  renderer parses nothing but display strings."
- **Alternatives considered:** Compute in the renderer from `detail.legs` by importing the engine —
  needs roll-chain grouping in the renderer and gives the list nothing.
- **Source:** `plans/us-103/research.md`

### ADR: `PmccCostBasis` is its own drawer component selected in `PositionCockpit`

- **Decision:** `src/renderer/src/components/position-cockpit/PmccCostBasis.tsx` renders
  `<CollapsedDrawer title="Cost basis" fieldCount={6} defaultOpen>` with a `Caption`
  (`US-103 · cash ledger, never a quote`, wrapped in `px-5 pt-3`) and one `StatGrid minWidth={150}`
  of six cells in mockup order: `Cost basis / share` (`text-wb-sky`), `Total`, `LEAPS cost to date`,
  `Short-call credits to date`, `Effective share cost`, `Premium recovered`. The PMCC branch of
  `PositionCockpit` becomes a `flex flex-col gap-3` stack of `PmccLegReference` then `PmccCostBasis`
  (only when `pmccLedger` is non-null). The wheel's private `CostBasisDrawer` is untouched. Green
  recorded two intentional departures from the mockup: `OwnerNote` → production `Caption`, and the
  mockup's green credits colour is ruled out by the story.
- **Why:** The story: "Select it on `position.strategy` in `PositionCockpit`; do not branch inside the
  wheel's `Cost basis & history` drawer." The shipped `PmccLegReference` is not yet a drawer (US-118
  reshapes the stack), so this drawer sits directly below it.
- **Alternatives considered:** Extend `CostBasisDrawer` with a `strategyType` prop — "the branch the
  story forbids."
- **Source:** `plans/us-103/research.md`, `plans/us-103/area-9-green-results.md`

### ADR: Display formatting of the six cells

- **Decision:**
  - Money through `fmtMoney` / `fmtMoneyGrouped`; a negative basis renders `-$0.40` / `-$40.00`
    (ASCII hyphen), never clamped.
  - `Short-call credits to date` shows the figure's **contribution to basis**: `fmtMoney` of the
    negated `shortCreditsPerShare` (via `Decimal.neg()`), so a $2.00 credit reads `-$2.00`. No
    colour: "credits are not a gain (the story explicitly rules out the mockup's green)."
  - `Premium recovered` is `fmtPct1(premiumRecoveredPercent)` → `8.0%`, `101.8%`; `—` when null.
    New `fmtPct1(value: string): string` in `lib/format.ts` (one decimal, `ROUND_HALF_UP` via
    `Decimal`).
  - `Effective share cost` is `fmtMoney(effectiveShareCost)` or `—`; the strike is **not** named in
    the cell ("Mockup cleanup pending: do not build").
  - No "LEAPS fully paid for" state, no profit / realized wording, no share count, no max profit,
    breakeven or annualized return.
- **Why:** "The AC fixes the labels and the numbers; the 'do not build' list fixes what is left out."
- **Alternatives considered:** A Unicode minus to match the Gherkin's `−$2.00` — "would be the only
  place in the app using one; the e2e asserts the app's own `-$2.00`."
- **Source:** `plans/us-103/research.md`, `plans/us-103/area-9-green-results.md`

### ADR: A dev-only `_test:pmcc-record-leg-event` channel drives post-entry events in e2e

- **Decision:** `src/main/ipc/test-pmcc-ledger.ts` registers `_test:pmcc-record-leg-event` under the
  existing `NODE_ENV === 'test'` gate in `src/main/index.ts` (next to `registerTestIvHistoryIpc(db)`).
  The handler, wrapped in `handleIpcCall`, Zod-parses then inserts the rows and calls
  `appendPmccSnapshot` inside **one** `db.transaction`, returning `{ ok: true, ledger, snapshot }`.
  Preload exposes `window.api.testPmccRecordLegEvent`. "It performs no lifecycle validation — it is a
  fixture writer, not a feature." The storage-failure scenario installs an SQLite
  `BEFORE INSERT ON cost_basis_snapshots … RAISE(ABORT)` trigger on the temp DB through the
  `sqlite3` CLI, not a flag on the seam.
- **Why:** "Eleven of the thirteen scenarios need an expiration, a subsequent short, a short roll or a
  LEAPS roll to exist, and no production write path for those lands before US-104/105/115/119.
  Seeding the snapshots themselves by SQL would make the chain scenarios tautological." The seam
  "exercises the real writer, the real read path and the real drawer", and the `_test:` + `NODE_ENV`
  convention keeps it out of packaged builds. On failure injection (authoritative, Area 11 Red): the
  planned `chmod 0o444` "returned `{ ok: true }`: the main process already holds the SQLite file
  descriptors open read-write, so a permission change after open cannot fail a write"; the abort
  trigger "is a stronger test: the leg row inserts first, then the snapshot write aborts, so
  `legs === 2` and `snapshots === 1` prove the transaction rolled back."
- **Alternatives considered:** Direct `sqlite3` inserts from the spec — "fine for legs, tautological
  for snapshots." Waiting for the consumer stories — leaves the AC unverified at e2e. Reusing
  `_test:` from `app.evaluate` with `require` — the bundle does not expose services. (Failure
  injection: `chmod` — tried and rejected.)
- **Source:** `plans/us-103/research.md`, `plans/us-103/area-11-red-results.md`,
  `plans/us-103/area-8-green-results.md`

### ADR: Logging

- **Decision:** INFO `pmcc_basis_recalculated { positionId, triggerEvent, basisPerShare, basisTotal }`
  from `appendPmccSnapshot`. DEBUG `pmcc_ledger_contributions { positionId, contributions }`,
  `pmcc_roll_chains { positionId, chains: [{ rollChainId, side, netCreditPerShare }] }`,
  `pmcc_snapshot_insert { positionId, snapshotId, triggerEvent }`. WARN
  `pmcc_ledger_unknown_leg_role { positionId, legId, legRole }`. Nothing in `core/`.
- **Why:** Story: "INFO: recalculated basis per leg event with its trigger. DEBUG: ordered
  contributions, roll-chain nets, and transaction checkpoints."
- **Source:** `plans/us-103/research.md`

### `positions:list` (US-103 extension)

- **Type:** IPC handler
- **Shape:**

  interface PmccListItem extends PositionListItemBase {
    strategyType: 'PMCC'

## Acceptance Criteria

Thirteen scenarios from Linear OPT-9, one named e2e `it` each in `e2e/pmcc-cost-basis.spec.ts` (all
13 PASS per `area-11-red-results.md`). Fixture: XYZ LEAPS $80 call BUY @ 25.00 (+368d), short $110
call SELL @ 2.00 (+32d), 1 contract, $0 fees; later events `EXPIRE_1`, `SHORT_2` (SELL $108 @ 1.80),
`SHORT_ROLL` (BUY $108 @ 3.00 + SELL $112 @ 2.40), `LEAPS_ROLL` (SELL $80 @ 26.00 + BUY $85 @ 23.50),
`CYCLES` (SELL $118 @ 19.70).

1. **Cost basis after the two opening legs** — `Cost basis` drawer open by default (`aria-expanded="true"`)
   below the `Buy LEAPS call` section; cells `$23.00`, `$2,300.00`, `$25.00`, `-$2.00`, `$103.00`,
   `8.0%`; no `Max profit`, `Breakeven`, `Annualized`.
2. **The open short-call credit is cash in the ledger, not profit** — `Short-call credits to date`
   `-$2.00`; no `profit` / `realized` (case-insensitive), no `Effective Basis / Share`, no `Shares`.
3. **A short call that expires worthless does not move cost basis** — after `EXPIRE_1`: `$23.00` /
   `$2,300.00`; two snapshots, last `PMCC_SHORT_EXPIRED` with `23.0000`.
4. **A subsequent short call lowers cost basis** — `$21.20`, `$2,120.00`, credits `-$3.80`,
   effective `$101.20`.
5. **A short-call roll contributes one net amount, not two gross amounts** — `$21.80`, `$2,180.00`;
   exactly one new snapshot `PMCC_SHORT_ROLL` `21.8000`, delta `0.6000` from previous.
6. **A LEAPS roll applies its net cash and re-anchors the effective share cost** — `$19.30`,
   `$1,930.00`, LEAPS cost `$22.50`, effective `$104.30` (not `$99.30` / `$109.30` — no strike-delta).
7. **Credits that exceed the LEAPS cost give a negative basis** — `-$0.40`, `-$40.00`, `101.8%`;
   not `$0.00`.
8. **Cost basis is per share of contract regardless of quantity** — 3 contracts: `$23.00`, `$6,900.00`.
9. **Fees are counted once, in the leg that incurred them** — $1.00 fee each leg: `$23.02`,
   `$2,302.00` (not `$23.04`, not `$23.00`).
10. **The audit chain records one snapshot per leg event** — five rows, triggers
    `PMCC_OPEN, PMCC_SHORT_EXPIRED, PMCC_SHORT_OPEN, PMCC_SHORT_ROLL, PMCC_LEAPS_ROLL`, bases
    `23.0000, 23.0000, 21.2000, 21.8000, 19.3000`, `snapshotAt` ascending.
11. **A failed leg event leaves no cost-basis change** — abort trigger on `cost_basis_snapshots`;
    `recordEvent(SHORT_2)` → `{ ok: false }`; reload `$23.00`; `legs === 2`; one snapshot.
12. **The positions list shows the running cost basis** — after `EXPIRE_1`, `SHORT_2`, `SHORT_ROLL`:
    XYZ row contains `$2,180.00`, neither `$2,300.00` nor `net debit`.
13. **Leave a classic wheel unaffected** — wheel at $46.50 basis (strike 48.50, premium 2.00,
    assigned) shows `Cost basis & history` (and `$46.50`), neither `Cost basis / share` nor
    `Effective share cost`.

## Decisions & Tradeoffs

- **Per-share figures divide by the LEAPS contracts**, so partial short coverage (US-115) prorates:
  `LONG +25 ×3`, `SHORT −2 ×1`, `leapsContracts 3` → `basisTotal 7300.0000`, `basisPerShare 24.3333`.
  (`plans/us-103/research.md` Open Questions; `plan.md` §2)
- **Negative basis is never clamped** — no `max(0, …)` anywhere; `fmtMoney` renders the sign.
  (`data-model.md` §2)
- **Rendered minus is the ASCII hyphen** (`-$2.00`), not the Gherkin's Unicode `−$2.00`; the e2e
  asserts the app's own string. (`research.md`)
- **No phase changes.** "`appendPmccSnapshot` accepts any PMCC position regardless of phase; phase
  guards belong to the consumer stories' lifecycle functions." (`data-model.md` §3)
- **List `long` / `short` summaries keep US-101's later-rows-win rule** (orchestrator decision, Area 7
  Green): the Red test asserting `pmcc.short` unchanged after `SHORT_2` "contradicts shipped US-101
  behaviour" and was corrected to assert `pmcc.short` equals the `SHORT_2` leg (strike `108.0000`);
  `pmccOpeningLegs` was left untouched. (`area-7-green-results.md`)
- **"Fill price missing → dropped" list test updated, not deleted**: renamed "lists a PMCC whose leg
  fill price is missing, with the basis from its premiums (US-103)"; it pins that the list basis is
  independent of `fill_price`. (`area-7-green-results.md`)
- **Test-fixture fallout the plan missed:** `PositionCard.test.tsx`'s PMCC fixture/`net debit`
  assertion (Area 10 Red), three renderer `GetPositionResult` fixtures gaining `pmccLedger: null`
  (Area 6 Green), and the stale US-101 e2e assertion `'$2,300.00 net debit'` in
  `e2e/open-pmcc-position.spec.ts:419` — "stale US-101 assertion, not a product defect"; whether to
  rename the `it` or amend OPT-7 "is a story-owner decision." (`area-10-red-results.md`,
  `area-6-green-results.md`, `area-11-red-results.md`)
- **The two nested `flex flex-col gap-3` stacks** in the cockpit PMCC branch (`PmccLegReference`
  already returns one) were flagged for refactor. (`area-9-green-results.md`)
- **Shared test fixtures:** `src/main/services/test-fixtures/pmcc-legs.ts` — `pmccFixtures(positionId, day = FIXED_DAY)`
  (`OPEN`, `EXPIRE_1`, `SHORT_2`, `SHORT_ROLL` `rc-1`, `LEAPS_ROLL` `rc-2`, `CYCLES`, `FEES`, `THREE`),
  `makePmccLeg`, `insertLegs`, `FIXED_DAY` anchored on 2026-09-14; e2e mirrors it in
  `e2e/pmcc-ledger-helpers.ts` with `localDate(n)` offsets because `createPmccPosition` validates
  against the run day. (`area-5-red-results.md`, `area-11-red-results.md`)
- **Out of scope (per Linear):** rendering the snapshot history (US-109); recording the leg events in
  production (US-104/105/111/115/119); live/unrealized P&L; max profit, breakeven, annualized return;
  the "LEAPS fully paid for" state, naming the strike inside the Effective share cost cell, green
  credits ("mockup cleanup pending"); final P&L on close; alerts; tax lots; editing fills.
  (`plan.md` Out of scope)
