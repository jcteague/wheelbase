# Extract: us-15

## Summary

Extends the existing `LegHistoryTable` component to detect ROLL_FROM/ROLL_TO leg pairs (grouped by `rollChainId`) and render them as visually linked sections with a group header, indented leg rows, and a cumulative summary row. Requires a small backend fix to expose `rollChainId` from `getPosition`, then pure grouping logic in the renderer, and finally updated component rendering.

## Architecture Decisions

### ADR: Expose `rollChainId` through `getPosition` rather than infer pairs by ordering

- **Decision:** Add `roll_chain_id` to `GET_LEGS_QUERY`, `LegRow`, and `mapLegRow` in `get-position.ts`, and add `rollChainId` to `LegRecord` in `schemas.ts`.
- **Why:** The DB column (`roll_chain_id TEXT`) exists in the schema (migration 001) and is written by both `roll-csp-position.ts` and `roll-cc-position.ts`, but `getPosition` does not surface it. The story claims "all data is already available from `getPosition`" — this requires a small backend fix to fulfil that claim.
- **Alternatives considered:** Derive grouping from leg order alone (ROLL_FROM always precedes ROLL_TO in fill_date/created_at order). Rejected: two rolls on the same day would be ambiguous without `rollChainId`.
- **Source:** `plans/us-15/research.md`

### ADR: Unified `getCcRollTypeLabel` / `getCcRollTypeDetail` for both CSP and CC rolls

- **Decision:** Use `getCcRollTypeLabel` from `src/renderer/src/lib/rolls.ts` for all roll pairs (CSP and CC alike). Use `getCcRollTypeDetail` to produce the strike/expiration detail string shown alongside the label.
- **Why:** `getCcRollTypeLabel` already handles all cases (same strike / different strike, same expiration / different expiration). `getRollTypeLabel` (CSP-only) only compares strikes and is narrower. The roll group header needs both the label ("Roll Down & Out") and the detail ("$180 → $175, Apr 18 → May 16").
- **Alternatives considered:** Separate CSP/CC roll type derivation. Rejected: unified utility avoids duplication and both functions already exist.
- **Source:** `plans/us-15/research.md`

### ADR: Pure `buildRollTimeline` function with discriminated-union `TimelineItem[]`

- **Decision:** A `buildRollTimeline` pure function in a new `src/renderer/src/lib/rollGroups.ts` produces a typed discriminated-union array (`TimelineItem[]`) consumed by `LegHistoryTable`. Each item is either `{ type: 'leg', leg }` or `{ type: 'roll', rollNumber, rollType, rollDetail, fillDate, rollFromLeg, rollToLeg, net }`.
- **Why:** Keeps the grouping logic pure and independently testable. The component becomes a thin renderer over the timeline array.
- **Alternatives considered:** Detecting roll pairs inline inside the component's render loop. Rejected: harder to unit-test; the component already has enough rendering complexity.
- **Source:** `plans/us-15/research.md`

### ADR: Render roll groups as spanning `<tr>` rows inside the existing `<table>`

- **Decision:** Roll group header and cumulative summary render as full-width `<tr>` rows where a single `<td colspan={8}>` spans all columns. Individual ROLL_FROM/ROLL_TO leg rows render as normal `<tr>` rows with a blue-tinted background and additional left padding on the first cell to create visual indentation.
- **Why:** The existing component uses an HTML `<table>`. Spanning rows via `colspan` is the standard table approach and avoids a complete rewrite.
- **Alternatives considered:** Converting the table to a flex/grid layout. Rejected: out of scope; risks breaking existing column alignment and tests.
- **Source:** `plans/us-15/research.md`

### ADR: Place cumulative roll summary immediately after the last roll group

- **Decision:** One `CumulativeSummaryRow` appears directly after the last roll group, before any subsequent normal legs (e.g. ASSIGN, CC_OPEN). It summarises total credits, total debits, and net across all roll groups.
- **Why:** Matches the mockup (`CumulativeSummary` appears after all roll groups) and the AC ("a cumulative summary shows…").
- **Alternatives considered:** Placing it in `<tfoot>`. Rejected: `<tfoot>` already holds the final P&L row; mixing them would be ambiguous.
- **Source:** `plans/us-15/research.md`

### ADR: Header shows net per contract only; total dollar amount lives in cumulative summary

- **Decision:** The roll group header row shows net credit/debit per contract only (e.g. "+$1.60/contract"). The per-contract figure appears in the right section of the spanning row. A separate total dollar amount is not shown in the header.
- **Why:** The mockup's `RollGroupHeader` right side shows `+$N.NN/contract`. Showing both per-contract and total in the header adds clutter; per-contract in header, total in cumulative summary.
- **Alternatives considered:** Showing both per-contract and total in the header. Not contradicted by the mockup but adds clutter.
- **Source:** `plans/us-15/research.md`

### `buildRollTimeline` and `computeCumulativeRollSummary` (pure utility)

- **Type:** Pure function module
- **Shape:**

```typescript
type RollGroup = {
  type: 'roll'
  rollNumber: number // sequential 1-based index (chronological by ROLL_FROM fillDate)
  rollChainId: string
  rollType: string // e.g. "Roll Out", "Roll Down & Out"
  rollDetail: string // e.g. "$180 → $175, Apr → May expiration"
  fillDate: string // ROLL_FROM fillDate
  rollFromLeg: LegHistoryEntry
  rollToLeg: LegHistoryEntry
  net: {
    isCredit: boolean
    perContract: number // absolute value per contract
    total: number // absolute value total (perContract * contracts * 100)
  }
}

type NormalLeg = {
  type: 'leg'
  leg: LegHistoryEntry
}

type TimelineItem = NormalLeg | RollGroup

type CumulativeRollSummary = {
  totalCredits: number
  totalDebits: number
  net: number // totalCredits - totalDebits
  rollCount: number
}

export function buildRollTimeline(legs: LegHistoryEntry[]): TimelineItem[]
export function computeCumulativeRollSummary(rollGroups: RollGroup[]): CumulativeRollSummary
```

Grouping algorithm:

1. Partition legs into roll legs (`legRole === 'ROLL_FROM' || legRole === 'ROLL_TO'`) vs normal legs.
2. Group roll legs by `rollChainId`. Each group must have exactly one ROLL_FROM and one ROLL_TO.
3. Sort roll groups by ROLL_FROM `fillDate` ASC; assign `rollNumber` 1, 2, 3…
4. For each group: compute `rollType` / `rollDetail` via `getCcRollTypeLabel` / `getCcRollTypeDetail`, compute `net` via `computeNetCreditDebit`.
5. Interleave normal legs and roll groups chronologically; append one `{ type: 'cumulative', summary }` item immediately after the last roll group.

- **Source:** `plans/us-15/plan.md`, `plans/us-15/data-model.md`
- **Implementation:** `src/renderer/src/lib/rollGroups.ts`

## Acceptance Criteria

- **AC1 — Roll pair is grouped with a visual header in the leg timeline:** ROLL_FROM and ROLL_TO legs sharing a `roll_chain_id` are grouped together; the group has a visual connector (indent, bracket, or background color); the group header shows "Roll #N — <Roll Type>" with the fill date.
- **AC2 — Roll pair shows net credit summary in green:** A summary line shows "Net Credit: $X.XX/contract ($Y.YY total)" and is displayed in green.
- **AC3 — Roll pair shows net debit in amber:** A summary line shows "Net Debit: $X.XX/contract ($Y.YY total)" and is displayed in amber/yellow.
- **AC4 — Multiple sequential rolls are numbered in order with cumulative summary:** Rolls are labeled "Roll #1", "Roll #2", "Roll #3" in chronological order; each roll pair shows its own net; a cumulative summary shows "Total roll credits: $X.XX, Total roll debits: $Y.YY, Net: $Z.ZZ".
- **AC5 — Roll type label reflects strike and expiration changes:** A roll that changed strike from $180 to $175 and expiration from Apr to May shows "Roll Down & Out: $180 → $175, Apr 18 → May 16".
- **AC6 — Non-roll legs display normally between roll pairs:** For a timeline of `CSP_OPEN`, Roll #1 (ROLL_FROM + ROLL_TO), `ASSIGN`, `CC_OPEN`, the non-roll legs render as normal rows; the roll pair renders as a grouped section between them; chronological order is maintained.
- **AC7 — Running cost basis column includes roll impact:** Given running basis $176.50 and a roll with net credit $1.60/contract, the ROLL_TO leg row shows updated running basis $174.90; the ROLL_FROM basis cell is blank.

## Decisions & Tradeoffs

- **`mapActiveLeg` sets `rollChainId: null` even for ROLL_TO active legs** where the DB has a real UUID. The activeLeg is used only for displaying current strike/expiration/premium in the position header — not for the timeline. If a future feature needs `activeLeg.rollChainId`, the `GET_QUERY` JOIN needs `l.roll_chain_id` added. (`plans/us-15/refactor-phase-area1-area2-results.md`)
- **Consolidated `NormalLegRow` + `RollLegRow` into a single `LegRow({ leg, isRoll })`** during refactor. The two functions had identical 8-column structure; they only differed in `background` style and `pl-7` indent on the first cell. Eliminated ~25 lines of duplicated JSX. (`plans/us-15/refactor-phase-results-layer3.md`)
- **Module-level color constants** (`ROLL_CREDIT_BG`, `ROLL_DEBIT_BG`, `ROLL_LEG_BG`, `CUMULATIVE_BG`, `CUMULATIVE_BORDER_TOP`) replace inline magic rgba strings scattered across components. Single source of truth for tinting values. (`plans/us-15/refactor-phase-results-layer3.md`)
- **`LegHistoryEntry` moved to `rollGroups.ts`** rather than redefined locally in `LegHistoryTable.tsx` — removes type duplication; both files import from the same module. (`plans/us-15/green-phase-results-layer3.md`)
- **`React.Fragment` with `rollChainId` key** wraps the three `<tr>` elements a roll group produces (header + two leg rows). (`plans/us-15/green-phase-results-layer3.md`)
- **Inline styles for dynamic colors** (`borderTop`, `background`, per-group colors) because they depend on runtime values from `rollCreditDebitColors`. (`plans/us-15/green-phase-results-layer3.md`)
- **ROLL_FROM premium rendered in red with a leading minus** (it represents the cost to close, not a credit); ROLL_FROM running basis cell is blank (the roll pair is atomic; basis is only shown on ROLL_TO). Legs following a same-day roll correctly inherit the post-roll basis via `deriveRunningBasis`. (`plans/us-15/manual-test-plan.md`)
- **All other service write-paths set `rollChainId: null`** on the `LegRecord` they construct (CSP_OPEN, ASSIGN, CC_CLOSE, CSP_CLOSE, CC_EXPIRED, EXPIRE, CC_OPEN, CALLED_AWAY). Only the two roll services (`roll-csp-position.ts`, `roll-cc-position.ts`) pass the actual UUID. (`plans/us-15/refactor-phase-area1-area2-results.md`)
