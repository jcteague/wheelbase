# Extract: us-60

## Summary

US-60 adds an **Expiration Calendar** page that plots active option expirations by date, color-coded by wheel phase, so a trader can see clustering before it becomes urgent. It ships two layouts selectable via a toggle — **Month Grid** (month-scoped, navigable, with a day-detail side panel and `+N more` overflow) and **Agenda** (a rolling horizon anchored at today — upcoming expirations over the next 30 days grouped by week with a density bar and a "BUSY WEEK" flag). The selected layout is persisted (`localStorage`) so it is restored on the next visit. The heatmap layout from the mockup was dropped per the user's instruction. The feature is pure renderer: it reuses the existing `positions:list` data via `usePositions()` and derives everything client-side — no new IPC, service, engine, or migration.

## Architecture Decisions

### ADR: Reuse `positions:list`; group in a pure renderer helper (no new IPC)

- **Decision:** US-60 adds no new IPC channel, service, migration, or engine. The calendar consumes the existing `usePositions()` query and derives its view-model with a new pure helper module `src/renderer/src/lib/expiration-calendar.ts`. Entries are filtered to `status === 'ACTIVE'` with a non-null `expiration`, then grouped by expiration date and shaped into a month grid and week-grouped agenda.
- **Why:** `PositionListItem` already carries every field the calendar renders (`ticker`, `phase`, `strike`, `expiration`, `dte`, `id`), with DTE already computed server-side and the `HOLDING_SHARES` exclusion already implied by the phase-aware active-leg join. Grouping-by-date is a pure display concern. A dedicated `calendar:list` endpoint would duplicate `positions:list`'s data for a trivial transform.
- **Alternatives considered:** A dedicated `expiration-calendar:list` IPC + service mirroring `evaluate-alerts.ts`'s `EVALUABLE_QUERY` and US-51's `listManagementQueue` read path (rejected). A derived `useExpirationCalendar()` hook wrapping `usePositions` with its own query key (rejected — would double-fetch or fork the cache).
- **Source:** `plans/us-60/research.md`

### ADR: Grid (month-scoped) + Agenda (rolling horizon), toggled by a segmented control

- **Decision:** Ship two layouts from the mockup, selected by a small segmented control; drop the Heatmap layout. Month Grid is month-scoped and navigable via `CalendarMonthNav` (prev/next/today), with a day-detail side panel. Agenda is a rolling horizon anchored at today — expirations `>= today` within the next `AGENDA_HORIZON_DAYS` (default 30), grouped by week. Agenda does not use `viewMonth`; the month nav is hidden while agenda is active. Each layout has its own empty state: grid → "No expirations this month"; agenda → "No expirations in the next 30 days".
- **Why:** The user asked for a rolling agenda — a rolling, today-anchored horizon matches the story's intent of anticipating clustering, and avoids splitting a cluster that straddles a month boundary. The grid stays month-scoped because a monthly calendar is inherently a month view.
- **Alternatives considered:** Month-scoped agenda sharing `viewMonth` with the grid (rejected per user instruction). Unbounded future-expirations list with no horizon cap (rejected). Adding shadcn `Tabs`/`ToggleGroup` for the toggle (viable, but a hand-rolled control matches the codebase's existing hand-rolled pills — `MarketStatusPill`, `UrgencyPill`).
- **Source:** `plans/us-60/research.md`

### ADR: Persist the layout choice in `localStorage` via a `useCalendarView` hook

- **Decision:** The selected layout (`'grid' | 'agenda'`) is persisted so it is restored on the next visit/app restart. Persistence is isolated in `useCalendarView()` (`src/renderer/src/hooks/useCalendarView.ts`), which reads/writes `localStorage` under key `wb.calendar.view`, defaulting to `'grid'` when absent or invalid. `viewMonth` and `selectedDate` remain ephemeral `useState`.
- **Why:** `localStorage` persists across app restarts in the Electron renderer and is the idiomatic home for a pure UI preference — no IPC round-trip, no DB migration. Isolating it in a hook keeps read/write in one place and makes it unit-testable with a mocked `localStorage`.
- **Alternatives considered:** Storing the preference in the settings table via an IPC handler like alert thresholds (US-57) (rejected — heavier than a UI-only preference warrants). Keeping it ephemeral `useState` (rejected — does not survive a restart). Inlining `localStorage` calls in `CalendarPage` (rejected — harder to test).
- **Source:** `plans/us-60/research.md`

### ADR: Chip overflow at 3 entries per date cell

- **Decision:** A month-grid date cell renders at most 3 ticker chips (`CHIP_LIMIT`); any remainder renders as a `+N more` affordance. The day-detail panel shows the full list for the selected date.
- **Why:** Directly satisfies the AC "Overflow indicator appears when more expirations exist than fit" and matches the mockup's `slice(0, 3)`.
- **Alternatives considered:** Scrolling within a cell (rejected — breaks the at-a-glance density read). Showing all chips and letting cells grow (rejected — destroys the uniform month grid).
- **Source:** `plans/us-60/research.md`

## Decisions & Tradeoffs

- **Phase colour binding is the one allowed inline-`style` exception.** `CalendarChip`'s dot and background/border, and `PhaseBadge`'s dot, bind phase colour via inline `style`/CSS custom property since the value set is genuinely dynamic (raw hex per phase) — everything else uses `wb-*` Tailwind classes. `WeekDensityBar`'s segment widths are the same category of exception (a genuinely dynamic numeric value).
- **`CalendarChip`'s dot was deliberately left independent of `PhaseBadge`'s dot** rather than factored into a shared sub-component — a chip and a badge are different concepts, and the Refactor passes for Area 2 explicitly chose not to over-abstract two small, differently-styled dot renderings.
- **`emptyMonth` is derived from the built grid** (`grid.flat().every(cell => cell.entries.length === 0)`), not a second date-range scan over raw entries — avoids duplicating the grid's own inMonth/entries filter logic.
- **`today` is frozen once per `CalendarPage` mount** via `useMemo(() => new Date(), [])` rather than a bare `new Date()` per render — a fresh Date object every render would change identity and defeat the `grid`/`weeks` `useMemo` memoization, forcing an `eslint-disable` workaround that was avoided by freezing it instead.
- **`MarketStatusPill` wiring on `CalendarPage` mirrors `PositionsListPage`** (`useSettingsStatus()` → `hasBroker` → `useMarketStatus(hasBroker)` → `deriveMarketStatusDisplay()`), with `stale` hardcoded `false` since the calendar page never fetches stock quotes and has no staleness signal to plumb through.
- **E2E tests seed positions directly through the IPC bridge** (`window.api.createPosition`/`assignPosition`/`openCoveredCall`) rather than walking the UI entry forms, mirroring the pattern already established in `e2e/option-pnl.spec.ts` — the calendar itself is pure-renderer, so the tests only need real rows in the DB.
- **`buildMonthGrid`'s row count is not a fixed 6×7 invariant** — it varies by month calendar shape (5 or 6 weeks depending on where the month starts/ends). An early e2e assertion incorrectly assumed a hardcoded 42-cell grid; the fix asserts `cellCount % 7 === 0 && cellCount >= 28` instead. The pre-existing unit test `'returns a 6x7 grid of DayCell rows'` only gets 6 rows because its fixture happens to use August 2026 — not a general contract.
