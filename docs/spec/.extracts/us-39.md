# Extract: us-39

## Summary

US-39 delivers `MassiveMarketDataProvider` — a REST-based market data adapter backed by the Massive.com API — as the second concrete implementation of the `MarketDataProvider` interface established by US-31. The plan is part of a larger broker/market-data split (US-31→US-39→US-40) that separates market data concerns (stock NBBO quotes, option snapshots with optional Greeks, paginated option chains) from broker concerns (account info, activities, market status). Implementation spans a full Red→Green→Refactor cycle across nine areas, introduces no database migrations, and delivers 1,155+ passing tests. The old `AlpacaMarketDataProvider` class and the combined `MarketDataProvider`/`BrokerProvider` interface are replaced by separate `MarketDataProvider` and `BrokerProvider` interfaces with split concrete implementations. (Sources: `plans/us-39/plan.md`, `plans/us-39/research.md`, all `*-phase-results.md` files)

## Architecture Decisions

### ADR: Massive REST over raw `fetch` — no SDK

- **Decision:** Use Node 20+ platform `fetch` directly for all Massive API calls. No SDK dependency.
- **Why:** Massive has no official Node SDK. Raw `fetch` is built-in to Node 20+ and available in Electron's main process without additional dependencies.
- **Alternatives considered:** Wrapping `axios` or `node-fetch` — rejected as unnecessary overhead for a simple REST client.
- **Source:** `plans/us-39/research.md`

### ADR: Bearer token auth in HTTP header

- **Decision:** Pass the Massive API key as `Authorization: Bearer ${apiKey}` on every request.
- **Why:** Massive REST API specification requires the Bearer header pattern.
- **Alternatives considered:** Query-string `?apiKey=` param — rejected because it exposes secrets in URLs and logs.
- **Source:** `plans/us-39/research.md`

### ADR: WebSocket streaming declared but deferred

- **Decision:** `supportsStreaming()` returns `true` for `stockQuotes` and `optionQuotes` feeds but `stream()` throws `MarketDataError` with `code: 'streaming_unsupported'`.
- **Why:** REST polling meets Phase 2 requirements. WebSocket auth for Massive is orthogonal and will be a separate story.
- **Alternatives considered:** Returning `false` from `supportsStreaming()` — rejected to avoid misleading callers about Massive's real capabilities.
- **Source:** `plans/us-39/research.md`, `plans/us-39/area7-green-phase-results.md`

### ADR: Optional Greeks — no fabricated zeros

- **Decision:** `greeks` and `impliedVolatility` are typed as optional on `OptionSnapshot`. When the Massive response omits them, the adapter returns `undefined` rather than zero-filled objects.
- **Why:** Fabricating zeros would cause the Greeks display panel to render `0.00` instead of `—` (unavailable), misleading traders into treating missing data as real values.
- **Alternatives considered:** Throw when Greeks are absent — rejected because some option types (e.g. deep ITM) legitimately have no Greeks data.
- **Source:** `plans/us-39/data-model.md`, `plans/us-39/research.md`

### ADR: Market status stays on BrokerProvider

- **Decision:** `getMarketStatus()` is not ported to `MassiveMarketDataProvider`. It lives exclusively on `BrokerProvider` (implemented by `AlpackaBrokerProvider`).
- **Why:** Massive's market-status endpoint is per-asset-class and doesn't map cleanly to the single `MarketStatus` shape. Alpaca's `getClock()` is the authoritative source for the regular/pre/post/closed session signal used across the UI.
- **Source:** `plans/us-39/research.md`

### ADR: Old Alpaca market-data path deleted — no fallback

- **Decision:** `AlpacaMarketDataProvider` is removed entirely. Users without Massive configured receive a clear `auth_failed` error rather than falling back to Alpaca quote data.
- **Why:** Maintaining two live data paths creates silent inconsistency. The product decision is Massive-first for market data.
- **Source:** `plans/us-39/research.md`

### ADR: Split IPC namespaces — `market-data:*` vs `broker:*`

- **Decision:** New `broker:*` IPC channels (`broker:account-info`, `broker:market-status`, `broker:activities`) route to `AlpacaBrokerProvider`; existing `market-data:*` channels route to `MassiveMarketDataProvider`. The old combined `AlpacaMarketDataProvider` handled both; now each namespace has its own handler file and provider.
- **Why:** The broker/market-data split is a core architectural requirement of US-39. Mixing channels in one namespace makes the split invisible at the IPC layer.
- **Source:** `plans/us-39/research.md`, `plans/us-39/contracts/ipc-channels.md`

### ADR: `market-data:option-snapshots` (plural bulk) replaced by singular + chain

- **Decision:** The US-33 `market-data:option-snapshots` channel (bulk array of OCC symbols) is renamed/replaced: single-contract lookup becomes `market-data:option-snapshot` (singular), and paginated filtered chain lookup becomes `market-data:option-chain`.
- **Why:** The old bulk endpoint forced callers to batch OCC symbols themselves and didn't support filter-based discovery. The new shapes match Massive's actual API surface.
- **Source:** `plans/us-39/area7-green-phase-results.md`, `plans/us-39/contracts/ipc-channels.md`

### ADR: `market-data:stock-quotes` replaces `market-data:stock-quote` (singular push) for REST

- **Decision:** The polling-based REST endpoint for stock quotes is `market-data:stock-quotes` (plural, request/response). The push event `market-data:stock-quote` (singular) is retained for streaming ticks.
- **Why:** Consistent naming: plural = batch REST invoke, singular = per-tick push event.
- **Source:** `plans/us-39/contracts/ipc-channels.md`

## Contracts

### `market-data:stock-quotes`

- **Type:** IPC handler (request/response)
- **Shape:**
  ```ts
  // Request
  { tickers: string[] }
  // Response
  { ok: true; quotes: Record<string, StockQuote> }
  | { ok: false; errors: string[] }
  ```
- **Source:** `plans/us-39/contracts/ipc-channels.md`
- **Implementation:** `src/main/ipc/market-data.ts`

### `market-data:option-snapshot`

- **Type:** IPC handler (request/response)
- **Shape:**
  ```ts
  // Request
  { underlying: string; contract: string }  // contract is OCC format regex-validated
  // Response
  { ok: true; snapshot: OptionSnapshot | null }
  | { ok: false; errors: string[] }
  ```
- **Source:** `plans/us-39/contracts/ipc-channels.md`
- **Implementation:** `src/main/ipc/market-data.ts`

### `market-data:option-chain`

- **Type:** IPC handler (request/response)
- **Shape:**
  ```ts
  // Request
  {
    underlying: string;
    expirationFrom?: string;   // ISO date
    expirationTo?: string;     // ISO date
    type?: 'call' | 'put';
    strikeFrom?: number;
    strikeTo?: number;
    limit?: number;
    cursor?: string;
  }
  // Response
  { ok: true; snapshots: OptionSnapshot[]; nextCursor: null }
  | { ok: false; errors: string[] }
  ```
- **Note:** `nextCursor` is always `null` in the current implementation; real pagination deferred.
- **Source:** `plans/us-39/contracts/ipc-channels.md`
- **Implementation:** `src/main/ipc/market-data.ts`

### New `broker:*` IPC channels

- **Type:** IPC handlers (request/response)
- **Channels introduced:** `broker:account-info`, `broker:market-status`, `broker:activities`
- **Purpose:** Replaces the broker methods that were previously mixed into `AlpacaMarketDataProvider`. Now routed to `AlpacaBrokerProvider` via `src/main/ipc/broker.ts`.
- **Source:** `plans/us-39/contracts/ipc-channels.md`
- **Implementation:** `src/main/ipc/broker.ts`

### `BrokerProvider` interface

- **Type:** TypeScript interface (not an IPC channel)
- **Shape:** `getAccountInfo()`, `getMarketStatus()`, `getActivities(filter)` — mirrors the broker methods that were on the old combined interface.
- **Source:** `plans/us-39/data-model.md`
- **Implementation:** `src/main/integrations/broker-provider.ts`

## Schema Changes

None recorded. US-39 introduces no database migrations, no new tables, and no new columns. All changes are TypeScript interfaces and integration layer code.

## Acceptance Criteria

- **AC-1:** `getStockQuotes(tickers)` returns NBBO for each ticker; `mid = (bid + ask) / 2` rounded HALF_UP to 2 dp.
- **AC-2:** `getOptionSnapshot(underlying, contract)` returns a full snapshot including Greeks when the Massive response includes them.
- **AC-3:** `getOptionSnapshot` omits `greeks` and `impliedVolatility` when the Massive response omits them — no fabricated zeros.
- **AC-4:** `getOptionChainSnapshot(underlying, filters)` returns filtered and paginated option snapshots matching the supplied filters.
- **AC-5:** The Massive API key is loaded once per process and reused across all requests.
- **AC-6:** A missing or empty API key surfaces `MarketDataError` with `code: 'auth_failed'`.
- **AC-7:** A Massive 429 response triggers retry with exponential backoff (2 retries max).
- **AC-8:** A Massive 401 or 403 response surfaces `MarketDataError` with `code: 'auth_failed'`.
- **AC-9:** `supportsStreaming('stockQuotes')` and `supportsStreaming('optionQuotes')` return `true`; `stream()` throws `MarketDataError` with `code: 'streaming_unsupported'`.

## Decisions & Tradeoffs

- **REST-first, streaming deferred.** Polling meets Phase 2 needs; Massive WebSocket auth is a separate concern. The interface declares streaming capability to avoid future breaking changes.
- **Option chain pagination deferred.** `nextCursor` is always `null` in the initial implementation. Real cursor-based pagination requires a follow-up story when the option screener (Epic 3) needs it.
- **Optional Greeks is a breaking change for renderers.** Any renderer code reading `snapshot.greeks.delta` must be updated to `snapshot.greeks?.delta`. The Greeks panel (US-34) renders `—` when `greeks` is `undefined`.
- **`market-data:option-snapshots` (plural bulk) removed.** Callers in US-33 that used the old bulk endpoint must migrate to `market-data:option-snapshot` (singular per-contract lookup) or `market-data:option-chain` (filtered chain).
- **Error code taxonomy cleaned up.** `MarketDataError` no longer includes `options_no_subscription` (Alpaca-specific). `BrokerError` gains `environment_mismatch` for paper/live credential mismatch detection.
