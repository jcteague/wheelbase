# Extract: us-67

## Summary

US-67 makes the screener's criteria — delta band, DTE window, liquidity gates, price ceiling,
IV-rank floor, and earnings policy — editable from a right-hand sheet on the Screener page itself,
persisted as one JSON document in `app_settings` and read by the scoring engine on every screen.
Before this plan `screenWatchlistCandidates` always fell back to `DEFAULT_SCREENING_CRITERIA`
because nothing ever supplied `opts.criteria`, and the engine had no IV-rank floor at all; both
gaps are closed here. Criteria editing lives on the Screener rather than in Settings because tuning
a filter is an act of reading results, and saving re-screens the table underneath. Settings never
gains a screening-criteria section.

## Architecture Decisions

### ADR: Screening criteria persist as one JSON document in `app_settings`, not nine scalar rows

- **Decision:** Store the whole criteria object under a single `app_settings` key,
  `screening_criteria`, holding a JSON document. Read it back through a Zod schema whose every field
  carries `.default()` from `DEFAULT_SCREENING_CRITERIA`, so a missing key, a corrupt value, or a
  document written before a field existed all resolve to the shipped default rather than `undefined`.
- **Why:** `appSettings.set` writes one key per call and is not wrapped in a transaction, so nine
  sequential writes can half-apply — leaving the screener running a delta band from one save and a
  DTE window from another, which is worse than either save losing entirely. The criteria are a single
  cohesive object: they always travel together, are validated by one Zod schema on both sides of IPC,
  and are handed to the engine as one value.
- **Alternatives considered:** One key per field, mirroring `alert-defaults.ts` — rejected for the
  partial-write hazard. A dedicated table with typed columns — rejected as needless ceremony and a
  migration for a single always-one-row record.
- **Source:** `plans/us-67/research.md`

### ADR: The IV-rank floor is a hard filter that never excludes an unknown IV rank

- **Decision:** Add `minIvRank: string | null` to `ScreeningCriteria` (`null` = disabled, the shipped
  default) and an `iv_rank_floor` entry to the `FILTERS` registry, placed immediately after
  `price_ceiling` in the ticker-level group. Its `applies` predicate requires **both**
  `criteria.minIvRank !== null` **and** `ctx.ivRank !== null`.
- **Why:** The AC is exclusion behaviour, so it belongs in the ordered registry, not the scorer.
  Letting an unknown IVR fail a floor it was never measured against would contradict the standing
  US-65 criterion "Missing IV rank does not exclude a candidate" and would silently empty results
  whenever the scrape lags.
- **Alternatives considered:** Treating unknown IVR as failing the floor — rejected; it converts a
  data gap into a trading verdict. Scoring IV rank into `yieldPerDelta` instead of filtering —
  rejected; the AC says candidates "drop out". Placing the filter after `delta_band` — rejected; the
  registry is ordered whole-ticker disqualifiers first.
- **Source:** `plans/us-67/research.md`

### ADR: The screener service resolves persisted criteria; the IPC handler stays payload-free

- **Decision:** `screenWatchlistCandidates` changes its default from
  `opts.criteria ?? DEFAULT_SCREENING_CRITERIA` to `opts.criteria ?? getScreeningCriteria(db)`.
  `screener:results` keeps its no-payload signature and one-line handler body.
- **Why:** The thin-IPC-handler rule forbids reading settings and branching inside a handler file.
  Resolving inside the service means every caller — the handler today, a scheduled refresh or the
  US-68 promote pre-fill tomorrow — gets the trader's criteria automatically.
- **Alternatives considered:** The handler fetching and passing criteria — rejected as business logic
  in the handler. A `criteria` field on the `screener:results` request — rejected; it makes the
  renderer the authority on what the engine screens with.
- **Source:** `plans/us-67/research.md`

### ADR: `maxSpreadAbsolute` is persisted but not editable, and is omitted from the save payload

- **Decision:** The save payload is `Omit<ScreeningCriteria, 'maxSpreadAbsolute'>`. The service
  composes the stored document by taking `maxSpreadAbsolute` from `DEFAULT_SCREENING_CRITERIA`. The
  read path returns the full `ScreeningCriteria`.
- **Why:** The mockup exposes no input for it — it appears only as caption text on the Max bid-ask
  spread field. A payload field with no control is a field the renderer must invent a value for.
- **Alternatives considered:** Round-tripping it as a hidden form value — rejected; a renderer bug
  could write a spread tolerance the trader never chose and cannot see. Adding an input — rejected as
  out of scope.
- **Source:** `plans/us-67/research.md`

### ADR: Earnings handling is persisted here and applied in US-70

- **Decision:** US-67 ships the Exclude / Flag-only control and persists the enum. It does not wire
  an earnings calendar into the screener and does not render an earnings warning. The story's
  earnings AC was narrowed to persistence.
- **Why:** `src/main/services/screener.ts` passes `earningsDate: null` unconditionally, so the enum
  cannot change any outcome. Making it change one is the entirety of US-70, whose ACs already cover
  exclude, flag-with-warning, unknown-date caution, and calendar outage.
- **Alternatives considered:** Wiring `fetchNextEarningsDates` in now — viable and cheap, but it is
  US-70's job and was explicitly declined by the story owner before planning.
- **Source:** `plans/us-67/research.md`

### ADR: Save & re-screen invalidates both the criteria and the results queries

- **Decision:** The save mutation's `onSuccess` invalidates `screenerQueryKeys.criteria` **and**
  `screenerQueryKeys.results`. No criteria key is added to `settingsQueryKeys`.
- **Why:** "Saving re-screens" is the behavioural payoff of moving the form onto the Screener —
  invalidating `results` is what refreshes the table behind the sheet. Invalidating `criteria` keeps
  the summary strip and a reopened sheet showing what was actually persisted.
- **Alternatives considered:** `setQueryData` with the mutation result — rejected; `results` must be
  refetched from the provider regardless. Putting criteria under `settingsQueryKeys` — rejected; it
  would re-couple them to the surface the story is moving them off.
- **Source:** `plans/us-67/research.md`

### ADR: Renderer form bounds import from a shared pure core module

- **Decision:** New `src/main/core/screening-criteria.ts` holds every bound, message, and range
  predicate plus the two cross-field predicates. It is imported by `src/main/schemas.ts` (IPC
  validation), `src/main/services/screening-criteria.ts` (persistence), and
  `src/renderer/src/schemas/screening-criteria.ts` (form validation).
- **Why:** The established shape — `src/main/core/alert-thresholds.ts` is imported by exactly those
  three layers. Every AC message string is pinned verbatim by an e2e test, so a second copy in the
  renderer is guaranteed future drift.
- **Alternatives considered:** Duplicating bounds in the renderer schema — rejected for the drift.
  Deriving the renderer schema from the IPC Zod schema — rejected; the form works in strings (an
  in-progress `"0."` must be typeable) whereas the IPC payload is validated post-parse.
- **Source:** `plans/us-67/research.md`

### ADR: The criteria sheet is a 460px `SheetPanel`, not a new overlay primitive

- **Decision:** Build `ScreeningCriteriaSheet` from the existing `SheetOverlay` / `SheetPanel` /
  `SheetHeader` / `SheetBody` / `SheetFooter`, portalled via `getSheetPortal()`, passing `width={460}`.
- **Why:** `SheetPanel` already takes a `width` prop defaulting to 400, and `SheetOverlay` is already
  `left-[200px]`, which satisfies "the sidebar navigation remains visible and clickable" for free —
  the same reason four existing sheets sit on it.
- **Alternatives considered:** A bespoke wider overlay — rejected; it would re-derive the sidebar
  inset and scrim-dismiss behaviour the shared primitive already gets right.
- **Source:** `plans/us-67/research.md`

### ADR: Cross-field band rules live in the service, not in the Zod payload schema

- **Decision:** The delta-band and DTE-window inversion rules are raised by `saveScreeningCriteria`
  as `ValidationError('deltaMax' | 'dteMax', 'inverted_band', …)` rather than by a `.superRefine` on
  `SaveScreeningCriteriaPayloadSchema`.
- **Why:** Zod v4 restricts `ctx.addIssue({ code })` to its own issue codes, and `handleIpcCall` maps
  a Zod issue's `code` verbatim — so a `.superRefine` could only ever reach the renderer as
  `code: 'custom'`, while the contract pins `inverted_band`. The service path already produces the
  exact triple the contract tabulates.
- **Alternatives considered:** Teaching `handleIpcCall` to prefer `issue.params.code` — rejected; it
  changes shared IPC infrastructure used by every other channel.
- **Source:** discovered during implementation; recorded in `plans/us-67/contracts/screener-save-criteria.md`
  and in the comment on `SaveScreeningCriteriaPayloadSchema`.

### ADR: An IV rank is displayed with the day it was observed

- **Decision:** Both surfaces that show an IV rank stamp its observation date in `MMM d` form — the
  screener's IVR column (`44 (Aug 7)`, via `fmtIvr`) and the `iv_rank_floor` exclusion reason
  (`IV rank 22.0 (Aug 7) below 30`, via the engine's `formatObservedOn`).
- **Why:** `IvRank` has always carried `observedAt` precisely so a caller could judge whether a
  reading is still worth acting on, but nothing displayed it — acceptable while IV rank was a
  display-only ranking input, not once US-67 made it a hard filter. `getLatestIvrByUnderlying`
  applies no recency bound, so a months-old snapshot could silently drop a candidate. Showing the
  date makes the age visible without enforcing a threshold the story never defined.
- **Alternatives considered:** A hover tooltip — rejected; a staleness signal that is invisible until
  hovered, and invisible to keyboard users. Tinting the date gold past a staleness cutoff — rejected;
  it invents a threshold, and a wrong one would silently re-filter results. Formatting the date once
  in a shared module — rejected; the engine's reason string and the renderer's column are different
  strings that merely happen to agree, and the two live either side of the process boundary.
- **Source:** raised as a product question during implementation review; resolved by the story owner.

### ADR: Bound predicates fail closed against `decimal.js`

- **Decision:** `parseNumeric` matches strings against a strict decimal pattern rather than trimming
  or normalising them, establishing the invariant *if a predicate returns true, `new Decimal(value)`
  cannot throw*. Values like `' 0.20'`, `'1e2'`, and `'0x10'` are rejected outright.
- **Why:** Every downstream consumer — the engine's filters and the criteria-strip formatters — hands
  these values straight to `decimal.js`, which is stricter than `Number` and throws on padded input.
  A padded value that passed `Number` could be persisted, then blank the Screener page on render
  (there is no React error boundary in the renderer) and degrade every ticker to `data_unavailable`.
  Rejecting rather than normalising means nothing the trader did not type reaches the database.
- **Alternatives considered:** Trimming in `parseNumeric` — rejected; it persists a value the trader
  did not type. Normalising only in `toPayload` — rejected; it leaves the direct-IPC path open.
- **Source:** discovered during implementation review.

## Contracts

### screener:get-criteria

- **Type:** IPC handler
- **Shape:**

```typescript
// Request: no payload — matching `screener:results`.
// Response:
{
  ok: true
  criteria: {
    deltaMin: string
    deltaMax: string
    dteMin: number
    dteMax: number
    minOpenInterest: number
    maxSpreadPercent: string
    maxSpreadAbsolute: string // read-only, no input in the sheet
    maxUnderlyingPrice: string | null // null = ceiling disabled
    minIvRank: string | null // null = floor disabled
    earningsHandling: 'exclude' | 'flag'
  }
}
```

Never absent and never partial: an unsaved, missing, or corrupt row resolves to
`DEFAULT_SCREENING_CRITERIA`. Only `__root__` / `internal_error` is a realistic error row.

- **Source:** `plans/us-67/contracts/screener-get-criteria.md`
- **Implementation:** `src/main/ipc/screener.ts`

### screener:save-criteria

- **Type:** IPC handler
- **Shape:**

```typescript
// Request — SaveScreeningCriteriaPayloadSchema in src/main/schemas.ts.
// Omits maxSpreadAbsolute; the service supplies it from DEFAULT_SCREENING_CRITERIA.
{
  deltaMin: string // '0.01'–'0.99'
  deltaMax: string // '0.01'–'0.99', strictly greater than deltaMin
  dteMin: number // integer 1–365
  dteMax: number // integer 1–365, strictly greater than dteMin
  minOpenInterest: number // integer >= 0
  maxSpreadPercent: string // '1'–'50'
  maxUnderlyingPrice: string | null // null = ceiling disabled; when set, > 0
  minIvRank: string | null // null = floor disabled; when set, '0'–'100'
  earningsHandling: 'exclude' | 'flag'
}
// Response: { ok: true, criteria: ScreeningCriteria } — the full stored document.
```

Error rows (every message pinned verbatim by an e2e test):

| field                | code            | message                                         |
| -------------------- | --------------- | ----------------------------------------------- |
| `deltaMin`           | `out_of_range`  | `Delta must be between 0.01 and 0.99`           |
| `deltaMax`           | `out_of_range`  | `Delta must be between 0.01 and 0.99`           |
| `deltaMax`           | `inverted_band` | `Minimum delta must be less than maximum delta` |
| `dteMin`             | `out_of_range`  | `DTE must be at least 1`                        |
| `dteMax`             | `out_of_range`  | `DTE must be at most 365`                       |
| `dteMax`             | `inverted_band` | `Minimum DTE must be less than maximum DTE`     |
| `minOpenInterest`    | `out_of_range`  | `Open interest floor cannot be negative`        |
| `maxSpreadPercent`   | `out_of_range`  | `Max spread must be between 1% and 50%`         |
| `maxUnderlyingPrice` | `out_of_range`  | `Price ceiling must be greater than zero`       |
| `minIvRank`          | `out_of_range`  | `IV rank floor must be between 0 and 100`       |
| `__root__`           | `internal_error`| `An unexpected error occurred`                  |

A rejected payload persists nothing — validation runs before the single `appSettings.set`. Per-field
bounds are enforced at both the Zod boundary and in the service; because Zod parses first, a
bound caught at the boundary reaches the renderer as `code: 'custom'` rather than `out_of_range`.
The two `inverted_band` rows are service-only and always carry that exact code. `field` and
`message` are identical on both paths, and the sheet binds errors by `field`.

- **Source:** `plans/us-67/contracts/screener-save-criteria.md`
- **Implementation:** `src/main/ipc/screener.ts`, `src/main/schemas.ts`, `src/main/services/screening-criteria.ts`

## Acceptance Criteria

- Open the criteria sheet from the page header — every field pre-filled, sidebar still clickable
- Open the criteria sheet from the criteria summary strip
- Open the criteria sheet from the empty state, without navigating away
- Save new screening criteria and re-screen — persisted, sheet closes, results refresh, page shows
  "Screening criteria saved", strip updates
- Saved criteria survive a restart
- Toggle earnings handling between exclude and flag (persistence only; behaviour is US-70)
- Reject an inverted delta band — "Minimum delta must be less than maximum delta", save disabled
- Reject an inverted DTE window — "Minimum DTE must be less than maximum DTE", save disabled
- Reject out-of-range criteria — max delta `1.5`, minimum DTE `0`, minimum open interest `-100`, max
  spread `0`; nothing saved and the results behind the sheet unchanged
- IV-rank floor is optional and off by default; enabling it at 30 drops candidates below IVR 30
- Price ceiling is optional and off by default; enabling it at $75 drops underlyings above $75
- Dismissing the sheet (Cancel, close button, or scrim) discards unsaved edits
- Reset to defaults returns every field to its shipped default without persisting
- Settings does not own screening criteria — no section there, alert defaults and broker credentials
  unchanged

## Decisions & Tradeoffs

- **The read path falls back wholesale, never field-by-field.** A half-defaulted band is not a band
  the trader ever chose. Beyond the documented four steps, both bands are re-checked with
  `isAscending` after a successful parse, because per-field `.default()`s are applied independently —
  a document holding one end of a band and missing the other would otherwise parse cleanly into an
  inverted band the write path would have rejected.
- **`maxSpreadAbsolute` carries a bound check despite being uneditable**, because a stored value
  reaches the engine's `Decimal` comparison unguarded.
- **Dismissal discards silently**, consistent with every existing sheet. The form mounts inside the
  `open` check, so the unmount *is* the discard mechanism — no `reset` call to forget.
- **A save failure always produces visible feedback.** Known field errors bind inline via `setError`;
  anything unbindable (`__root__`, `earningsHandling`, a malformed envelope) routes to a root
  `ErrorAlert`, with a generic message when the detail list is empty. The sheet stays open.
- **The criteria query distinguishes four states, not two.** TanStack keeps the last successful
  `data` when a later fetch fails and the client refetches on window focus, so the entry points are
  gated on `isError && criteria === undefined` — the one state where there is nothing to open and
  nothing on the way. A click made while merely *pending* is honoured once the criteria land.
- **Registry order is load-bearing.** `FilterFailure.index` records how far a strike got through the
  funnel and `representativeExclusion` picks `excluded[0]`, so `iv_rank_floor` must stay immediately
  after `price_ceiling`.
- **The e2e suite needed two new fixtures** to keep assertions non-vacuous: `PEP_PUT` at IVR 22 (the
  only fixture below a 30 floor) and `SBUX_PUT`, so that the "save and re-screen" AC proves the
  ranked set changes in both directions rather than merely emptying.

## Open Questions

None recorded in the plan. The one genuinely ambiguous item — how much earnings behaviour US-67 owns
— was raised before planning and resolved by the story owner: all of it moves to US-70, and the story
file was updated to match.

Carried forward from implementation review, for the product owner rather than the code:

- **Stale IV rank can still remove candidates, but now says so.** `getLatestIvrByUnderlying`
  applies no recency bound and returns the newest row of any age, which was harmless while IVR
  was display-only. With the floor enabled it is a hard filter. The reading's observation date is
  now surfaced in both places IVR appears — the screener's IVR column
  (`44 (Aug 7)`) and the `iv_rank_floor` exclusion reason
  (`IV rank 22.0 (Aug 7) below 30`) — so a candidate dropped on a months-old snapshot is visibly
  dropped on a months-old snapshot. No recency *threshold* is enforced: the trader judges the age,
  since the story defines no staleness bound and inventing one would silently re-filter results.
- **"Reset to defaults" is hidden while the form is invalid**, per the mockup — which is exactly when
  a one-click return to a known-good state would be most useful.
