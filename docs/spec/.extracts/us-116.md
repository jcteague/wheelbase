# Extract: us-116

## Summary

Moves `getMarketStatus()` and `getMarketCalendar(range)` — with the `MarketStatus`,
`MarketCalendarDay` and `MarketCalendarRange` types — from `BrokerProvider` to
`MarketDataProvider`. `BrokerProvider` becomes exactly `getAccountInfo` + `getActivities`.
`AlpacaMarketDataProvider` answers both from `ALPACA_TRADING_BASE_URLS[environment]` using the
`apiFetch` path it already uses for open interest, so there is no new credential, no new vendor
and no new dependency.

Neither capability is a fact about the trader's account. "Which days were exchange sessions" and
"is the exchange open right now" are facts about the **market**; they sat behind the broker only
because Alpaca serves them from its trading host. That sourcing accident leaked into the domain
boundary with a consequence nobody intended: IV rank is scraped from Barchart with no credentials
at all, yet the whole IV column was dead on any install without a broker, because the calendar
that ages a reading could not be fetched. The market-status pill was dead for the same reason.

Two behavioural changes ride along. `refreshTradingCalendar` previously had exactly one caller —
`collectIVRSnapshots`, fired by the `afterClose + 60min` job — so on a fresh install
`trading_session` stayed empty and no reading could be aged until that job first ran. A new
`ensureTradingCalendar` is now **awaited** by `buildWatchlistSnapshot` and
`screenWatchlistCandidates` before either reads the calendar. And the market-status pill gates on
`CredentialStatus.marketData === 'configured'` instead of `activeBrokerEnv !== 'none'`.

Observed 2026-09-13 (a Sunday), Alpaca paper credentials saved, chains pulling normally:
`trading_session` 0 rows, `ivr_snapshot` 0 rows, and `"Trading calendar has never been fetched;
IVR freshness is unavailable"` firing on every `watchlist_snapshot_built`. (Source: Linear OPT-8;
`plans/us-116/plan.md` "Summary"; `plans/us-116/research.md`.)

## Architecture Decisions

### ADR: Both market facts move to `MarketDataProvider`

- **Decision:** `getMarketStatus()` and `getMarketCalendar(range)` move from `BrokerProvider` to
  `MarketDataProvider`, together with the `MarketStatus`, `MarketCalendarDay` and
  `MarketCalendarRange` types, which relocate from `integrations/broker-provider.ts` to
  `integrations/market-data-provider.ts`. `BrokerProvider` becomes exactly `getAccountInfo` +
  `getActivities`. `BrokerErrorCode` keeps `'environment_mismatch'` — `getAccountInfo` still
  produces it.
- **Why:** Neither is a fact about the trader's account; both are facts about the market. This is
  the rule recorded in `CLAUDE.md`: the broker is optional, one capability, one port. The
  interface is defined by what the consumer needs, not by which host answers. Moving only the
  calendar would fix IV rank and leave the pill gated on a broker — the same defect in a second
  place.
- **Alternatives considered:** Keep the calendar on `BrokerProvider` and have the market-data
  provider delegate — preserves the wrong boundary while adding indirection. A third
  `MarketCalendarProvider` port — a port per method, with no consumer that wants them separately.
- **Source:** `plans/us-116/research.md`

### ADR: Alpaca serves clock and calendar as a fourth upstream behind the same port

- **Decision:** `AlpacaMarketDataProvider` answers both from `ALPACA_TRADING_BASE_URLS[environment]`
  through its existing `apiFetch`. New pure helpers in `alpaca-market-data-mappers.ts`:
  `buildClockUrl(environment)`, `buildCalendarUrl(environment, range)`, `mapClock(raw)`,
  `mapCalendarDays(raw)`. `deriveSession` and `parseOffsetMinutes` move there verbatim from
  `alpaca-broker.ts` with the five session-hour constants.
- **Why:** The provider already authenticates against that host for open interest, and
  `alpaca-hosts.ts` already documents the sharing. Errors become `MarketDataError` with the codes
  `apiFetch` already produces, which every other market-data consumer already handles.
- **Alternatives considered:** Use the `@alpacahq/typescript-sdk` client the broker uses — a
  second HTTP stack inside the market-data provider, bypassing its retry/429 handling. Keep
  `environment_mismatch` classification — a credential-setup diagnosis belonging to the settings
  connection test, which has its own copy.
- **Source:** `plans/us-116/research.md`

### ADR: The bench refreshes the calendar; the read stays synchronous

- **Decision:** `ensureTradingCalendar(db, getProvider, now)` in `trading-calendar-store.ts` is
  **awaited** by both `buildWatchlistSnapshot` and `screenWatchlistCandidates` before they call
  `readTradingCalendar`. It resolves the provider inside its own `try` (an unconfigured provider
  is a logged skip), delegates to `refreshTradingCalendar`, and holds a module-level in-flight
  promise so the bench's two concurrent IPC calls share one fetch. `readTradingCalendar` stays
  pure, synchronous and DB-only.
- **Why:** US-98's "read never fetches" ADR is about `readTradingCalendar`, and it is preserved —
  the fetch moves into the service orchestration that already awaits quotes and earnings. Awaiting
  rather than firing-and-forgetting is what makes AC 1 true on *that* page open; a fire-and-forget
  refresh shows `n/a` for one render. The await is free in steady state: `refreshTradingCalendar`
  self-throttles behind a single `MIN/MAX` query and returns `{ status: 'skipped' }` without
  touching the network, and it swallows every failure into `{ status: 'failed' }`, so it can
  neither block nor break the bench.
- **Consequence to hold:** the "never rejects" guarantee is load-bearing, not a courtesy — both
  callers await it inside a `Promise.all`, so a rejection would sink the bench, which is the exact
  failure AC 5 and AC 6 exist to prevent. It holds because `refreshTradingCalendar` wraps its whole
  body in a catch; only the `getProvider()` call, outside that, is guarded in
  `ensureTradingCalendar`. The in-flight promise caches the *fetch*, not the *result*, so a later
  open retries a refresh that failed.
- **Alternatives considered:** Fire-and-forget (the story's suggestion) — fails AC 1 on the first
  open. A `market-data:refresh-calendar` IPC the renderer calls — orchestration in the renderer,
  plus a round trip. Refresh in `watchlist-snapshot` only — leaves the screener reading an empty
  cache on first paint, since the bench issues both queries concurrently. Keep the nightly job as
  the only writer — that is the bug.
- **Source:** `plans/us-116/research.md`

### ADR: Unconfigured market data parks scheduled jobs

- **Decision:** `createPollingScheduler` takes `getStatusSource: () => MarketStatusSource`, where
  `MarketStatusSource = Pick<MarketDataProvider, 'getMarketStatus'>`. `scheduler-instance.ts`
  supplies `marketDataFactory.create()` wrapped so a `MarketDataError` with code `auth_failed`
  degrades to a synthetic `closed` status, logged at `debug`; every other error propagates to the
  scheduler's existing "fall back to default cadence" branch. `fallbackBroker`, `getSafeBroker`
  and the `brokerFactory` import are deleted.
- **Why:** Dropping the stub outright would make interval jobs re-tick every 60s against a
  provider that throws immediately, with a `warn` per tick. Narrowing the parameter to the one
  method the scheduler uses also stops `polling-scheduler.ts` importing a port that can stream
  quotes.
- **Alternatives considered:** Pass the whole `MarketDataProvider` — a wider seam than the job
  needs. Treat every status failure as `closed` — a transient blip would park a job until an
  unknown `nextOpen`.
- **Supersedes:** the `scheduler-singleton-safe-broker` ADR.
- **Known limitation (pre-existing, carried over from `fallbackBroker`):** the synthetic status
  carries a `nextOpen` stamped at module load, so it is always in the past. `decideNextCadenceMs`
  returns `null` for a `marketClosedMs: null` job, but `parkUntilNextOpen` then sees a
  non-positive delay and takes its fallback branch — a `warn` plus a re-tick at `marketOpenMs`.
  An unconfigured install therefore re-ticks rather than parking. Not addressed by this story.
- **Source:** `plans/us-116/research.md`

### ADR: `broker:market-status` is renamed, not re-pointed

- **Decision:** The channel becomes `market-data:market-status`, registered in
  `ipc/market-data.ts`. `preload`'s `broker.marketStatus` moves to `marketData.marketStatus`. In
  the renderer, `getMarketStatus` and the `MarketStatus` type move from `api/broker.ts` to
  `api/market-data.ts`, and the key moves from `brokerQueryKeys.marketStatus` to
  `marketDataQueryKeys.marketStatus = ['market', 'status']`.
- **Why:** The existing `ipc-channel-naming` and `vendor-scoped-query-keys` ADRs both key off the
  namespace. Leaving a market fact on a `broker:` channel re-creates the confusion this story
  removes.
- **Consequence handled:** `useSettings.ts`'s invalidation predicate matched only
  `queryKey[0] === 'broker'`. With the status key now `['market', …]`, saving credentials would
  have silently stopped refreshing the pill. `hasBrokerQueryKey` becomes `hasVendorQueryKey`,
  matching `'broker'` or `'market'` — which correctly also refreshes quotes and snapshots after a
  credential change.
- **Alternatives considered:** Keep the channel name and swap the service behind it — cheapest
  diff, but the name would then lie permanently.
- **Source:** `plans/us-116/research.md`

### ADR: The pill gates on market-data credentials

- **Decision:** `useMarketStatusDisplay` gates on `settingsQuery.data?.marketData === 'configured'`
  and renames `hasBroker` → `hasMarketData`.
- **Why:** `CredentialStatus.marketData` is already computed for exactly this question
  (`settings.ts:168`). The pill asks "can we reach the market-data provider", not "is a broker
  attached".
- **Consequence:** the old predicate `data?.activeBrokerEnv !== 'none'` was `true` while
  `settingsQuery.data` was still `undefined`, so it fired one status request during settings load
  whose result TanStack Query then cached indefinitely. The new predicate is correctly `false`
  until credentials are known, so an install with no credentials never issues the request and the
  pill falls back to `computeNYSESession()` — which is what `deriveMarketStatusDisplay` was always
  written to do.
- **Alternatives considered:** Always enable the query and let the error state drive `DELAYED` —
  spends a failing IPC round trip every 60s on an unconfigured install.
- **Source:** `plans/us-116/research.md`

### ADR: The fake seams move with the capabilities

- **Decision:** `FakeMarketDataProvider` gains `getMarketStatus` (from `FAKE_MARKET_STATUS`) and
  `getMarketCalendar` (from `FAKE_MARKET_CALENDAR`, defaulting to generated weekday sessions);
  `FakeBrokerProvider` loses both, along with `DEFAULT_MARKET_STATUS`, `weekdaySessions` and its
  `date-fns` import. The e2e env var `FAKE_BROKER_CALENDAR` is renamed `FAKE_MARKET_CALENDAR` and
  `IvrLaunchOpts.brokerCalendar` becomes `marketCalendar`. `FAKE_MARKET_STATUS` keeps its name —
  already vendor-neutral. A dedicated `FAKE_MARKET_CALENDAR_ERROR` fails **only**
  `getMarketCalendar`.
- **Why:** `FAKE_BROKER_ERROR` must stop being able to break market status and the calendar; after
  the move `FAKE_MARKET_DATA_ERROR` is the correct injection point. But that seam is global to the
  fake, and AC 5 / AC 6 need the calendar to fail *while quotes and chains serve normally* — which
  only a calendar-scoped variable can express without racing a global toggle.
- **Source:** `plans/us-116/research.md`; `plans/us-116/plan.md` area 11

### ADR: "No broker, yes market data" is expressed through the env-fallback credentials

- **Decision:** An e2e launch option `marketDataWithoutBroker: true` drops
  `WHEELBASE_PRESEED_ACTIVE_ENV` (so `activeBrokerEnv` reads `'none'`) while setting non-empty
  `ALPACA_KEY_ID` / `ALPACA_SECRET_KEY` (so `hasFallbackCredentials()` is true and `marketData`
  reads `'configured'`). The existing `withoutBrokerCredentials` option is left alone.
- **Why:** This is the only state the current credential model can express for the story's
  Background, and it is a real state — the documented dev/CI path in `.env.example`. Changing
  `withoutBrokerCredentials` in place would silently re-point the specs that use it to assert a
  "market data missing" app.
- **Alternatives considered:** Split saved credentials into separate broker and market-data
  records — a settings-model change well outside this story.
- **Source:** `plans/us-116/research.md`

## Contracts

### `market-data:market-status` (new — replaces `broker:market-status`)

- **Type:** IPC channel
- **Request:** no payload. Invoked as `window.api.marketData.marketStatus()`.
- **Response:** `{ ok: true, status: { isOpen: boolean, nextOpen: string, nextClose: string,
  session: 'regular' | 'pre' | 'post' | 'closed' } }`
- **Errors:** no story-specific validation — there is no payload. Every failure arrives as a
  `MarketDataError` translated by `handleIpcCall` into `{ ok: false, errors: [{ field: '__root__',
  code, message }] }`: `auth_failed` (`Alpaca credentials not configured`, or `HTTP 401`/`403`),
  `network_error`, `rate_limited`, and `internal_error` for an unhandled error logged as
  `market_data_market_status_unhandled_error`.
- **Handler:** `src/main/ipc/market-data.ts` — one `handleIpcCall` around a single
  `getProvider().getMarketStatus()`; no service, no Zod schema, thin per the IPC rule.
- **Preload:** `marketData.marketStatus()`; typed as `IpcGetMarketStatusResult` in
  `src/preload/index.d.ts`.
- **Renderer:** `src/renderer/src/api/market-data.ts` → `getMarketStatus()`, keyed
  `marketDataQueryKeys.marketStatus`.
- **Source:** `plans/us-116/contracts/market-data-market-status.md`

| -- | -- |

### Alpaca upstream shapes

Both on `ALPACA_TRADING_BASE_URLS[environment]`, authenticated with the same
`APCA-API-KEY-ID` / `APCA-API-SECRET-KEY` pair `apiFetch` already sends.

```typescript
// GET {tradingBase}/v2/clock
type AlpacaClock = { timestamp: string; is_open: boolean; next_open: string; next_close: string }

// GET {tradingBase}/v2/calendar?start=YYYY-MM-DD&end=YYYY-MM-DD
type AlpacaCalendarDay = { date: string; open: string; close: string } // `open` is not mapped
```

Mapping rules, carried over unchanged from `alpaca-broker.ts`:

- `session` is derived, not reported: `is_open` → `'regular'`; otherwise the ET hour parsed off
  `timestamp`'s own offset (falling back to `-04:00`) picks `'pre'` (04:00–09:30), `'post'`
  (16:00–20:00) or `'closed'`.
- Alpaca lists only days the exchange traded, so **absence is a closure**. `close` already
  reflects early closes, so none are derived.
- Rows whose `date` or `close` is not a string are dropped.

- **Implementation:** `src/main/integrations/alpaca-market-data-mappers.ts`
- **Source:** `plans/us-116/data-model.md` "Alpaca upstream shapes"

## Schema Changes

**None.** `trading_session` (US-98, migration `019`) is unchanged — this story changes *who
fetches it*, not what it holds. `ivr_snapshot` is untouched. No migration is written. (Source:
`plans/us-116/data-model.md`.)

Restated because the ACs turn on it: `refreshTradingCalendar` writes **every calendar day** in its
range, closures included as `close_at = NULL`, so coverage is derivable from the rows and "closed"
is never confused with "never fetched".

| Stored coverage | `readTradingCalendar` returns | IV rank renders |
| -- | -- | -- |
| no rows | `EMPTY_TRADING_CALENDAR` + `warn` "never been fetched" | `n/a` |
| rows, but none covering today | `EMPTY_TRADING_CALENDAR` + `warn` "does not cover today" | `n/a` |
| rows covering today | window clipped to stored coverage | assessed, with freshness ring |

`needsRefresh` is true when `last_day < now + (400 − 7) days` — at most weekly after a success. A
**failed** refresh leaves `needsRefresh` true, so the next bench open retries; there is no backoff
and none is added (the retry is user-paced, one per page open).

## Acceptance Criteria

Background for all eight: the trader has saved market-data credentials, no broker credentials are
saved, and the watchlist contains KO. (Source: Linear OPT-8.)

- **AC1 — IV rank is judged without a broker.** Given KO has an IV rank recorded at the previous
  close and the trading calendar has never been fetched, when the trader opens the Watchlist page,
  then the calendar is fetched from the market-data provider, the KO IV rank is shown with its
  freshness ring, and no "calendar has never been fetched" warning is logged.
- **AC2 — The market-status pill resolves without a broker.** Opening the Watchlist page shows the
  current session state; it does not show an unresolved or error state.
- **AC3 — A fresh install does not wait for the nightly collection.** Given the calendar has never
  been fetched and the scheduled IVR collection has never run, opening the Watchlist page fetches
  the calendar, and a reading collected afterwards is aged rather than read as unreadable.
- **AC4 — The calendar is not refetched on every render.** Given it was fetched today, opening the
  Watchlist page twice fetches it no more than once.
- **AC5 — A calendar failure degrades IV freshness only.** Every saved stock is still listed with
  its ticker, thesis and price; each IV rank reads "n/a"; the failure is logged at warn level; no
  error is surfaced to the trader.
- **AC6 — A calendar failure is not reported as a market-data outage.** With quotes and chains
  served normally, the bench does not show the "Market data unavailable" notice and stocks that
  meet their criteria are still listed under "Meets criteria".
- **AC7 — Assignment detection still requires a broker.** With no broker credentials, no
  assignment detection runs, and the absence of a broker is not reported as a market-data problem.
- **AC8 — Collection still refreshes the calendar on its own schedule.** Given the calendar was
  last fetched eight days ago, the scheduled IVR collection refreshes it.

E2E coverage: `e2e/market-facts-without-broker.spec.ts`, one `it()` per scenario, named in the
scenario's own language. Notes on how two of them are made load-bearing:

- **AC2** launches twice — a regular-session fixture asserting `LIVE`, then a `CLOSED_SESSION`
  fixture asserting `CLOSED`. A *disabled* status query is not visibly unresolved:
  `deriveMarketStatusDisplay` falls back to `computeNYSESession()`, the renderer's own wall clock,
  which would read `LIVE` unaided during market hours. The clock cannot be both regular and
  closed, so the pair fails at any hour if the query is not actually running.
- **AC7** seeds the same `AAPL_PUT_180` + OPASN fixture that *does* raise a pending assignment in
  `assignment-detection.spec.ts`, runs the real detect-assignments job through
  `assignments:run-detection-now`, and asserts nothing was detected while the pill still resolves.
  Deleting the `activeBrokerEnv === 'none'` guard makes it fail.
- **AC1 / AC3** need a recorded reading *and* an unfetched calendar. Only the collector can write
  a reading and it refreshes the calendar on the same run, so those tests launch with
  `FAKE_MARKET_CALENDAR_ERROR` set, let the collector persist the reading against an empty
  `trading_session` (asserted, not assumed), then clear the fault and open the bench.
- **AC5**'s warn-level clause and **AC1**'s negative-log clause are pinned by
  `trading-calendar-store.test.ts` rather than e2e — there is no main-process log seam in the e2e
  suite.

## Decisions & Tradeoffs

- **Test-only observability.** The refresh throttle lives in the store, so a bench that skipped a
  fetch looks exactly like one that made it. `FakeMarketDataProvider` counts its calendar fetches,
  and two dev-only IPC channels — `_test:trading-session-count` and
  `_test:market-calendar-fetch-count`, registered only when `NODE_ENV === 'test'` — expose that
  and the row count to specs. Without them AC 3 and AC 4 cannot be asserted at all.
- **Specs that already set `FAKE_MARKET_DATA_ERROR` now also lose the calendar.**
  `watchlist-bench.spec.ts`'s "Market data unavailable degrades verdicts, not rows" was re-worked
  to inject the outage *after* seeding rather than at launch: both the IV readings and the
  calendar are local caches an established install already holds, and a launch-time error would
  have left the tiers it asserts reporting an empty calendar rather than an outage.
- **`live-underlying-price.spec.ts` now sets explicit credentials.** Its pill assertions were
  previously satisfied by the accidental during-load fetch described in the pill-gating ADR; they
  now ride their own `FAKE_MARKET_STATUS` fixtures, which is strictly more honest.
- **`environment_mismatch` is not carried over.** Calendar and clock failures are `MarketDataError`
  with the codes `apiFetch` already maps; the environment diagnosis belongs to the settings
  connection test, which keeps its own copy.
- **The collector still calls `refreshTradingCalendar` directly**, not `ensureTradingCalendar`:
  the nightly job owns its own provider and wants no in-flight sharing with bench reads. Two
  doors into one operation, only one deduped — accepted.
- **Coverage.** Every file containing code this story wrote is at or above the project's 95%
  lines + branches bar. `alpaca-broker.ts` and `polling-scheduler.ts` fall below it on
  **pre-existing** lines: the first is a pure deletion (1 line added, 62 removed) and the second a
  pure parameter rename (8/8), and no uncovered region overlaps the diff.

## Open Questions

None blocking. Follow-ups surfaced and deliberately not taken:

1. The unconfigured-install scheduler status never actually parks (see the scheduler ADR's known
   limitation). Fixing it needs a product decision about how long an uncredentialed install should
   wait before retrying.
2. `buildWatchlistSnapshot` resolves the provider twice — once in `readQuotes`, once inside
   `ensureTradingCalendar` — and logs two "unavailable" events for one cause.
   `screenWatchlistCandidates` already resolves once and passes the value.
3. `mapClock` / `mapCalendarDays` cast `apiFetch`'s `unknown` straight to the vendor shape, so a
   malformed 200 escapes as a raw `TypeError` rather than a `MarketDataError`. Inherited in kind
   from `alpaca-broker.ts`.
4. The ensure→read→assess ordering is now written out at two call sites with a comment at each
   explaining why the await must precede the read; folding it into the IVR assessment would make
   the ordering impossible to skip.
5. `deriveSession` / `parseOffsetMinutes` are vendor-neutral ET wall-clock reasoning living in the
   Alpaca mapper; `src/main/core/trading-calendar.ts` already owns that kind of logic.
