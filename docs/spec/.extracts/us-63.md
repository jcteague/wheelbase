# Extract: us-63

## Summary

US-63 delivers the foundation of the candidate-screener watchlist: a `watchlist`
table keyed by normalized ticker, three `watchlist:list/add/remove` IPC handlers
through `handleIpcCall`, and a new Watchlist page where a trader adds a ticker
(optionally with a thesis and structured entry conditions — would-own price,
IV-rank trigger, post-earnings gate, core-holding) and removes ones they no longer
track. The list renders newest-first with the thesis note and compact condition
tags; the add form validates symbols, rejects duplicates, and normalizes to
uppercase; an empty state explains that adding tickers enables the screener. Live
price/IVR/earnings/Signal columns (US-96) and editing an entry (US-69) are out of
scope; the add form is deliberately built to be reused by US-69's edit mode.

## Architecture Decisions

### ADR: Watchlist keyed by normalized ticker (no surrogate id)

- **Decision:** `watchlist` uses `ticker TEXT PRIMARY KEY`; normalization to
  uppercase happens at the service boundary before insert/select/delete.
- **Why:** the ticker *is* the identity of a watchlist entry; a surrogate key adds
  nothing and duplicate-prevention is a natural PK constraint plus an explicit
  pre-insert existence check that yields a friendly `ValidationError`.
- **Source:** `plans/us-63/data-model.md`, `plans/us-63/plan.md`

### ADR: Structured conditions stored, but informational only

- **Decision:** conditions (`own_below_price`, `ivr_trigger`, `post_earnings_only`,
  `core_holding`) are persisted as columns but are display/Signal inputs only —
  never a screener ranking input.
- **Why:** keeps the watchlist a curated bench, not a ranking engine; the Signal
  (US-96) derives from these against live data later.
- **Source:** `plans/us-63/plan.md`, story Technical Notes

### ADR: Shared add/edit form surface

- **Decision:** `WatchlistAddForm` is the single add surface, built so US-69 can
  reuse it in edit mode (ticker fixed) without a rewrite; edit mode is NOT built here.
- **Why:** avoids a second near-identical form and folds thesis + conditions into one
  place per the mockup.
- **Source:** `plans/us-63/plan.md` (Area 8 refactor note), mockup

### ADR: RHF input/output typing for defaulted booleans

- **Decision:** the page form uses `useForm<WatchlistFormInput, unknown,
  WatchlistEntryFormValues>` (3-generic) and resets on the mutation's per-call
  `onSuccess` rather than a `useEffect`.
- **Why:** the schema's `.default(false)` booleans make the Zod input type differ
  from the output type; per-call `onSuccess` avoids the `react-hooks/set-state-in-effect`
  lint rule while preserving the hook-level cache invalidation.
- **Source:** `plans/us-63/layer-5-implementation.md`

## Contracts

### watchlist:list

- **Type:** IPC handler
- **Shape:** request none → `{ ok: true, entries: WatchlistEntryRecord[] }` (ordered
  by `added_at DESC`) | `{ ok: false, errors }`
- **Source:** `plans/us-63/contracts/watchlist-list.md`
- **Implementation:** `src/main/ipc/watchlist.ts` → `src/main/services/watchlist.ts`

### watchlist:add

- **Type:** IPC handler
- **Shape:** request `WatchlistAddPayload { ticker, notes?, ownBelowPrice?,
  ivrTrigger?, postEarningsOnly?, coreHolding? }` → `{ ok: true, entry:
  WatchlistEntryRecord }` | `{ ok: false, errors: [{ field: 'ticker', code:
  'duplicate', message: '<T> is already on the watchlist' }] }`
- **Source:** `plans/us-63/contracts/watchlist-add.md`
- **Implementation:** `src/main/ipc/watchlist.ts`, `src/main/schemas.ts`

### watchlist:remove

- **Type:** IPC handler
- **Shape:** request `{ ticker }` → `{ ok: true, ticker }` | `{ ok: false, errors }`;
  removing an absent ticker is a no-op success.
- **Source:** `plans/us-63/contracts/watchlist-remove.md`
- **Implementation:** `src/main/ipc/watchlist.ts`

### WatchlistEntryRecord

- **Type:** result interface
- **Shape:** `{ ticker: string; notes: string | null; ownBelowPrice: string | null;
  ivrTrigger: number | null; postEarningsOnly: boolean; coreHolding: boolean;
  addedAt: string }` (`ownBelowPrice` is 4dp TEXT money; booleans mapped from 0/1)
- **Source:** `plans/us-63/contracts/watchlist-add.md`, `src/main/schemas.ts`

## Acceptance Criteria

- Add a ticker to the watchlist (list shows the new count).
- A newly added ticker appears at the top of the list.
- Create an entry with a thesis and entry conditions (row shows note + tags `≤ $38`,
  `IVR ≥ 50`).
- Conditions and thesis are optional (row carries no condition tags).
- Ticker symbols are normalized to uppercase (`nvda` → `NVDA`).
- Reject a duplicate ticker → inline "AAPL is already on the watchlist"; appears once.
- Reject empty/malformed symbol → "Enter a ticker symbol" (empty) / "Enter a valid
  ticker symbol" (`12345`, `AB CD`); nothing added.
- Remove a ticker from the watchlist.
- Empty watchlist shows guidance that adding tickers enables the screener.

## Decisions & Tradeoffs

- Add form is always visible (no Add-trigger toggle) — simplest surface covering
  every AC and lets the e2e seed tickers directly.
- Condition tags are display-only in US-63 (click-to-edit is US-69).
- Symbol is NOT validated as optionable/real at add-time — that surfaces later when
  the screener pulls chains (US-64).
- `buildConditionTags` extracted as a pure helper for reuse by the page and future US-96.
- Renderer/preload boundary types (`WatchlistEntry`/`AddWatchlistPayload` vs
  `IpcWatchlistEntry`/`IpcWatchlistAddPayload`) duplicated intentionally per repo pattern.
