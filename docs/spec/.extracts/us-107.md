# Extract: us-107

## Summary

"Add a medium-urgency `PMCC_LEAPS_ROLL_WINDOW` rule that fires while a PMCC's LEAPS has
0–60 calendar days to expiration, whether or not a short call is open. Rules now declare
which leg they read, so on a LEAPS-only PMCC the short-leg rules are inapplicable rather
than skipped. PMCC selection widens from "short open" to "LEAPS open". The queue badge
becomes leg-aware (`PMCC · LEAPS` / `PMCC · short call`). Done means all 8 Linear scenario
families pass as 12 named e2e cases, with wheel output unchanged." Linear story: OPT-15 / US-107
(Linear is the authority; the plan's audit table is a test index, not a copy). Mockup:
`mockups/us-107-pmcc-leaps-dte-alert.mdx`. Builds on US-106 as merged (`18e1617`, 2026-10-23),
using its shipped names (`PMCC_ASSIGNMENT_RISK`, `priceVsStrikeMissingData`, camelCase
`EvaluableRow`, `loadPmccEvaluableRows({ db, heldIds, logger })`, `heldPositionIds` /
`AlertsToKeep.positionIds`, `PhaseBadge`'s `label` prop, the preload `ManagementQueueItem` alias).
"No migration." One additive response field on `alerts:list` (`ruleCode`). All Area 1–6 tasks are
checked off in `tasks.md`. (Source: `plans/us-107/plan.md` Summary, Prerequisites;
`plans/us-107/research.md` § Starting point; `plans/us-107/data-model.md`; `plans/us-107/tasks.md`.)

## Architecture Decisions

### ADR: Append PMCC_LEAPS_ROLL_WINDOW to the rule registry

- **Decision:** "Add `'PMCC_LEAPS_ROLL_WINDOW'` to `RuleCode`, a fixed
  `PMCC_LEAPS_ROLL_WINDOW_MAX_DTE = 60`, a missing-data reason
  `MISSING_LEAPS_DTE = 'missing_leaps_dte'`, and one `RULES` entry with `urgency: 'medium'`,
  test `0 <= leapsDte <= 60` and summary helper `pmccLeapsRollWindowSummary`. The engine
  reads two new inputs, `leapsDte: number | null` and `leapsStrike: string | null`; the
  existing `dte`/`strike`/`expiration` keep meaning the short leg."
- **Why:** "The registry already provides dedupe, refresh-in-place, resolve-on-clear,
  skip-keeps-open and dismissal; the story is one more predicate. Separate LEAPS fields
  leave every existing rule's input untouched, so no short-leg rule can read the LEAPS
  by accident. Inclusive 60 matches how every other rule fires at its named number; the
  `>= 0` lower bound mirrors EXPIRATION_IMMINENT, so an unrecorded expired LEAPS stops
  matching and resolves."
- **Alternatives considered:** "Feeding the LEAPS through `dte`/`strike` as a second
  evaluation input per position (would trip MANAGEMENT_WINDOW/EXPIRATION_IMMINENT on the
  LEAPS, which US-106 forbids). A configurable threshold or 90/60/45 escalation (out of
  scope per the story). Reusing the renderer-only `LEAPS_DECAY_WINDOW_DAYS = 90`
  (`src/renderer/src/lib/pmcc-roll-coverage.ts`) — a different window for a different
  purpose, and the core cannot import from the renderer."
- **Source:** `plans/us-107/research.md` ADR 1; `plans/us-107/data-model.md` § Rule

### ADR: Rules declare which leg they read; an absent leg makes a rule inapplicable

- **Decision:** "Add a required `leg: 'short' | 'leaps'` field to `RuleDefinition` and a
  `LEG_PRESENT: Record<RuleLeg, (input) => boolean>` table in `alerts.ts`:
  `short` → `input.instrumentType !== null`; `leaps` → `input.phase === 'PMCC_OPEN'`.
  `evaluatePosition` filters `RULES` to those whose leg is present **before** computing
  skips and matches. Every existing rule (including US-106's `PMCC_ASSIGNMENT_RISK`)
  declares `leg: 'short'`; the new rule declares `leg: 'leaps'`."
- **Why:** "This is the hazard the story calls out. A LEAPS-only PMCC has no short leg;
  if the short-leg rules ran they would skip with `missing_dte` / `missing_strike` /
  `missing_option_mark`, and the US-50 keep-open set would then hold the expired short's
  EXPIRATION_IMMINENT and US-106's PMCC_ASSIGNMENT_RISK open forever. US-106's shipped
  `priceVsStrikeMissingData('PMCC_OPEN')` is the concrete case … 'Inapplicable' must produce
  neither a match nor a skip. One table answers 'which leg does this rule read' for every rule,
  and it makes 'neither rule reads the other's leg' (S6) a property of the registry instead of a
  convention. The LEAPS presence test uses phase, not `leapsDte !== null`, because a PMCC whose
  LEAPS expiration is unreadable must **skip** (S7), not be inapplicable. Wheel positions always
  have `instrumentType` set, because the wheel query inner-joins an option leg … So no existing
  wheel outcome changes (S8)."
- **Alternatives considered:** "A per-rule `instrumentType === null` check inside each
  `missingData` guard (five copies of the same gate, easy to forget on the next rule).
  A new LEAPS-only PMCC phase (US-101 uses `PMCC_OPEN` for both states; adding a phase
  ripples into the lifecycle engine, list and detail)."
- **Type design:** required `leg` means "forgetting is a compile error, which is the guard
  against the LEAPS-only hazard reappearing on the next rule"; `LEG_PRESENT` as a `Record` is
  exhaustive — "adding a leg kind without a presence test fails to compile."
- **Source:** `plans/us-107/research.md` ADR 2; `plans/us-107/data-model.md` § Applicability,
  § Type Design

### ADR: A PMCC is evaluable whenever its LEAPS is open

- **Decision:** "In US-106's `loadPmccEvaluableRows({ db, heldIds, logger })`, replace the
  `currentShortCallLeg(legs)` call with the existing `pmccOpenLegs(legs)` from
  `src/main/services/pmcc-ledger.ts`. `null` (no LEAPS) → not evaluable; otherwise emit one
  `EvaluableRow` whose short-leg fields come from `short` (all `null` when no short is
  open, with `instrumentType: short ? 'CALL' : null`) and whose new `leapsStrike` /
  `leapsExpiration` fields come from `long`. `EvaluableRow.instrumentType` widens from
  `'PUT' | 'CALL'` to `'PUT' | 'CALL' | null`, and `occSymbolForRow` returns `null` when it
  is null (before it reaches `buildOccSymbol`). The wheel `EVALUABLE_QUERY` selects
  `NULL AS leapsStrike, NULL AS leapsExpiration`. `toEvaluationInput` adds
  `leapsDte: computeDte(row.leapsExpiration, now)` and `leapsStrike: row.leapsStrike`."
- **Why:** "`pmccOpenLegs` already replays both sides in one pass over shared roll chains
  (`currentLeapsLeg` follows LEAPS-side `ROLL_TO`, so a US-105 roll to 2028-01-21 is seen
  as 185 DTE and the alert resolves). A null short makes `occSymbolForRow` return null,
  so no option snapshot is requested for a LEAPS-only PMCC and the LEAPS OCC is never
  requested. US-106's per-candidate catch and `heldIds` keep-open set (carried to
  `resolveAlertsNotIn` / `clearStaleDismissals` as `AlertsToKeep.positionIds`) apply
  unchanged."
- **Alternatives considered:** "Extending `activeLegSubquery` as the issue's technical
  note suggests. US-106 already rejected that because the subquery also feeds
  `get-position` and `list-positions`, where PMCC `activeLeg` is deliberately null
  (pmcc-alerts-select-current-short-by-ledger-replay). A second SQL join for the LEAPS
  (duplicates replay logic and mis-handles LEAPS rolls)."
- **Source:** `plans/us-107/research.md` ADR 3; `plans/us-107/data-model.md` § Selection

### ADR: Share the today / in 1 day / in N days phrase

- **Decision:** "Extract `inDays(days: number): string` in `alerts.ts` from
  `earningsProximitySummary`; both that summary and `pmccLeapsRollWindowSummary` use it.
  The LEAPS summary is
  `` `LEAPS expires ${inDays(leapsDte)} at ${formatStrike(leapsStrike)} strike — review for roll or close` ``."
- **Why:** "Story technical note; two callers now exist. The 'LEAPS' prefix and the
  leap strike make the row distinguishable from the short call's EXPIRATION_IMMINENT row."
- **Alternatives considered:** "Reusing `expirationImminentSummary`'s `in ${dte} days`
  form (wrong at 0 and 1, which S4 at 2 days does not exercise, but the edge is real)."
- **Source:** `plans/us-107/research.md` ADR 4

### ADR: Leg-aware PMCC queue badge, carried by rule code on the queue item

- **Decision:** "Add `ruleCode: RuleCode` to `ManagementQueueItem` in `src/main/schemas.ts`,
  selected as `a.rule_code AS rule_code` in `listManagementQueue`. The preload global
  `ManagementQueueItem` is already an alias of the schema type (US-106), so it needs no
  edit. In `ManagementQueueRow`, the `label` passed to US-106's `PhaseBadge` reads
  `PMCC · LEAPS` when `item.ruleCode === 'PMCC_LEAPS_ROLL_WINDOW'` and `PMCC · short call`
  otherwise; tint, dot and the 150px column are unchanged." US-106's test "the branch follows
  phase, not rule or summary" is renamed, "since the branch now reads the rule code."
- **Why:** "User decision (2026-10-16): US-106's phase-driven badge would label the
  LEAPS row 'short call'. The queue item carries phase but not rule code, so the renderer
  cannot tell the rows apart without it. This is the one IPC response change in the story;
  the issue said 'no IPC change', but that assumed US-106's badge needed no leg."
- **Alternatives considered:** "Plain `PMCC` on every PMCC row as the US-107 mockup draws
  it (drops US-106's leg label; the short-call summaries do not name their leg). Parsing
  the summary for 'LEAPS' (brittle). Keeping US-106's label (mislabels the row)."
- **Type design note (plan):** label map `PMCC_LEG_LABEL = { short: 'PMCC · short call',
  leaps: 'PMCC · LEAPS' } as const` and `pmccBadgeLabel(ruleCode: RuleCode)` in
  `ManagementQueueRow.tsx`. "Plain types; the rule→leg decision mirrors `RULES` but the
  renderer cannot import core values. One literal compare is enough."
- **Source:** `plans/us-107/research.md` ADR 5; `plans/us-107/data-model.md` § Type Design

### ADR: The alert job's own clock; fixed dates in service tests, run-relative in e2e

- **Decision:** "Service tests pin the issue's calendar (LEAPS 2027-09-17, short
  2027-08-20, `now` at 16:00Z on each example date, `TZ=America/New_York`). Electron e2e
  seeds legs at run-day-relative dates that preserve each scenario's DTE … The unreadable-expiration
  scenario overwrites **only the LEAPS leg's** `expiration` to a non-date string via a
  new `setLegExpiration(dbPath, legId, value)` e2e helper built on the existing
  `sqlite(dbPath, sql)` from `e2e/pmcc-helpers.ts`. Do not use the existing
  `setActiveLegExpiration`, because it rewrites every leg of the position."
- **Why:** "The alert scheduler uses real `new Date()`; there is no production clock seam
  and the story adds none. `legs.expiration` is `TEXT NOT NULL`, so 'unreadable' means a
  non-ISO string, which `computeDte` already maps to `null`. A service test must first
  prove `pmccOpenLegs` / `groupRollChains` tolerate a non-date expiration. If replay
  threw, the position would take US-106's held path, which keeps the alert open but
  does not record a `missing_leaps_dte` skip, and S7 needs that skip."
- **Alternatives considered:** "A test-only clock IPC (new surface for one story)."
- **Source:** `plans/us-107/research.md` ADR 6; `plans/us-107/quickstart.md`

## Contracts

### `alerts:list`

- **Type:** IPC handler (response shape, additive field)
- **Shape:**

```typescript
{
  ok: true
  items: Array<{
    alertId: string
    positionId: string
    ticker: string
    phase: WheelPhase
    ruleCode: RuleCode // NEW (US-107) — e.g. 'PMCC_LEAPS_ROLL_WINDOW'; a.rule_code
    urgency: 'high' | 'medium' | 'low'
    summary: string
    quickAction: string
    triggeredAt: string
  }>
}
// Ordering unchanged: urgency high → medium → low, then triggered_at ASC.
```

  "`ruleCode` is additive; existing consumers ignore it. The renderer uses it only to pick
  the PMCC badge's leg label (`PMCC · LEAPS` vs `PMCC · short call`)." Errors: standard
  `handleIpcCall` envelope only (`__root__` / `internal_error`).
- **Source:** `plans/us-107/contracts/alerts-list.md`
- **Implementation:** handler `src/main/ipc/alerts.ts` (unchanged); service
  `src/main/services/alerts.ts` (`listManagementQueue`, `mapQueueRow`, `QueueRow`); type
  `src/main/schemas.ts` `ManagementQueueItem`; preload alias `src/preload/index.d.ts` (no edit)

### `PMCC_LEAPS_ROLL_WINDOW` rule (alert registry entry)

- **Type:** other (pure engine rule)
- **Shape:**

| Property | Value                                                                                                 |
| -------- | ----------------------------------------------------------------------------------------------------- |
| leg      | `leaps`, present iff `phase === 'PMCC_OPEN'`                                                          |
| urgency  | `medium`                                                                                              |
| constant | `PMCC_LEAPS_ROLL_WINDOW_MAX_DTE = 60`                                                                 |
| missing  | `leapsDte === null` → `missing_leaps_dte`; `leapsStrike` not numeric → `missing_strike`               |
| test     | `leapsDte >= 0 && leapsDte <= 60`                                                                     |
| summary  | `LEAPS expires ${inDays(leapsDte)} at ${formatStrike(leapsStrike)} strike — review for roll or close` |
| action   | `Review position` (registry default)                                                                  |

  "The `missing_strike` guard exists so `formatStrike` never renders a fake `$0.00` from a
  null strike. In practice a LEAPS leg always has a strike."
- **Source:** `plans/us-107/data-model.md` § Rule
- **Implementation:** `src/main/core/alerts.ts`

### `AlertEvaluationInput` / `RuleDefinition` / `EvaluableRow` (type deltas)

- **Type:** other (TypeScript types)
- **Shape:** `AlertEvaluationInput` `+ leapsDte: number | null`, `+ leapsStrike: string | null`

- **Source:** `plans/us-107/data-model.md` § Entities touched, § Type Design
- **Implementation:** `src/main/core/alerts.ts`, `src/main/services/evaluate-alerts.ts`,

## Acceptance Criteria

Linear OPT-15 is the authority; the plan's audit table indexes the scenario families against e2e
test names (`plans/us-107/plan.md` § Acceptance coverage audit):

- **S1** Alert fires once the LEAPS has 60 days or fewer to expiration (60 / 59 / 30) — 3 cases
- **S2** Alert does not fire while the LEAPS has more than 60 days left (61 / 70) — 2 cases
- **S3** The queue row identifies the position as a PMCC and the LEAPS as the leg — 1 case
- **S4** A PMCC with only the LEAPS open is still evaluated for this rule — 1 case
- **S5** Alert resolves when the LEAPS is rolled out past the window — 1 case
- **S6** The short-call rules and the LEAPS rule co-fire without reading each other's leg — 1 case
- **S7** A LEAPS with no readable expiration keeps the alert open instead of resolving it — 1 case
- **S8** Classic wheel positions do not use the PMCC rule (MSFT CC_OPEN 59 / AAPL CSP_OPEN 20) — 2
  cases

"Total: 8 families, 12 named e2e cases." Exact summaries: `LEAPS expires in <n> days at $80.00
strike — review for roll or close`; S6 short row `Expires in 2 days at $112.00 strike`; S8 AAPL
`20 DTE remaining — review for roll or close`; S7 skip reason `missing_leaps_dte`.

## Decisions & Tradeoffs

- **Worked calendar** (issue calendar, LEAPS 2027-09-17 @ $80, short 2027-08-20 @ $112):
  2027-07-09 (70) and -07-18 (61) → no LEAPS row; -07-19 (60), -07-20 (59), -08-18 (30) → MED row;
  -08-18 also HIGH `Expires in 2 days at $112.00 strike`; -09-15 (2, short expired) → MED row,
  short-leg rules inapplicable so stale rows resolve; rolled to 2028-01-21 @ $85 → 185 DTE,
  resolves. (`plans/us-107/data-model.md` § Worked examples.)
- **Applicability table:** wheel → short-leg rules apply, LEAPS rule inapplicable; PMCC LEAPS +
  short → short-leg rules read the short, LEAPS rule reads the LEAPS; PMCC LEAPS only → short-leg
  rules inapplicable; PMCC LEAPS expiration unreadable → LEAPS rule skips `missing_leaps_dte`;
  PMCC no LEAPS / inactive → not evaluated. "Inapplicable rules contribute no key, so their prior
  alerts resolve … Skipped rules contribute a keep-open key (S7)." (`data-model.md` § Applicability.)
- **Lifecycle** is all existing US-50/US-59 behaviour: insert on first ≤ 60 DTE; refresh summary in
  place (same id and `triggered_at`); dismissed stays dismissed; roll past 60 → resolve; unreadable
  → skip keeps row unchanged; position closed → resolve. (`data-model.md` § Lifecycle.)
- **Nested `short: {...} | null` input rejected:** "would make 'short absent'
  unrepresentable-with-fields, but would rewrite every rule and fixture; out of proportion here."
  (`data-model.md` § Type Design.)
- **Badge follows the user's decision, not the mockup:** "use the leg-aware label instead of the
  mockup's plain `PMCC`." Mockup prototype pieces not shipped: "the gold row highlight, the 'why the
  LEAPS is in the queue' `StatGrid`, the `DteRuler`, the explanation `AlertBox`es and the preset
  controls. There is no new sheet, overlay or post-success navigation, and no extra visual treatment
  for the unreadable-expiration state." Keep the branch inline; "no strategy-badge component."
  (`plan.md` Area 5.)
- **Area 1 temporary phase gate:** the rule first gated inline on `input.phase === 'PMCC_OPEN'` so
  Area 1 was green alone; Area 2's `leg: 'leaps'` replaced it. (`plan.md` Areas 1–2.)
- **Property tests:** oracle "match ⇔ `0 <= leapsDte && leapsDte <= 60` (the literal inequality, not
  the predicate)"; guard for every non-PMCC phase; leg independence (LEAPS fields leave the set of
  non-LEAPS-rule matches and skips unchanged vs. the same input with them nulled); inapplicability
  guard (PMCC with `instrumentType: null` → only PMCC_LEAPS_ROLL_WINDOW may appear). Stressed at 500
  runs across ~5 seeds. (`plan.md` Areas 1–2; `tasks.md`.)
- **E2E harness:** Electron dates run-day relative — "the LEAPS at the scenario's DTE and the short
  28 days earlier"; fake market session closed; `delete env.VITEST` and capture
  `app.process().stdout` for the S7 log check; US-106's spec-local `launch` / `createXyzPmcc` "extract
  … into `e2e/pmcc-alert-helpers.ts` only if the new spec lifts them verbatim". No hand-inserted alert
  rows, no clock or quote IPC. (`plan.md` Area 6; `quickstart.md`.)
- **Logging:** "no new log calls are expected." The generic DEBUG `alert_rule_skipped` carries
  `ruleCode: 'PMCC_LEAPS_ROLL_WINDOW'`, `reason: 'missing_leaps_dte'` for S7; nothing in `core/`.
  (`quickstart.md`.)
- **Linear technical note left as is:** it "still says 'extend `EVALUABLE_QUERY` and
  `activeLegSubquery`'. US-106 rejected that route …; ADR 3 above follows the shipped design."
  (`research.md` § Out of scope.)
