# Extract: us-106

## Summary

"Add a medium-urgency PMCC short-call alert beginning 2% below its strike and remaining active at
every higher price. Reuse PMCC leg replay, the alert registry and persistence lifecycle, and the
existing management queue with a PMCC badge. Done means the current short alone feeds all applicable
short-leg rules, with wheel behavior preserved and every Linear scenario verified." Linear story:
OPT-14 / US-106 (Linear remains the requirements authority). Mockup:
`mockups/us-106-pmcc-assignment-risk-alert.mdx`. As shipped, `PMCC_ASSIGNMENT_RISK` "opens when the
underlying trades within 2% **below** a PMCC short-call strike, and stays open at any price at or
above the strike. The alert is a floor with no ceiling. Getting there also makes a PMCC evaluable by
the alert engine for the first time, with its **current short call** as the evaluated leg and never
the LEAPS. So the generic short-leg rules (EXPIRATION_IMMINENT, MANAGEMENT_WINDOW, PROFIT_TARGET,
EARNINGS_PROXIMITY) now apply to PMCC short calls too." Why: "A PMCC has no shares to deliver. If its
short call is assigned, the LEAPS has to be exercised or sold to cover, which ends the position. The
moment to roll up-and-out therefore comes on the way **up** to the strike, not at it … A two-sided
band like the CSP rule's (US-55) would wrongly resolve the alert as the stock ran through the
strike." **No schema, migration, or production IPC change.** All nine Linear scenario families (15
named e2e cases) pass; full suite 289 files / 4648 tests green after refactor. One accepted known gap:
an expired PMCC short stays "current" until US-119 / US-111 add production writers for closing
short-call legs. (Source: `plans/us-106/plan.md` Summary; `docs/us-106-implementation.md`;
`plans/us-106/refactor-phase-results.md`; `plans/us-106/data-model.md`.)

## Architecture Decisions

### ADR: Extend the existing rule registry with `PMCC_ASSIGNMENT_RISK`

- **Decision:** "Add `PMCC_ASSIGNMENT_RISK` to `RuleCode` and `RULES` in `src/main/core/alerts.ts`,
  with medium urgency and fixed `PMCC_ASSIGNMENT_RISK_MAX_PERCENT_BELOW = 2`. Match only `PMCC_OPEN`
  and compare the unrounded Decimal signed distance `(strike - price) / strike * 100 <= 2`. Reuse
  `priceVsStrikeMissingData('PMCC_OPEN')`, `proximityPercent`, `formatStrike` and the existing Review
  position action; add `pmccAssignmentRiskSummary`." One new registry entry; the evaluation loop is
  unchanged.
- **Why:** "The existing engine already returns matches and per-rule skips; storage and queue
  consumers accept additional rule codes. Absolute distance is appropriate for the displayed
  magnitude, but would incorrectly clear a deep-ITM call if used as the predicate. Direction uses
  `price >= strike`, including ATM."
- **Alternatives considered:** "A new engine, configurable threshold, absolute band, DTE-dependent
  urgency, and modifications to the wheel predicates are unnecessary or excluded by the issue. No new
  dependency is needed."
- **Refactor outcome:** `strikeProximitySummary` and `pmccAssignmentRiskSummary` both call one
  extracted `priceDirection(input)`, "which documents that at-the-money reads 'above'."
- **Source:** `plans/us-106/research.md`; `plans/us-106/refactor-phase-results.md` §1;
  `docs/us-106-implementation.md`

### ADR: Predicate uses the unrounded value; display uses rounded magnitude

- **Decision:** Predicate on unrounded signed Decimal distance; display
  `proximityPercent(input).toFixed(1)`, strike to two decimals. "The predicate uses the unrounded
  value, so a price like 107.7999, which *displays* as '2.0% below', stays outside the band." At the
  money reads "0.0% above".
- **Why:** Prevents entry through display rounding; keeps deep-ITM calls matched.
- **Source:** `plans/us-106/data-model.md` § Rule computation; `docs/us-106-implementation.md`

### ADR: Reuse PMCC replay (`currentShortCallLeg`) without broadening wheel active-leg SQL

- **Decision:** "Keep wheel `EVALUABLE_QUERY` and `activeLegSubquery()` unchanged. In
  `evaluate-alerts.ts`, additionally select ACTIVE PMCC positions in `PMCC_OPEN`, bulk-load their legs
  with `readLegsByPosition`, and resolve each short with `currentShortCallLeg`. Map a non-null short
  to the existing `EvaluableRow` shape before the existing market-data prefetch. Exclude a null short.
  Wrap each replay in its own error boundary." Shipped as `PMCC_CANDIDATE_QUERY` plus a
  module-private `loadPmccEvaluableRows({ db, failedIds, logger })` (object parameter after
  refactor).
- **Why:** "Source has already implemented short-leg replay in `src/main/services/pmcc-ledger.ts`: it
  handles paired rolls, ignores LEAPS rolls, and clears expired, closed or assigned shorts.
  `PMCC_OPEN` alone does not prove a short exists. `activeLegSubquery` also serves `get-position.ts`
  and `list-positions.ts`; broadening it would populate PMCC's deliberately null legacy `activeLeg`.
  Reuse the existing bulk reader instead of adding N+1 reads."
- **Alternatives considered:** "The issue suggests extending the shared SQL selector. This plan
  deliberately refines that technical note based on current source. Selecting the newest CALL or
  ROLL_TO can select the LEAPS or resurrect a closed short. Reimplementing replay in SQL duplicates
  established behavior."
- **Source:** `plans/us-106/research.md`; `plans/us-106/data-model.md` § Short-leg selection;
  `plans/us-106/refactor-phase-results.md` §4

### ADR: Generic short-leg rules ride along on the PMCC short

- **Decision:** "Feed the selected short's strike, expiration, premium, contracts and CALL OCC symbol
  into the existing engine. EXPIRATION_IMMINENT, MANAGEMENT_WINDOW, PROFIT_TARGET and
  EARNINGS_PROXIMITY intentionally ride along, as OPT-14 explicitly requires. Keep both
  wheel-specific rules phase-gated." "Only the short call's OCC symbol is ever requested; the LEAPS is
  never fed to the engine."
- **Why:** "The generic rules already have the right predicates; no extra dispatch layer is needed."
- **Alternatives considered:** "Duplicating the generic rules for PMCC or suppressing them
  contradicts the story."
- **Source:** `plans/us-106/research.md`; `docs/us-106-implementation.md`

### ADR: Replay failure is not a null short (failure isolation)

- **Decision:** "Selection failure is not a null short. Track failed candidate ids in a local
  `Set<string>`, log `alert_evaluation_failed`, and preserve the keys of their existing open/dismissed
  rows in the final keep-open set. Read those keys only for failed ids, using a prepared query with
  bound parameters. A bulk PMCC history-read failure logs and marks all PMCC candidates failed,
  allowing the wheel rows to continue. No new rule skip reason or public response field is
  introduced for a replay exception." A successful replay returning null resolves normally.
- **Why:** "`groupRollChains`, called by replay, parses Decimal data and may throw, so selection must
  not add an unguarded failure before the existing per-position loop. A successful replay returning
  null is distinct from a replay failure." A failed position "is unknown, not confirmed closed."
- **Alternatives considered:** "Leave unrelated existing engine-error behavior outside this change."
- **Source:** `plans/us-106/research.md`; `plans/us-106/data-model.md`

### ADR: Reuse persistence and interfaces unchanged

- **Decision:** "Reuse `upsertOpenAlert`, `resolveAlertsNotIn`, `clearStaleDismissals`, and
  `listManagementQueue` in `src/main/services/alerts.ts`. Add no schema, migration, production IPC
  channel, preload payload, or settings field."
- **Why:** "`rule_code` is stored as TEXT. Queue results already contain `phase`; the shared phase
  enum already contains `PMCC_OPEN`. Missing/malformed quotes produce `missing_underlying_price` and
  preserve previous summaries. Dismissal, dedupe and clear/refire behavior are rule-neutral."
- **Alternatives considered:** "New alert storage or a queue `strategyType` field would add contracts
  without information this story needs."
- **Source:** `plans/us-106/research.md`

### ADR: Queue badge branches on phase, not rule code

- **Decision:** "In `ManagementQueueRow`, branch only the badge cell when `item.phase ===
  'PMCC_OPEN'`. Use `Badge` and the compact gold-dot `PMCC · short call` label from the mockup; keep
  `PhaseBadge` for wheel rows." Badge column widened from 110px to 150px. "Because the branch keys on
  phase, a HIGH expiration-imminent row on a PMCC gets the same badge."
- **Why:** "`PhaseBadge` currently renders a valid but long PMCC phase label, rather than the
  requested strategy badge. No standalone PMCC badge component exists to import."
- **Alternatives considered:** "Do not ship the mockup's explanatory panel, `StrikeRuler`, gold row
  highlighting or preset controls: they explain the prototype states and are not requested
  production UI. There is no new sheet, form, success banner or detail-page alert." A strategy
  component hierarchy was rejected — "A small inline badge branch is sufficient."
- **Source:** `plans/us-106/research.md`; `plans/us-106/data-model.md` § Renderer design;
  `docs/us-106-implementation.md`

### ADR: Preload `ManagementQueueItem` aliases the schema type

- **Decision:** "The global is now an alias of the schema's `ManagementQueueItem` (`phase:
  WheelPhase`), so the cast is gone and the new `=== 'PMCC_OPEN'` branch is type-checked."
  (Supersedes the data-model's "Unchanged" note for this type.)
- **Why:** "The preload hand-copied the queue item with `phase: string`, which forced `item.phase as
  WheelPhase` in the row."
- **Source:** `plans/us-106/refactor-phase-results.md` §3

### ADR: Deterministic verification

- **Decision:** "Core/service tests pin the issue's dates and exact money strings; run service cases
  with `TZ=America/New_York` and explicit noon-UTC `now` values. Electron tests use the existing
  run-day-relative convention, preserving 18 DTE initially and 4 DTE in the imminent case." Use fake
  market data, scheduler run-now, real PMCC creation and short-roll IPC, and the existing
  `testPmccRecordLegEvent` seam for `SHORT_CALL_EXPIRED`. Capture DEBUG pino output for the
  missing-quote assertion (clear inherited `VITEST`, build with `MAIN_VITE_LOG_LEVEL=debug`).
- **Why:** "The alert scheduler uses real `new Date()`; the IVR fake clock does not control this
  job. Relative Electron dates avoid a new clock API and expired-fixture failures."
  "`setActiveLegExpiration` updates every leg and must not be used for PMCC."
- **Alternatives considered:** "Do not add production clock or quote controls." "Do not hand-insert
  alert rows to make the feature appear to work."
- **Source:** `plans/us-106/research.md`; `plans/us-106/quickstart.md`

### ADR: Logging

- **Decision:** "Preserve existing INFO/DEBUG events and per-item catches; log selection errors
  using `alert_evaluation_failed`, with position id when known." Missing quote surfaces as DEBUG
  `alert_rule_skipped` with the rule and `missing_underlying_price`. No logging in the pure engine.
- **Source:** `plans/us-106/plan.md` Area 2; `plans/us-106/quickstart.md`

## Acceptance Criteria

Verbatim from Linear OPT-14 (Gherkin):

- **Background:** valuation date 2026-09-28 in America/New_York; XYZ is a PMCC with one open XYZ
  $80.00 LEAPS call expiring 2027-09-17 and one open XYZ $110.00 short call expiring 2026-10-16, sold
  at $2.00 per share, 1 contract; the alert engine evaluates live underlying prices for positions
  with an open short option leg.
- **S1 — Alert fires as the stock approaches or passes the short-call strike:** a medium-urgency
  PMCC_ASSIGNMENT_RISK alert is open for XYZ with summary:
  - $107.80 → "Stock is 2.0% below the $110.00 short-call strike — approaching assignment"
  - $108.35 → "Stock is 1.5% below the $110.00 short-call strike — approaching assignment"
  - $110.00 → "Stock is 0.0% above the $110.00 short-call strike — in the money, LEAPS would have to cover"
  - $112.53 → "Stock is 2.3% above the $110.00 short-call strike — in the money, LEAPS would have to cover"
  - $118.80 → "Stock is 8.0% above the $110.00 short-call strike — in the money, LEAPS would have to cover"
- **S2 — Alert does not fire while the stock is more than 2% below the strike:** $107.70, $105.00 →
  no PMCC_ASSIGNMENT_RISK alert is created for XYZ.
- **S3 — The queue row identifies the position as a PMCC:** at $112.53, the XYZ row shows the MED
  urgency pill, a PMCC badge in place of a wheel phase badge, and the alert summary; the "Review
  position" quick action opens the XYZ position detail page.
- **S4 — Alert resolves when the stock retreats below the band:** with an open alert and price
  $106.00, the alert is marked resolved and the row no longer appears in the management queue.
- **S5 — Alert resolves when the short call is rolled further from the money:** after rolling to a
  XYZ $115.00 call expiring 2026-11-20 at $112.53, the alert is marked resolved and no new
  PMCC_ASSIGNMENT_RISK alert is created, because $112.53 is 2.1% below the new strike.
- **S6 — A PMCC with no open short call is not evaluated:** the $110.00 short call expired worthless
  on 2026-10-16 and only the LEAPS remains; at $118.80 no PMCC_ASSIGNMENT_RISK alert is created and
  any previously open one is marked resolved.
- **S7 — A missing quote keeps the alert open instead of resolving it:** with no XYZ price, the alert
  stays open with its previous summary and the rule is recorded as skipped for XYZ with reason
  "missing_underlying_price".
- **S8 — Classic wheel positions do not use the PMCC rule:** no PMCC_ASSIGNMENT_RISK alert, and the
  wheel's own rules behave as before:
  - MSFT CC_OPEN $420.00 at $415.00 → no COVERED_CALL_BREACH alert, because the stock is below the strike
  - AAPL CSP_OPEN $180.00 at $178.50 → a STRIKE_PROXIMITY alert reads "Stock is 0.8% below the
    $180.00 put strike — now in the money"
- **S9 — The existing short-leg rules evaluate the PMCC short call, never the LEAPS:** valuation date
  2026-10-12, price $112.53 → a high-urgency EXPIRATION_IMMINENT alert reads "Expires in 4 days at
  $110.00 strike"; the PMCC_ASSIGNMENT_RISK alert is also open; no alert for XYZ refers to the $80.00
  LEAPS strike or its 2027-09-17 expiration.

Out of scope (story technical notes): configurable threshold, ex-dividend/extrinsic modelling,
urgency escalation, LEAPS DTE alert (US-107), changes to STRIKE_PROXIMITY / COVERED_CALL_BREACH /
dismiss behaviour / PMCC card or detail page.

## Decisions & Tradeoffs

- **Floor with no ceiling.** The band is one-sided (signed distance), unlike the CSP rule's two-sided
  band, so a stock running through the strike keeps the alert open. (`docs/us-106-implementation.md`)
- **Closure follows recorded leg events, not dates.** "Do not infer closure merely from a past
  expiration date: closure follows recorded leg events. Do not introduce a new PMCC phase for this
  story. Do not populate the legacy `GetPositionResult.activeLeg` for PMCC."
  (`plans/us-106/data-model.md`)
- **Alert lifecycle table** (`plans/us-106/data-model.md`):

  | Input state                                                    | Existing lifecycle operation                                         |
  | -------------------------------------------------------------- | -------------------------------------------------------------------- |
  | Rule matches, no blocking row                                  | Insert open row.                                                     |
  | Rule continues matching                                        | Update existing row; preserve id and triggered time.                 |
  | Quote is missing or malformed                                  | Add skipped key; retain previous summary and open/dismissed state.   |
  | Price retreats, or rolled replacement is outside the threshold | Key absent; resolve existing open/dismissed row.                     |
  | No current short, or position inactive                         | Position absent from eligible targets; resolve its prior alerts.     |
  | User dismissed and rule still matches                          | Suppress new open row.                                               |
  | Condition clears then returns                                  | Resolve old lifecycle; create fresh open row.                        |
  | PMCC history read/replay fails                                 | Preserve existing keys for failed position; other positions proceed. |

- **Co-firing.** "A 4-DTE short can generate HIGH EXPIRATION_IMMINENT and MED PMCC_ASSIGNMENT_RISK
  simultaneously." HIGH sorts before MED in the queue. (`plans/us-106/data-model.md`)
- **Superseded US-101 test.** The US-101 blanket-exclusion test (PMCC produced no alerts) was
  replaced by a 5-DTE `EXPIRATION_IMMINENT` expectation. (`plans/us-106/red-phase-results.md`)
- **Property tests** in `alerts.property.test.ts`: "fires iff `price × 100 ≥ strike × 98` (an
  independent multiplication oracle over near-strike and arbitrary pairs); a firing price keeps
  firing as it rises; non-PMCC phases never match or skip. Stressed at 500 runs across seeds 1, 42,
  1337, 20261017 and 987654 with no counterexample." (`plans/us-106/red-phase-results.md`)
- **E2E helper fix.** "`e2e/alert-helpers.ts` `readAlertRows` now returns `[]` for an empty table.
  `sqlite3 -json` prints nothing at all in that case." (`plans/us-106/red-phase-results.md`)
- **E2E refactor.** S8 cases carry their own `wheelRule` / `wheelOutcome`; shared
  `expectNoLeapsReference` holds the "no `$80.00` / LEAPS expiration in any summary" check for S6/S9.
  (`plans/us-106/refactor-phase-results.md` §6)
- **Mockup elements not shipped:** explanatory amber/red/green panels, `StrikeRuler`, gold row
  highlight, preset controls; no missing-quote banner or detail-page alert. (`plans/us-106/research.md`)

## Open Questions

- **Accepted known gap (2026-10-17):** "When US-106 shipped, no production path wrote
  `SHORT_CALL_EXPIRED`, `SHORT_CALL_CLOSE` or `SHORT_CALL_ASSIGNED`; only the
  `_test:pmcc-record-leg-event` hook did. Until US-119 (OPT-25) records expiration/close and US-111
  (OPT-19) records assignment, a short past its expiration date remains the current short, and
  `PMCC_ASSIGNMENT_RISK` keeps firing while the stock is above its strike. Those stories close the gap
  by writing the closing leg; the alert service needs no change. Both issues carry a comment with the
  details and the e2e follow-up for S6." (`plans/us-106/data-model.md`;
  `plans/us-106/refactor-phase-results.md`)
