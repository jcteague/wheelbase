# Extract: us-62

## Summary

Added the `COVERED_CALL_BREACH` rule to the pure alert registry (`src/main/core/alerts.ts`) — firing medium-urgency when a `CC_OPEN` position's underlying trades at or above its short-call strike, reporting the percent above the strike so the trader can gauge how deep in-the-money the call has gone. The rule reuses the existing `AlertEvaluationInput.strike` / `.currentUnderlyingPrice` fields (already populated for every phase) and the existing US-51 queue, US-50 evaluation, persistence, and resolution machinery. No new tables, migration, IPC, or renderer change was needed. All five story ACs pass as named e2e tests; a breached call auto-resolves when the stock falls back below the strike and skips cleanly (keeping any open alert open) when the underlying price is unavailable.

## Architecture Decisions

### ADR: Rule shape — CC-only, medium urgency, price ≥ strike, co-fires with DTE rules

- **Decision:** `COVERED_CALL_BREACH` is `urgency: 'medium'`, quick action `Review position`, applies to `CC_OPEN` only, and fires when `phase === 'CC_OPEN' && strike !== null && currentUnderlyingPrice !== null && price ≥ strike`. Skip reason: `missing_underlying_price` when a `CC_OPEN` position has `currentUnderlyingPrice === null`. It co-fires independently of the DTE rules (`EXPIRATION_IMMINENT`, `MANAGEMENT_WINDOW`) per US-50 — each keeps its own queue row.
- **Why:** Medium urgency and the summary template come verbatim from the story ACs. The breach is the CSP strike-proximity rule's covered-call counterpart (US-55 is CSP-only); a breached covered call is a "good problem" that still demands a roll-vs-call-away decision. The `≥` boundary means the alert fires the moment the call is at-the-money (0.0% above). Co-firing follows the established US-53/54/55/56 decision — orthogonal conditions, no AC asks for suppression.
- **Alternatives considered:** Extending US-55's `STRIKE_PROXIMITY` to cover CCs (rejected: different semantics — proximity is a two-sided band around the strike, breach is a one-sided price ≥ strike trigger). PMCC short-call-against-LEAPS assignment is a structurally different concern deferred to Epic 09.
- **Source:** `plans/us-62/plan.md`, `plans/us-62/research.md`, `docs/epics/07-stories/US-62-covered-call-breach-alert.md`

### ADR: Shared `PriceVsStrikeInput` slice for the two price-vs-strike rules

- **Decision:** Introduced `export type PriceVsStrikeInput = Pick<AlertEvaluationInput, 'strike' | 'currentUnderlyingPrice'>` as the shared shape; `StrikeProximityInput` (US-55) and `CoveredCallBreachInput` (US-62) are aliases of it, and the shared `proximityPercent` helper is typed to `PriceVsStrikeInput`. The breach summary reuses `proximityPercent(...).toFixed(1)` and `formatStrike(...)` — when `price ≥ strike` the absolute-value `proximityPercent` equals the signed percent-above.
- **Why:** Makes the shared helper's contract rule-neutral and explicit rather than a structural coincidence, while preserving the per-rule named slices for consistency with the sibling rules (`ProfitTargetInput`, `EarningsProximityInput`). Follows the established narrow-Pick helper-input convention.
- **Alternatives considered:** Relying on structural compatibility between two independent identical Picks (rejected in the refactor phase: implicit); a discriminated union across rule inputs (rejected: over-engineered for two identical shapes).
- **Source:** `plans/us-62/plan.md`, `plans/us-62/refactor-phase-results.md`

## Contracts

None recorded. The story adds no new IPC surface; alerts are read through the existing US-51 `alerts:list` handler unchanged, and the new `rule_code` value flows through transparently.

## Schema Changes

None recorded. The story reuses the US-50 `alerts` table — `rule_code` is plain `TEXT NOT NULL` with no CHECK constraint, so `'COVERED_CALL_BREACH'` is just a new value under the existing partial-unique open-alert index `(position_id, rule_code) WHERE status = 'open'`. No migration, no `schemas.ts` change.

## Acceptance Criteria

- Alert fires when the stock rises above the covered-call strike (MSFT `CC_OPEN` at $420.00 strike, price $427.40 → medium-urgency `COVERED_CALL_BREACH`, summary exactly `Stock is 1.8% above the $420.00 call strike — shares may be called away`)
- Alert does not fire while the stock is below the covered-call strike (MSFT `CC_OPEN` at $420.00, price $416.00 → no alert)
- Alert resolves when the stock falls back below the strike (open alert at $427.40, next evaluation at $415.00 → marked resolved)
- Cash-secured-put positions do not use this covered-call breach rule (AAPL `CSP_OPEN` at $180.00, price $185.00 → no `COVERED_CALL_BREACH` alert)
- Holding-shares positions without an open call are not evaluated (TSLA `HOLDING_SHARES`, no open call → not evaluated; excluded by the evaluable-position query)

Each AC has exactly one named e2e test in `src/main/services/evaluate-alerts.e2e.test.ts` (`describe('US-62 acceptance — COVERED_CALL_BREACH')`). Unit coverage lives in `src/main/core/alerts.test.ts` (`describe('evaluatePosition — COVERED_CALL_BREACH (US-62)')`), including the exact-at-strike 0.0% boundary and the co-fire-with-DTE-rules case.

## Decisions & Tradeoffs

- **Percent-above via the existing absolute-value helper:** `proximityPercent` returns an absolute gap; because the breach only fires at `price ≥ strike`, the absolute percent equals the signed percent-above, so no new signed helper was needed. (`plans/us-62/plan.md`)
- **No production code beyond the pure engine:** the e2e tests exercise the existing service selection (`EVALUABLE_QUERY` restricts to `ACTIVE` `CSP_OPEN`/`CC_OPEN` with an active short-option leg, excluding `HOLDING_SHARES`), persistence (`upsertOpenAlert`), and resolution (`resolveAlertsNotIn` + `skippedKeys`) paths — no service, IPC, or renderer change. (`plans/us-62/plan.md`, `plans/us-62/data-model.md`)
- **Quick action stays generic:** `Review position` in Phase 3; roll-up-and-out automation is out of scope until order execution (Phase 4) lands. (`docs/epics/07-stories/US-62-covered-call-breach-alert.md`)
- **E2e fixtures reuse the shared helpers:** the `US-62 acceptance` block uses only `evaluate-alerts-test-utils.ts` helpers (`seedShortOptionAtPremium`, `stubProvider`, `expirationForDte`, `seedPosition`, `listOpenAlerts`, `readAlertRows`); the local `seedMsftCc` fixture mirrors the sibling `seedNvdaCc`/`seedAaplCsp` pattern. (`plans/us-62/refactor-phase-results.md`)
