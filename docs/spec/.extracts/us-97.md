# Extract: us-97

## Summary

Widens the nightly IVR collection targets from open positions only to the **union of open
positions and the watchlist**, so IV rank is populated for the bench names the screener
actually ranks. IV rank is how a premium seller decides whether selling a put on a name is
worth the capital at all — a judgement made *before* a position exists — but the US-44
collector picked its batch from `positions` alone, so every watchlist-only candidate joined
the ranked list with `ivRank: null`. US-65 wired the field, US-96 builds acceptance criteria
on it, and US-67's IV-rank floor could never fire on a bench name because those names had no
reading to compare against. The production change is one SQL statement plus per-ticker
failure isolation; everything downstream of the target list was already target-agnostic.

## Architecture Decisions

### ADR: IVR collection targets are the union of open positions and the watchlist

- **Decision:** Replace `ACTIVE_UNDERLYINGS_QUERY` with `COLLECTION_TARGETS_QUERY` —
  `SELECT ticker FROM positions WHERE status != 'CLOSED' UNION SELECT ticker FROM watchlist`
  — and rename `listActiveUnderlyings` to `listCollectionTargets`. The existing
  `toUpperCase()` → `Set` → `localeCompare` normalisation stays untouched.
- **Why:** One query, one loop, one set of counters. The collector's rate limiting, failure
  isolation, and same-day overwrite semantics are all downstream of the target list, so
  widening the list is the entire change. `UNION` (not `UNION ALL`) keeps the row set small
  before the in-memory `Set`; SQL de-duplicates case-sensitively and the `toUpperCase()`
  that follows closes the `spy`/`SPY` gap. Together they are what guarantee a ticker that is
  both held and watchlisted is fetched exactly once.
- **Supersedes:** the US-44 ADR "IVR collection targets come from active positions"
  (`../architecture/02-adrs/active-ivr-targets-from-positions.md`).
- **Alternatives considered:** A second collection pass over the watchlist (rejected:
  doubles the loop, splits the counters, and needs its own dedupe against the first pass);
  reusing `listWatchlist()` + `listPositions()` and merging in TypeScript (rejected for the
  same reason US-44 rejected `listPositions()` — those compute renderer-facing fields the
  collector does not need, and one SQL statement is simpler to test).
- **Source:** `plans/us-97/research.md`, `plans/us-97/data-model.md`

### ADR (as-built): Per-ticker failure isolation in the collection loop

- **Decision:** Wrap each ticker's **fetch** in `try/catch`, counting a thrown failure as
  `errorCount` with a WARN logged under the `err` key. A `persistSnapshot` throw is systemic
  and aborts the run as a run-level failure; pacing is delegated to the scraper's internal
  1 req/s rate limiter (the collector's extra sleep was removed).
- **Why:** CLAUDE.md's batch-job rule requires per-item isolation, and this loop had none.
  The scraper does not return every failure as a status: `fetchIVR` parses the response body
  outside a `try`, so a non-JSON body (interstitial, captcha, HTML error page) *rejects*
  rather than returning a `network_error`. `persistSnapshot` can throw too. Because
  `PollingScheduler.runHandler` catches a rejected handler and returns `undefined`, an
  unguarded throw aborted the batch and lost every ticker after the offending one — and on
  the manual path `CollectIvrNowBatchSchema.parse(undefined)` then threw, giving the trader
  a generic error with no summary.
- **Why now:** pre-existing in US-44, but this story is what amplifies it. The batch moves
  from "names the trader holds" to arbitrary speculative bench names, which are far likelier
  to be uncovered and so likelier to provoke exactly those odd responses.
- **Logging detail:** the caught value is logged as `err`, not `error`. `src/main/logger.ts`
  configures `pino({ level })` with no custom serializers, and pino applies its Error
  serializer only to the `err` key — under any other key a thrown `Error` stringifies to
  `{}` (its `message`/`stack` are non-enumerable), so the one line that exists to diagnose
  the failure would carry nothing. The two branches also log distinct messages
  (`IVR collection failed for ticker` vs `IVR collection threw for ticker`) because a
  returned error status and a broken scraper contract are operationally different.
- **Source:** as-built; not anticipated in the plan

### ADR: Minimal pending state on "Refresh IVR now"

- **Decision:** Disable the Settings "Refresh IVR now" button while `collectIvrNow.isPending`
  and swap its label to `Refreshing IVR…`. Nothing else — no progress bar, no per-ticker
  feedback.
- **Why:** The story's Technical Notes ask to *confirm* the manual affordance shows a pending
  state; it did not. A watchlist-length run is now the case where a human waits, and at the time
  `scheduler.runNow` had no overlap guard, so a double-click launched two concurrent Barchart
  batches. Disabling the button is the smallest change that closes both gaps and is the
  existing shadcn/TanStack idiom on the page (`disabled:opacity-40`, matching the neighbouring
  disabled button rather than inventing a variant).
- **Alternatives considered:** Do nothing, on the grounds the story says "no renderer surface"
  (rejected: the story names the manual-trigger wait as a thing to check, and the check found a
  gap); add an in-flight guard to `scheduler.runNow` (initially rejected as its own story; review
  hardening then added it — `runNow` joins an in-flight run and a firing tick skips one,
  closing the scheduled-vs-manual overlap).
- **Source:** `plans/us-97/research.md`

### ADR: E2E harness drops the throwaway-position workaround, and guards its replacement

- **Decision:** `seedIvr` in `e2e/screener-helpers.ts` stops seeding a throwaway active CSP per
  ticker; the tickers are already on the watchlist via `launchScreener`. `seedWatchlist` moves
  to `e2e/ivr-helpers.ts` (screener-helpers already imports from it, not the reverse), joined by
  `removeFromWatchlist` and `seedClosedPosition`. `seedIvr` gains `assertIvrTickersCollectible`,
  which throws if an `ivr` key is not a fixture ticker.
- **Why:** The workaround existed only because of the gap this story closes. Leaving it in would
  make the screener e2e suite silently depend on positions while claiming to test the bench, and
  would hide a regression of this story. The guard exists because removing the workaround
  introduced a *new* silent failure: the collector reaches a ticker only if it is on the
  watchlist, and `launchScreener` seeds the watchlist from `fixtures` — so an `ivr` key that is
  not a fixture ticker now persists nothing at all, with no error. Six call sites in
  `e2e/screener-earnings.spec.ts` were asking for exactly such inert rows and were narrowed to
  the tickers they actually screen. The file's existing `assertClearOffsetUsable` is the
  precedent for failing loudly on this class of harness mistake.
- **Alternatives considered:** Leave the workaround (rejected: it is exactly the kind of "why is
  this here" code the next reader trips over); let `seedIvr` add non-fixture tickers to the
  watchlist itself (rejected: that changes what the screener screens, so it would alter the
  inputs of unrelated earnings and criteria specs).
- **Source:** `plans/us-97/research.md`, as-built

## Contracts

No new IPC surface. `ivr:collect-now` and `CollectIvrNowBatchSchema` are unchanged, and
`CollectIVRSnapshotsResult` keeps its shape — `{ successCount, errorCount, skippedCount,
skippedReason }`. The counts now span watchlist and position tickers together; there is no
per-source breakdown.

## Schema Changes

None. No migration. `watchlist` (US-63, `migrations/012_create_watchlist.sql`) and
`ivr_snapshot` (US-44, `migrations/007_create_ivr_snapshot.sql`) both already existed. Every
watchlist column other than `ticker` is ignored by the collector — being on the list is the
only criterion.

## Acceptance Criteria

Background: the watchlist holds KO, AAPL, and XYZ; the trader holds an open CSP on MSFT;
MSFT is not on the watchlist.

- **Watchlist underlyings are collected alongside held positions.** IVR is fetched for KO,
  AAPL, XYZ, and MSFT; the summary reports 4 succeeded, 0 skipped, 0 errors.
- **A watchlisted ticker with only a closed position is still collected.** KO's only position
  is CLOSED → IVR is still fetched for KO.
- **A ticker that is both held and watchlisted is collected once.** AAPL watchlisted with an
  open CSP → fetched exactly once, exactly one AAPL snapshot for the day.
- **A watchlist ticker with no IVR coverage is skipped, not failed.** Barchart does not cover
  XYZ → 3 succeeded, 1 skipped, 0 errors; KO, AAPL, and MSFT each have a fresh IV rank.
- **One ticker failing does not suppress the others.** KO's fetch fails → AAPL, XYZ, and MSFT
  are still attempted, the KO failure is logged at warn level, and the summary reports
  3 succeeded, 0 skipped, 1 error.
- **Removing a ticker from the watchlist stops future collection.** KO removed with no open
  position → no new KO snapshot is written, and yesterday's KO snapshot is still readable.
- **The manual collect-now trigger covers the watchlist too.** TSLA just added → the manual
  trigger fetches IVR for TSLA.
- **A screened candidate shows a real IV rank instead of n/a.** KO watchlisted with no open
  position and a recorded IVR of 38.0 → the KO candidate row shows an IV rank of 38.0.
- **A populated IV rank lets the screener's IV floor apply to a bench name.** KO at IVR 22.0
  with an IV-rank floor of 30 → KO appears in the excluded list with reason
  `IV rank 22.0 below 30`.

## Decisions & Tradeoffs

- **The IV-rank floor now bites bench names, deliberately.** US-67's `iv_rank_floor`
  (`src/main/core/screener.ts`) applies only when `ctx.ivRank !== null`. Before this story a
  watchlist-only ticker always read `null`, so the floor could never exclude it. Now a bench
  name with a thin IVR *will* drop out of the ranked list when the floor is enabled — which is
  exactly what the trader asked the floor to do. This is covered by an acceptance criterion,
  not an accident.
- **Runtime cost grows with the watchlist.** Collection is sequential, paced by the scraper's
  internal 1 req/s rate limiter, so the after-close run grows by roughly one second per name: a
  25-name watchlist turns a 5-name run into a ~30 second run. Acceptable for a job firing 60
  minutes after close, but it argues against letting the watchlist grow unbounded without
  revisiting the pacing. The same growth lands on the awaited "Refresh IVR now" click, which is
  why the pending state was added.
- **The skip count becoming non-zero is normal, not breakage.** `not_available` (ticker not
  covered by Barchart) was already handled as a skip rather than an error. That path is
  exercised far more often now — speculative bench names are likelier to be uncovered than
  names the trader already holds.
- **Existing e2e counts were not disturbed.** `e2e/ivr-collector.spec.ts` (US-44) seeds no
  watchlist rows, so its exact `skippedCount`/`successCount` assertions are unaffected — the
  risk the story's Technical Notes flagged did not materialise. In the screener harness, MSFT
  is now a watchlist target with no programmed outcome, so it is fetched, skipped, and still
  renders `n/a`.
- **The collect-once AC is inherently weak.** Its tests seed an *open* AAPL position plus
  watchlist AAPL, which the old positions-only query also fetched exactly once — and the
  pre-existing `new Set(...)` guarantees dedup regardless of `UNION` vs `UNION ALL`. The AC is
  worth stating, but its tests pin nothing the old code failed.

## Open Questions

- **Staleness is still unhandled.** `getLatestIvrByUnderlying` returns the newest row
  regardless of age, so a ticker that stopped being collected (removed from the watchlist, or
  dropped by the scraper) still reports its last known IVR with no age signal. This gets more
  likely with bench names. Deciding the tolerance and the UI treatment is its own story.
- **`getMarketStatus` degrades instead of rejecting (closed in review hardening).** The broker
  call at the top of `collectIVRSnapshots` is wrapped: on failure — or with no broker configured
  at all — the run logs and assumes a trading day, satisfying the "boundary I/O must degrade
  rather than reject the whole run" half of the same CLAUDE.md batch-job rule. Barchart needs no
  broker, so the watchlist-only trader still gets collection.
- **Scheduled-vs-manual overlap (closed in review hardening).** `scheduler.runNow` now joins
  an in-flight run and a firing tick skips one, so a manual run can no longer overlap the
  scheduled one.
- **Stale doc comments predate US-67's floor.** The `readIvRanks` comment in
  `src/main/services/screener.ts` and US-98's Out of Scope both still say IVR is "display-only
  and never a hard filter". Flagged by the story as a separate docs pass.
