# Data Model: US-104 — Roll the PMCC short call

## 1. Entities

### `legs` (existing table, no migration)

A short-call roll appends two rows sharing one fresh `roll_chain_id`. Every other column follows
US-14's covered-call roll; `fees` (migration 017) is written as `'0.0000'`.

| Row         | `leg_role`  | `action` | `instrument_type` | `strike`          | `expiration`    | `contracts`  | `premium_per_contract` = `fill_price` | `fill_date`                | `roll_chain_id` |
| ----------- | ----------- | -------- | ----------------- | ----------------- | --------------- | ------------ | ------------------------------------- | -------------------------- | --------------- |
| buy back    | `ROLL_FROM` | `BUY`    | `CALL`            | open short strike | open short exp. | open short's | `costToClosePerContract` (4 dp)       | `fillDate` (default today) | new UUID        |
| replacement | `ROLL_TO`   | `SELL`   | `CALL`            | `newStrike`       | `newExpiration` | open short's | `newPremiumPerContract` (4 dp)        | same                       | same            |

US-103's `groupRollChains` reads the pair as one chain with `netCreditPerShare = SELL − BUY`
(`2.40 − 3.00 = −0.6000`), and `buildPmccContributions` classifies it `SHORT` because
`rollFrom.action === 'BUY'`.

### `cost_basis_snapshots` (existing table, no migration)

Written **only** by US-103's `appendPmccSnapshot`, inside this service's transaction:

| Column                    | Value                                                       |
| ------------------------- | ----------------------------------------------------------- |
| `basis_per_share`         | `ledger.basisPerShare` after the roll (`21.8000` in the AC) |
| `total_premium_collected` | `ledger.shortCreditsTotal` (`320.0000`)                     |
| `final_pnl`               | `NULL`                                                      |
| `trigger_event`           | `'PMCC_SHORT_ROLL'` (US-103's `PmccTriggerEvent`)           |
| `snapshot_at`             | `makeSnapshotAt(fillDate)`                                  |

### `positions` (existing table)

Untouched. `phase` stays `PMCC_OPEN`; `updated_at` is not bumped (parity with `rollCcPosition`).

### `PmccOpenLegs` (in-memory, service-derived, carried on IPC)

| Field   | Type                | Rule                                                                                                                                                                                                          |
| ------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `long`  | `LegRecord`         | `currentLeapsLeg(legs)`: the newest long-side BUY — `LEAPS_OPEN`, or the `ROLL_TO` of the latest LEAPS roll (US-103's `newestLongBuy`, now exported)                                                          |
| `short` | `LegRecord \| null` | `currentShortCallLeg(legs)`: replay in `readLegs` order — `SHORT_CALL_OPEN` / short-chain `ROLL_TO` opens; `SHORT_CALL_EXPIRED` / `SHORT_CALL_CLOSE` / `SHORT_CALL_ASSIGNED` / short-chain `ROLL_FROM` closes |

`pmccOpenLegs(legs)` returns `null` when there is no long leg. `GetPositionResult.pmccOpenLegs` is
`null` for a wheel.

### `RollPmccShortCallInput` (engine input) and the rule table

See research.md § ADR "`rollPmccShortCall`". Eleven rules (1–10 plus 3b, fill date on/before the
open short's expiration), fixed order, first failure throws.

### `RollPmccShortCallResult` (service result, IPC success body)

| Field                 | Type                                                                            | Source                                 |
| --------------------- | ------------------------------------------------------------------------------- | -------------------------------------- |
| `position`            | `{ id; ticker; phase: 'PMCC_OPEN'; status: 'ACTIVE' }`                          | detail                                 |
| `rollFromLeg`         | `LegRecord & { legRole: 'ROLL_FROM'; action: 'BUY' }`                           | inserted row                           |
| `rollToLeg`           | `LegRecord & { legRole: 'ROLL_TO'; action: 'SELL' }`                            | inserted row                           |
| `rollChainId`         | `string`                                                                        | new UUID                               |
| `costBasisSnapshot`   | `CostBasisSnapshotRecord & { triggerEvent: 'PMCC_SHORT_ROLL'; finalPnl: null }` | `appendPmccSnapshot(...).snapshot`     |
| `ledger`              | `PmccLedgerResult`                                                              | `appendPmccSnapshot(...).ledger`       |
| `shortCallRollNumber` | `number` (≥ 1)                                                                  | short-side chains in `detail.legs` + 1 |

## 3. State transitions

None. `rollPmccShortCall` returns `phase: 'PMCC_OPEN'` (with the validated open short and the
resolved new strike — see § 4) and the service does not update the position row.

No new Zod enum, no new `LegRole` or `TriggerEvent` value (US-103 defined `'PMCC_SHORT_ROLL'`).

**Departure from the original design (recorded after review).** The plan specified
`newStrike: string` and an engine result of `{ phase: 'PMCC_OPEN' }`. The implementation instead
takes `newStrike?: string` and returns `{ phase; openShort: S; newStrike }`, generic over the
caller's short-leg type `S extends PmccShortCallTerms`. Reason: the engine owns both the
"no open short" rule and the "omitted strike means the current strike" default. With the plain
result, the service had to re-check `short === null` after the engine call only to narrow the type
for the inserts, and keep a never-read `?? 0` strike fallback. Returning the validated short (the
caller's own object, narrowed to non-null) and the resolved strike removes both: the service has
no dead re-check and no fallback.

**Fill date (review B1).** `PmccShortCallTerms` carries the open short's `fillDate` and the input
gains the roll's `fillDate`. Rule 3 rejects a roll filled before the open short was filled, with the
`close_date_before_open` code and wording of `requireFillDateOnOrAfterOpen`; since review it is
reported by `pmccShortRollIssues` with the other roll date rules. Without it, a too-early roll sorts before the open
short in `currentShortCallLeg`'s fill-date replay, so the closed short reads as still open.

**Shared roll rules (review).** The form schema used to re-spell rules 3, 8 and 10 and restate the
open short as `current*` fields. Now `pmccShortRollIssues` in `pmcc-rules.ts` is the one home of
rules 3 and 7–10; the engine throws its first issue in rule order, and the schema's `superRefine`
feeds it decided values (an incomplete ISO date or unparsable strike is `undefined`, so its rules
are skipped) and reports the first issue per path — on/after-current still wins over
expiration-after-fill. The fill-date input declares `deps: 'newExpiration'` so a fill-date change
re-validates rule 9, which reports on `newExpiration`.
