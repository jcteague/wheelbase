# Research: US-51 — Management Queue Dashboard

## Context

US-51 surfaces the open alerts already persisted by US-50 as a prioritized
"management queue" at the top of the dashboard. US-50 delivered the full alert
backend (engine, `alerts` table, scheduled evaluation) but **no renderer-facing
read path**. US-51 owns:

1. A sorted, position-enriched read path from `alerts` → renderer.
2. The `alerts:list` IPC surface + preload bridge + renderer adapter/hook.
3. The dashboard queue UI (queue card, rows, urgency pills, empty state).

### What already exists (verified)

- **`alerts` table** — `migrations/009_create_alerts.sql`. Columns: `id`,
  `position_id` (FK → `positions.id`), `rule_code`, `urgency`
  (`high` | `medium` | `low`), `summary`, `quick_action`, `status`
  (`open` | `resolved` | `dismissed`, default `open`), `triggered_at`,
  `last_evaluated_at`, `resolved_at`, `created_at`, `updated_at`. Index
  `idx_alerts_status_urgency (status, urgency)` already supports this read.
- **`listOpenAlerts(db)`** — `src/main/services/alerts.ts:140`. Returns
  `AlertRecord[]` for `status='open'` ordered by `rowid` (insertion order — **not**
  urgency, and **no ticker/phase**). Insufficient for the queue as-is.
- **`AlertRecord`** + `AlertUrgency`/`AlertStatus` types —
  `src/main/schemas.ts:462-488`. `AlertRecord` carries `positionId` but **not**
  `ticker` or `phase`.
- **Summary text** is generated by the US-50 engine and stored in
  `alerts.summary` (e.g. `Expires in 3 days at $180.00 strike`). US-51 displays
  it verbatim — no new summary generation.
- **Scheduled evaluation** runs every 60s (market open) / 300s (extended) and
  keeps `alerts` current. `alert-evaluation` job is registered in
  `src/main/index.ts` and runnable on demand via the test scheduler IPC
  (`window.api.testSchedulerRunNow('alert-evaluation')`).
- **IPC pattern** — `handleIpcCall` envelope (`src/main/ipc/utils.ts`), thin
  handlers (`src/main/ipc/assignments.ts` is the closest reference: a read-only
  `assignments:list-pending` returning `{ assignments: [...] }`).
- **Preload** — `window.api.*` in `src/preload/index.ts`, typed in
  `src/preload/index.d.ts` under `interface Window { api: { ... } }`.
- **Renderer adapter pattern** — `src/renderer/src/api/assignments.ts` +
  `usePendingAssignments` show the read-with-`refetchInterval` pattern returning
  `[]` on `!ok`.
- **Dashboard** — `src/renderer/src/pages/PositionsListPage.tsx`. Position grid
  renders under the `Active` `SectionHeader` (line 262). Queue belongs above it.
- **Reusable UI** — `SectionCard` (`header` + `children`), `PhaseBadge`
  (`phase`, `variant: 'default' | 'short'`; short label for `CSP_OPEN` = "CSP
  Open"), `Badge`. `wb-*` design tokens in `src/renderer/src/index.css`
  (`text-wb-red`/`bg-wb-red-dim` = high, `text-wb-gold`/`bg-wb-gold-dim` =
  medium, `text-wb-blue`/`bg-wb-blue-dim` = low).
- **Navigation** — hash router (wouter). Position detail route is
  `/positions/:id` (`src/renderer/src/App.tsx`). Existing cards navigate via
  `window.location.hash = `/positions/${id}``.

## Architecture Decisions

### ADR: New enriched + sorted read path `listManagementQueue(db)` rather than reusing `listOpenAlerts`

- **Decision:** Add a new service function `listManagementQueue(db)` in
  `src/main/services/alerts.ts` that JOINs open `alerts` to `positions` to
  attach `ticker` and `phase`, and returns rows already sorted by urgency tier
  then time. Leave `listOpenAlerts` untouched (still used by US-50 evaluation
  tests).
- **Why:** The queue UI needs `ticker` and the current `phase` badge, neither of
  which is on the `alerts` row. `listOpenAlerts` also sorts by `rowid`, which
  does not satisfy the "ordered by urgency then time" acceptance criterion. A
  dedicated function keeps the existing primitive's contract stable.
- **Alternatives considered:** (a) Sort/enrich in the renderer after calling a
  raw list — rejected: pushes business logic (urgency ranking, JOIN) into the UI
  and duplicates it per consumer. (b) Extend `listOpenAlerts` to JOIN and sort —
  rejected: changes a primitive relied on by US-50 tests and conflates the
  "raw open alerts" concept with the "display queue" concept.

### ADR: Sort by urgency rank (high→medium→low) then `triggered_at` ascending, in SQL

- **Decision:** Order with
  `ORDER BY CASE urgency WHEN 'high' THEN 0 WHEN 'medium' THEN 1 WHEN 'low' THEN 2 ELSE 3 END, triggered_at ASC`.
- **Why:** The story requires "urgency then time". High urgency surfaces first.
  Within a tier, the alert that has needed attention longest (oldest
  `triggered_at`) surfaces first — the most actionable ordering for a
  start-of-day triage list. Doing it in SQL keeps the service a thin mapper and
  leverages the existing `idx_alerts_status_urgency` index for the status filter.
- **Alternatives considered:** Sorting in JS with a rank map (matches
  `list-positions.ts` style) — viable, but SQL keeps ordering co-located with
  the query and avoids a second pass. `triggered_at DESC` (newest first) —
  rejected: a brand-new low-urgency alert would jump ahead of a long-standing
  one in the same tier, which is the opposite of triage intent.

### ADR: Dedicated `ManagementQueueItem` view-model type (not raw `AlertRecord`)

- **Decision:** Define a new `ManagementQueueItem` interface in
  `src/main/schemas.ts` with exactly the fields the UI needs: `alertId`,
  `positionId`, `ticker`, `phase`, `urgency`, `summary`, `quickAction`,
  `triggeredAt`. Mirror it in `src/preload/index.d.ts` and re-export the type
  from the renderer adapter `src/renderer/src/api/alerts.ts`.
- **Why:** `AlertRecord` carries audit fields (`lastEvaluatedAt`, `resolvedAt`,
  `createdAt`, `updatedAt`, `status`) that the queue does not use and lacks
  `ticker`/`phase` that it does. A purpose-built view-model keeps the contract
  honest and small. `alertId` is included to serve as a stable React `key` (one
  row per open alert per US-51 scope).
- **Alternatives considered:** Returning `AlertRecord & { ticker, phase }` —
  rejected: leaks unused audit fields across the IPC boundary and the type
  becomes ambiguous about what the queue depends on.

### ADR: `alerts:list` IPC handler in a new `src/main/ipc/alerts.ts`, registered as `registerAlertsHandlers`

- **Decision:** Add `ipcMain.handle('alerts:list', …)` in a new
  `src/main/ipc/alerts.ts` exposing `registerAlertsHandlers({ db })`, wired into
  `src/main/index.ts` alongside the other `register*Handlers` calls. Handler body
  is `handleIpcCall('alerts_list_error', () => ({ items: listManagementQueue(db) }))`.
- **Why:** Matches the thin-handler architecture rule (Zod-or-nothing + single
  service call inside `handleIpcCall`). Read-only with no request payload, so no
  Zod schema is needed. Mirrors `assignments:list-pending` exactly.
- **Alternatives considered:** Folding the channel into `positions.ts` —
  rejected: alerts are their own domain; a dedicated handler file matches the
  one-domain-per-file convention.

### ADR: Renderer fetches via `useManagementQueue` with a polling `refetchInterval`

- **Decision:** Add `src/renderer/src/api/alerts.ts` (`listManagementQueue()`
  adapter, returns `[]` on `!ok`) and `src/renderer/src/hooks/useManagementQueue.ts`
  (`useQuery` with `queryKey: ['alerts','queue']`, `refetchInterval: 30_000`).
- **Why:** The backend re-evaluates alerts on a 30–60s cadence; a matching
  renderer poll keeps the queue fresh without manual refresh, consistent with
  `usePendingAssignments` (`refetchInterval: 30_000`). Returning `[]` on error
  lets the queue degrade to its empty state rather than crash the dashboard.
- **Alternatives considered:** Push via an IPC event channel — rejected as
  out-of-scope for this slice; polling matches the existing read patterns and the
  evaluation cadence. Throwing `ApiError` like `usePositions` — the queue is a
  secondary surface, so silent empty-degrade is preferable to an error banner.

### ADR: Reuse `PhaseBadge` (short variant) and `SectionCard`; new `UrgencyPill` for tiers

- **Decision:** Build the queue inside a `SectionCard` (header "Management
  Queue"), render each alert as a `ManagementQueueRow`, reuse `PhaseBadge
variant="short"` for the phase, and add a small `UrgencyPill` component mapping
  `high|medium|low` → red/gold/blue `wb-*` tokens (labels HIGH/MED/LOW).
- **Why:** The story's Technical Notes mandate reusing `SectionCard` and
  `PhaseBadge` and the gold/red urgency accents. `PhaseBadge` short labels
  ("CSP Open"/"CC Open") match the mockup. A dedicated `UrgencyPill` isolates the
  tier→token mapping for reuse in future alert surfaces (US-59/60).
- **Alternatives considered:** Hand-rolling phase markup from the mockup's inline
  styles — rejected: violates the Tailwind-tokens-not-inline-styles rule and
  duplicates `PhaseBadge`.

### ADR: Render the queue unconditionally above the positions grid (component owns loading/empty)

- **Decision:** Mount `<ManagementQueue />` in `PositionsListPage` immediately
  after `AssignmentNotificationBanner` and above the `Active` section. The
  component calls `useManagementQueue` itself and renders the empty state when
  there are zero open alerts.
- **Why:** AC requires the queue "above the positions grid" and an empty-state
  message when there are no alerts — both are satisfied by always mounting it.
  Self-fetching keeps `PositionsListPage` from growing another data dependency.
- **Alternatives considered:** Gating the queue behind `data.length > 0` (the
  positions-present block) — rejected: the empty-alerts state must show even when
  positions exist, and the queue is conceptually independent of the positions
  query.
